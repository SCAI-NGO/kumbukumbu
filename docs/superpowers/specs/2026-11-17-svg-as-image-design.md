# SVG as an image

**Status:** approved by Chris on 2026-11-17. Version 0.6.0. Idea note: `/SWE/Kumbu/Ideas/Charts and SVG 2026-11-09.md`.

## Goal

A vault keeps SVG files beside its notes and shows them as images, embedded with `![[diagram.svg]]` as in Obsidian. Agents write SVG with `write`, read its source with `cat` and look at the rendered result with `img`, so they can correct what they drew instead of placing coordinates blind.

Why (decided 2026-11-15, roadmap): SVG is text, agents write it well, and it diffs and versions like a note. For sketches, schematics and icons it often beats Mermaid, because no layout engine gets in the way. As an image only, the feature stays small: inline SVG needs a sanitiser everywhere it is shown and waits in the backlog, towards 1.0.

## Decisions

1. **A format among the images.** `.svg`, `image/svg+xml`, kind `Image`, in `AttachmentFormat.All`; up to 15 MB like every attachment. Inside a skill's folder `.svg` stays a text file, as today (`AttachmentFormat.ForPath` checks the skill folder first).
2. **Checked as XML, not by magic bytes.** An SVG is accepted when it is well-formed XML whose root element is `svg` (the SVG namespace or none, as hand-written files often leave it out). The DTD is ignored, never resolved: files from Inkscape and Illustrator often carry one, and with `DtdProcessing.Ignore` and no resolver there is no XXE and no entity expansion. A leading BOM, XML declaration, comments and whitespace are allowed.
3. **Shown through `<img>` only.** The web app, publish pages and the SPA export show an SVG like every other image: fetched and shown through an object URL in an `<img>`, where no script runs and nothing external loads. Never `innerHTML`, never an `<object>` or `<iframe>`. Opened directly (a link, "open original", WebDAV), the response carries `Security.FileContentPolicy` (`sandbox; default-src 'none'`) and `nosniff`, as every attachment response does today (`/api/files`, `/dav`, the reader's files), so nothing runs and nothing loads there either. A test asserts that header on an SVG from each of those endpoints.
4. **Rendered by the sidecar.** `img` and thumbnails go through the sidecar's `@napi-rs/canvas` (Skia), which decodes SVG today. Checked on 2026-11-17: an `<image href="http://…">`, an `xlink:href="file:///…"` and a `@import` in `<style>` fetch nothing (a local server saw no request). A sidecar test keeps it that way: an SVG referring to a local server renders and the server sees no request. Why it matters: an external reference resolved on the server would be SSRF.
5. **Size from the file, render at our size.** Width and height come from the root's `width` and `height` (in px, or unitless), else from its `viewBox`; neither gives none, and the image is rendered as if square. The render is always at the requested size step, so a file claiming a huge canvas costs nothing for its size: the header guard that refuses raster images over a pixel count doesn't apply to SVG. *Changed while building:* what an SVG draws can still cost, so it is drawn in a process of its own, killed at the render's time limit (see "Decided while building").
6. **Agents write it with `write`, whole.** `write` takes an `.svg` path outside a skill's folder, as it takes a skill's text files today (`NoteWriter.cs:127`), with the same version rules: no version creates, a version replaces. The content goes through the check of decision 2; a refusal says what is wrong ("not an SVG: the root element is html"). `edit` and `replace` refuse with "replace it whole with write", as for a skill's text files. Why `write` and not an upload: the agent's loop (write, look with `img`, correct) is the point of the feature, decided by Chris on 2026-11-17.
7. **`cat` prints the source.** `cat diagram.svg` prints the SVG text after the attachment's one-line description, so an agent can read and change it. `rg` doesn't search it: SVG text is mostly coordinates.
8. **No shrinking on upload.** The web app shrinks large photos before upload; an SVG is never shrunk or converted.
9. **No sanitiser in 0.6.0.** Every path Kumbu² controls shows SVG as an image or under the sandbox policy. For the paths it doesn't control (export ZIP, Obsidian, WebDAV clients): Obsidian embeds SVG as an image too, and a file the user opens locally is their own file, like any HTML they downloaded. The sanitiser comes with inline SVG, where it is a must. Why: what we don't need now, we don't build now.

## Decided while building

Details the decisions above left open, each with its reason; one touch point moved.

- **The check and the size live in `src/Kumbu.Core/Attachments/SvgImage.cs`, not in `ImageHeader.cs`.** Why: `write` (in Core) stores an SVG, and the size is stored with it, so the attachment writer reads it itself for every way in (`write`, `/api/files`, `/dav`, a skill's copy); the server's `ImageHeader` stays the raster images' header guard, which an SVG skips.
- **One side and a viewBox:** `width="800"` with `viewBox="0 0 100 50"` is 800 × 400, as a browser shows it. Sizes are rounded to whole pixels, at least 1; a side beyond what an `int` holds counts as none.
- **A file whose DTD declares entities and whose document uses one is refused** as not well-formed (the entity is undeclared once the DTD is ignored). Older Illustrator exports do that; they are rare, and resolving entities is what decision 2 rules out.
- **The sidecar draws an SVG on a route of its own, `POST /render/svg`,** with the stored size as `width` and `height`, so that a crop counts in the size `cat` reports and the server's and the sidecar's sizes can't drift apart. Without a stored size it draws a square of 300 × 300 (300 the width a browser gives an SVG that names none). It draws at the size step, enlarged too, never limited by the canvas the file claims.
- **Publishing strips an SVG** as it strips a photo's EXIF (`ImageMetadata.Strip`): it keeps the elements and attributes of the SVG, XLink and XML namespaces (and none), and drops comments, processing instructions, the DTD, `metadata` and an editor's own namespaces. Why: an Inkscape file names its author and paths on their disk (`sodipodi:docname`, `inkscape:export-filename`), and without a strip a published SVG would have become plain text, against decision 3. XHTML inside a `foreignObject` goes too. An `href` keeps a fragment (`#id`) and an image embedded as a base64 `data:` URI, itself stripped in place (`Strip` of its media type: a JPEG's EXIF and GPS go, an embedded SVG is stripped by the same rules); every other reference goes, a linked image's absolute path on the author's disk among them (security review, 2026-11-17). Stripping in place costs a few lines, as the strip of each format exists already, so embedded pictures stay.
- **Changed while building: the sidecar draws an SVG in a child process, killed (`SIGKILL`) at the render's time limit.** Why (security review, 2026-11-17): Skia draws an SVG in one native call that a worker thread's `terminate()` can't interrupt, so the thread, and its place in the pool of two shared with PDF rendering, stays taken until the call returns. A 2.6 KB SVG of 50 filtered rects (`feGaussianBlur` and `feMorphology` over a large filter region) drew for 44 s, larger values for over 90 s, a 1.3 KB fan-out of `<use>` for 16 s: two such files would block every `img` and PDF page for everyone. A process is killed at its deadline whatever is expensive in it; a denylist of SVG features would always lag behind Skia. Its heap has the threads' limit (384 MB); every other job stays in a thread. Pinned in `pdf/test/pool.test.ts`.
- **An SVG image isn't moved or renamed into a skill's folder,** where `.svg` is a text file: it is refused with a sentence that says so, as other format changes are.
- **The Obsidian plugin** lives in its own repository and wasn't checked from here: the sync's version list now names SVGs, with kind `image`, to a client that asks with `attachments=1`. Whether the plugin 0.2 keeps, ignores or mistakes an `.svg` entry is to be checked there before the release.
