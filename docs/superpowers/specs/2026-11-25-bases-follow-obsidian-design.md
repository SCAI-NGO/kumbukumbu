# Bases follow Obsidian

Date: 2026-11-25. Status: decided for 0.8.0 on `release/0.8.0`, under the maintainer's go-ahead to work 0.8.0 ahead on its own, and built in both engines (2026-11-26); where the build settled or refined a decision, it says so here. It builds on [ADR 0039](../../adr/0039-bases-follow-obsidian.md): where a base's result differs, Kumbu² follows Obsidian and only adds diagnostics. The limits of §7 are [ADR 0040](../../adr/0040-query-work-is-bounded-and-regexes-are-a-common-subset.md).

The source is an automated run of the conformance cases against Obsidian 1.15.1, which read Obsidian's own Bases API over CDP (Kumbu² note `/SWE/Kumbu/0.8.0/Obsidian cross-checks.md`). It is completed by Obsidian's reference: obsidian.md/help/bases/functions and /syntax. Points the run hasn't settled yet are marked **probe** and listed in `/SWE/Kumbu/0.8.0/Obsidian probes 2026-11-25.md`. Until a probe answers one, the reading given here holds and its case stays `source: spec`.

This changes the queries spec of 2026-11-24 in §2 decision 6 (one rule for failures), §3 (values and types), §4 (the language and its limits) and §7 (which files a query runs over). Those sections now point here.

## 1. Rows

1. **A base runs over every file of its vault.** That means notes, `.base` files and attachments, the query note and the base file themselves included (findings 1, 15, 21). A path with a segment that starts with a dot (`.obsidian/`, the folder markers `.vaultkeep`) is not a file of the vault, and the parking area is none either; both stay out. *Why:* Obsidian lists every file, and indexes no dot folder: without the rule, `.obsidian/types.json` would be a row of every base. A query that should list notes says so, as Obsidian's own examples do (`file.ext == "md"`). A dot file Obsidian does list would be a probe-5 case.
2. **Archived notes are rows too.** `_archive/` is an ordinary folder to Obsidian. *Changed from* the queries spec §7, which left them out. *Why:* the same base must give the same rows on both sides; a query that should skip the archive filters `!file.inFolder("_archive")`. *Cost:* the existing named queries of a vault see archived notes until they filter. The `create-query` skill teaches the filter. `query ls` and finding a query by its name still leave the archive out; an archived query runs by its path.
3. **Attachments' fields** are those of their file: `name` with its extension, `basename` without it, `ext`, `size` (its bytes), `ctime` (its oldest kept state) and `mtime` (its last write), empty `properties`, no `tags`, links or embeds. A note's `size` is its text's UTF-8 length, its `ctime` the creation it recorded (for an old note that never recorded one, its oldest kept state, which may be later), its `mtime` its last write; times are in the caller's zone, as `now()` is. **Probe 5** confirms which fields Obsidian gives attachments.
   - **A note's times are read only when a query uses them.** The server reads a note's `ctime` and `mtime` only for a query whose YAML (filters, formulas, views) mentions `ctime` or `mtime`; otherwise they are null. *Why:* a note's times take one lookup per note, which a query over thousands of notes shouldn't pay for nothing. No expression reaches a field by a computed name (`file["c" + "time"]` gives null), so the textual check can't be fooled. An attachment's times come with its listing and are always there.

## 2. Values

4. **One date type.** A date carries a time or not, as it was written or made (`today()` is midnight, `now()` has the time, `.date()` drops the time). There is no separate datetime type in values (finding 8). The conformance notation keeps `date 1980-11-03` and `date 2026-11-23T14:30:00`. Equality and order compare the moment, so `date("2026-11-25") == today()` holds at any time of that day only if **probe 4** says so. Until then, a date without a time equals only midnight.
5. **Declared types don't change a base's values** (finding 10). A base reads the YAML as YAML 1.2's core schema reads it: hex `0x1F`, octal `0o17` and `.inf` are numbers (finding 11), and a quoted value is text whatever `types.json` declares. `types.json` stays what `query properties` reports as the declared type, beside the type of the values (`birthday: date (declared), date, 3 notes`). *Changed from* the queries spec §3. The `properties/` cases follow.
   - **A number parameter accepts plain decimals only** (`11`, `-1.5`), its default too; `.nan`, `.inf`, `0x0B` and `0o13` are `param-value`. *Why:* a call's arguments are untrusted input (an agent may have read them on a web page), and the core schema's other forms would let one slip NaN or infinity into a comparison. The YAML of a note keeps the core schema's numbers.
6. **A single value is not made a list** (finding 13): `aliases: Annie` stays text, and list items keep their own types. That holds for `tags` too: `tags: person` is the text `#person`, not a list. Whether Obsidian makes its own `tags` property a list is a **probe**.
7. **Tags keep their `#`** in `file.tags` and in a `tags` property read through a base (finding 6). `file.hasTag("project")` still finds `#project/kumbu`. `file.tags` lists the text's tags before the frontmatter's, each once ignoring case, as first written; that is the one reading of finding 6's single result besides an ordinal sort, and a **probe** (a note with frontmatter `[a]` and body `#b`) settles it. With the `#` kept, `tags.contains("friend")` is false and `tags.contains("#friend")` true (`source: spec`).
8. **`file.name` of a note drops `.md`**, and only `.md`; other files keep their extension. `file.folder` at the root is `/` (finding 2).
9. **An error is a value.** An unknown function or method, a formula that doesn't exist, a cycle, a calculation between types that don't fit (`name * 2`), `number("soon")`, or a field of a type that hasn't one (`birthday.month` on a text) gives an error value in that cell, with Obsidian's message where the findings quote it (findings 4, 14). It is not an error of the query. A method or field of null is null. The conformance notation is `error`, optionally with the message's start. How an error travels through `+`, `==`, `&&`, `if`, `isEmpty`, sorting and filters is **probe 1**. Until it answers:
   - an error taints whatever uses it: an operator (its left side first), `!` and unary `-`, a method's target and arguments, a function's arguments, `if`'s condition, an index, list and object literals holding one, `isEmpty()` and `toString()` of it;
   - `&&` and `||` short-circuit before they taint: `false && error` is false, `true && error` and `false || error` are the error, as JavaScript evaluates them; `if` evaluates only the branch it takes;
   - a filter that gives an error drops the row (finding 19), and in an `and`, `or` or `not` group the items are read in order as `&&` and `||` read theirs, an error dropping the row whatever the group;
   - a sort puts error rows after the empty ones, in both directions;
   - unary `-` on what isn't a number (a text, a duration) is null, not an error.
   - `a = 1` stays a `syntax` error of the query (with the hint to write `==`), where Obsidian gives null (finding 18). *Why:* an assignment in a filter is a typo that silently matches nothing; the author learns of it from `query check`. Whether to give null instead is a **probe**.
10. **Numbers are JavaScript's.** `n / 0` is `Infinity`; `NaN` and the infinities display as JavaScript writes them. `number(text)` reads as JavaScript's `Number()` (exponents, `Infinity`, `0x`, `0o`, `0b`, the empty text 0); `.inf` is an error there.

## 3. Operators

11. **`&&`, `||` and `!` give booleans** (finding 12), on truthiness as JavaScript counts it: null, false, 0, NaN and the empty text are false; every other text (`"0"` too), an empty list, an object and a duration are true.
12. **Comparisons coerce** as Obsidian does. Text that reads as a number equals and orders with that number (`"11" == 11`, `"11" > 10`), and an order against null is null, so a filter on it drops the row (finding 3). The rest of the matrix (booleans, dates against text, lists, null in arithmetic) is **probe 2**. Until then, `==` between other types is false and an order between them is null; `list.contains` and deep list equality use the same `==`, so `[1].contains("1")` is true. A sort stays strict within a type, since a coercing order isn't transitive (`"9" < "11"` as numbers, `"11" < "9"` as texts).
   - **`-`, `*`, `/` and `%` read a text that reads as a number as that number** (`t - 1` is 10 for `t: "11"`); `+` with a text still joins (`t + 1` is `111`). A text that isn't a number is `Invalid operator between String and Number`, and so is the empty text (JavaScript gives 0: a **probe**). *Why:* the same coercion as the comparisons, and Obsidian's operators are JavaScript's.
13. **Date arithmetic** follows the reference. `date ± "1d"` takes the units `y M w d h m s` (case counts), with their long names (case ignored), a sign and decimals (`-1d`, `1.5h`); the parts of one text are added as Moment adds a duration, milliseconds, then days, then months (`date("2024-01-30") + "1M 1d"` is 29 February), while the operators chain left to right (`+ "1M" + "1d"` is 1 March). *Why:* Obsidian computes date arithmetic with Moment. A date without a time gets one only when the duration has hours, minutes or seconds. `duration(text)` makes a duration, and `date - date` is a duration; `duration ± duration` is one. A duration times or divided by a number keeps the duration on the left and scales each part; `n * duration`, `duration + n` and `date + "soon"` are errors (`Invalid duration "soon"` for the last). A date outside the years 1 to 9999 is `Invalid date`. How a duration displays and compares is **probe 3**. Until then it displays in milliseconds and compares as a number of milliseconds (a month 2,629,746,000 ms, as Moment counts it). Readings for probe 3 besides: scaling the parts rather than the milliseconds, and `date + "x"` as an error rather than a join.

## 4. The language

14. **The functions and methods are Obsidian's**, every one that gives data. That is the reference's list: globals `date`, `duration`, `file`, `if`, `link`, `list`, `max`, `min`, `now`, `number`, `random`, `today`, `escapeHTML`. Methods per type: any (`isTruthy`, `isType`, `toString`), text, number, date (`format` in Moment's tokens, `relative`, `time`), list (`filter`, `map`, `reduce` with `value`, `index` and `acc`, `flat`, `sort`, `unique` and the rest), object, link, file and regex. Not taken: `upper` and the text `matches` (Obsidian hasn't them, finding 18): they are unknown, so an error value and a `query check` warning. `html`, `image` and `icon` come with the UI, since they only render. *Changed from* the queries spec §4's own list. *Why:* a base written in Obsidian must run here. As built:
   - **Links are values.** `link(path, display)`, `file.asLink()`, `file.links` and `file.embeds` give a link: the path of the file it leads to, resolved as `[[…]]` is, or its target as written when it leads to none, and the text it shows if given. It equals another link, a file or `this` by that path. The conformance notation is `link People/Ann.md`, or `link People/Ann.md|Ann` with its display. A property `author: "[[Ann]]"` stays text, not a link (reading links from frontmatter would change every `properties/` case; a later step).
   - **`number(date)` is milliseconds since 1970, the date read as UTC.** *Why:* the moment has no zone in a base, and reading it as UTC gives the same number on the server and in any tab.
   - **`format` takes Moment's tokens in English, without a zone.** Left out, so their letters stand as written: `Mo`, `DDD`/`DDDD`, `Q`, `W`/`w`, `E`/`e`, `X`/`x`, `Z`/`ZZ`, `k`/`kk`, `N`, `gg`/`GG`, `Y`; `format()` without a pattern is null, since Moment's default writes a zone. `relative` is Moment's `fromNow` against the run's `now`.
   - Readings that are **probes**: the names `isType` takes (`string number boolean date duration list object file link null`), `max` and `min` on what isn't a number (an error value), `file.links` keeping a wikilink's alias as its display, `file.backlinks` as files and embeds counting as backlinks, a link equal to a file, `sort` across types (by type rank, null and then errors last), `unique` without `==`'s coercion (`1` and `"1"` stay two, as a JavaScript `Set` keeps them), `toString()` of null staying null, `title()` leaving the rest of each word alone, `reverse()` by code points.
15. **Regular expressions match through the regex:** `/^ann/i.matches(name)` (finding 17), with the flags `g i m s u`. An unknown or repeated flag, a pattern that doesn't compile, or one outside the common subset of §7 gives null, not an error, as Obsidian gives for its own failures, and `query check` warns (`regex`). *Why null for our refusals too:* the engine stays linear in time (ADR 0034), and both engines must refuse the same patterns (ADR 0040). A pattern Obsidian runs and Kumbu² doesn't is the one place the two differ; `query check` names it. A regex displays, and `toString()` gives it, as JavaScript writes it: `/a+b/gi`, the flags in `gimsu` order.
    - **`[\s\S]` isn't accepted:** a class takes `\d`, `\w` and `\s` but not their negations. Write `.` with the `s` flag for "any character". *Why:* the subset is kept as small as both engines read alike; widening the class grammar is possible later.
16. **`random()`** is drawn once per run and row, so a sort by it stays stable within the run.
17. **Lambdas** (`value`, `index`, `acc`) are names only inside `filter`, `map` and `reduce`, the innermost lambda first, `acc` from the nearest `reduce`; elsewhere `value` is the property of that name, and a formula doesn't see them. A lambda's body counts one level more, against the nesting limit and the evaluation budget of §7.

## 5. Bases and views

18. **A view needs a name.** One without a name, or whose `name` isn't a text (null `~`, a number, a boolean, a list), makes the whole base an error (`base`: `Missing or invalid "name" in view N`), as does an invalid filter group (finding 7: a group is one of `and`, `or`, `not` with a list). An embedded block with such a view shows nothing (finding 16). A quoted `"5"` is a text and a name; so are `yes` and `on`, which YAML 1.2's core schema reads as text. *Why non-text names fail:* Obsidian calls a view's name invalid when it isn't one, and a name must be something `--view` can give. A query note with several base blocks is read as a whole: one failing block fails the note, every view of every block, in `query ls`, `inspect`, `check` and `execute` alike, with the failing block's message. *Why:* a note's views are one list; serving some of them would hide the error from an agent that calls another.
19. **Only `ASC` and `DESC` sort.** A sort key without a direction, or with another one (`asc`), sorts nothing, and the rows keep path order (finding 20). A direction given but not one of the two is a `query check` warning (`sort-direction`); a key without one is skipped silently, as it may be deliberate.
20. **Column ids are kept as written** in `order`. Obsidian normalises `status` to `note.status` (finding 9), which is notation and not meaning.

## 6. What Kumbu² adds

21. **Diagnostics on top, never instead.** `query execute` prints the view and how many rows (`By day: 3 rows`, `By day: no rows`), then, before the table, one line for each column with an error in its cells: `2 errors in formula.age: Invalid operator between String and Number`, the count and the first message; the cells show `error: <message>`. `query check` warns about every unknown function, method or formula, every formula cycle, every regex that is null and every sort direction that sorts nothing, each as `warning: view <view>: <code> in '<expression>' at <position>: <message>`, after the line `<path>: ok, <views>, <parameters>; N warnings`. These are warnings: the query still runs, as in Obsidian, and `check` succeeds. *Why:* an agent reading a table must not overlook an error hidden in a column. That is the strictness the old rule (one error for the whole query) was for.
22. **Kumbu²'s own errors stay errors of the call:** `no-base`, `params`, `unknown-param`, `missing-param`, `param-value`, `unknown-view`, `base`, `syntax`, and the limits (`too-deep`, `too-large`). *Why:* they are about the call or about a base that can't be read, not about a cell. The old `regex` error is gone (decision 15).

## 7. Limits

A query is anyone's input: a query note in a shared vault is written by one member and run by another, on the server or in a reader's tab. So its work is bounded, deterministically and the same in both engines, and past a bound the call fails with `too-deep` or `too-large` (decision 22), never with a half result. *Why deterministic:* a time budget would give one query a result on a fast machine and an error on a slow one, and differ between the engines. *Why the same in both:* the conformance cases hold them to one result, the limits included (`expressions/limits-of-values-and-work.yaml`). This is [ADR 0040](../../adr/0040-query-work-is-bounded-and-regexes-are-a-common-subset.md); it refines ADR 0034.

23. **What an expression may be:** at most 10,000 characters and 64 levels of nesting (a chain's steps, `.name`, `[index]`, a call and a lambda's body each count a level; operator chains are walked in a loop, so they don't nest), `syntax` past either; a base or frontmatter of at most 10,000 YAML values and 64 levels. *Why:* the parser and every walk of a tree recurse, and anchors could otherwise expand into millions.
24. **One evaluation budget of 512 levels across formulas.** Compiling and evaluating count an expression's own levels and those of the formulas it uses, added up along the way, against one budget of 512 (eight for each of 64 formulas); past it is `too-deep`. Each formula is still checked once and worked out once per row. *Why:* each formula alone kept to 64 levels, but chained through each other (and through cycles the check walked once) they could go 64 × 64 deep and overflow the stack in both engines. Measured on a thread pool's stack of 1.5 MB, the costliest levels (`if`, `number()`, objects) run out at about 1,420 in a Debug build and 1,723 in a Release one; 512 leaves most of the stack to the caller and the parser. In C# a stack check stays as a net behind the budget, in TS a `RangeError` becomes `too-deep`. *Cost:* formulas that nest each other past 512 levels in total, valid before, are now `too-deep` (64 formulas each nested more than about six levels).
25. **What a value may be:** for one note and expression, a value's characters, items and keys added up at most 1,000,000, and its nesting (lists in lists) at most 128; past these `too-large` and `too-deep`. A builder (a list literal, `map`, `flat`, `join`, `replace`, `repeat`, `split`) checks as it goes, so nothing huge is allocated first. *Why:* a lambda or two formulas that use each other double a value at each step (`reduce(acc + acc, "x")`), so a short expression could fill the server's memory; a property's value is far smaller. *Cost:* a frontmatter value over 1,000,000 characters fails a query that reads it.
26. **What the work may be:** 1,000,000 steps for one note and expression, 5,000,000 for the whole run, and 10,000,000 for the size of all the values a run keeps (cells, sort keys, filter results); past any `too-large`. A step is each part evaluated, each item a method goes through, and each 64 characters and items an operation reads or builds; `contains`, `containsAll` and `containsAny` count their target once per argument, `sort` its target times 1 + log₂(n + 1) / 4, and `format`, `relative`, `toFixed`, `date()` and `duration()` 8 each, as measured. A list or object field of a file (`tags`, `links`, `embeds`, `backlinks`, `properties`, `note`) is built once per run and charged then. *Why:* the bound on a note alone would let a large vault keep the server busy for hours. Measured over 35 kinds of expression, a run at its bound takes at most about 3 s on the server and 4 to 5 s in a tab; by the steps of an ordinary query (about 20 a note), that fits vaults of about 250,000 notes, and about 100,000 by size. Not counted, since linear in the vault and done once a run: reading the notes, working out links and backlinks, and the view's sort.
27. **The server stops a cancelled run between rows.** `query execute` passes its cancellation to the run, which checks it at each row while filtering and while building the cells. The offline engine has no token and is bounded by its steps.
28. **Regular expressions are the common subset both engines read alike, gated by their size written out.** A pattern runs only when all of these hold; otherwise it is null with a `query check` warning that says which (decision 15):
    - **Only the common syntax:** literals, the escapes `\d \D \w \W \s \S \b \B \t \n \r \f \v \xHH` and an escaped punctuation mark, classes of characters, ranges and `\d \w \s`, the dot, `^` and `$`, groups `(…)` and `(?:…)`, alternation, the counts `? * + {n} {n,} {n,m}` and their lazy forms, and the flags `i`, `m` and `s`, alone (`(?i)`) or for a group (`(?i:…)`). Not: lookaround, backreferences, named groups, comments, `\p{…}`, `\A \z \Z \G`, `\Q…\E`, other flags, a count of a count, a lone `{`, `}` or `]`, a class starting with `]`, a character outside the BMP, groups nested deeper than 100. *Why:* RE2 and .NET read the edges differently (`\Z`, `[a-z-[aeiou]]`, named groups numbered after the unnamed ones, so `$1` differs); a strict reader of the common part is the only way the two engines can't read one pattern two ways. The server rewrites what it accepts to mean what RE2 means: `\d`, `\w` and `\s` as ASCII, `$` without `m` as the end of the text, and under `i` each letter with every case form RE2 folds it with (23 orbits where .NET folds fewer, such as `s`/`ſ` and the Greek sigmas).
    - **Counts within RE2's bound:** no count over 1,000, alone or multiplied through nesting. *Why:* RE2 refuses them, so the server must too.
    - **At most 64 positions written out:** an atom, a class or an anchor is one, an alternation adds its branches, `{n,m}` multiplies its body by m, `?` counts it once, `*` and `+` twice, and `{n,}` n + 1 times and at least twice. *Why:* .NET's linear engine builds its states lazily as it matches, and doesn't look at its match timeout while it does; for written-out optional groups of overlapping branches they grow steeply with the size. The first search of 1,000,000 characters by `(?i)` and `(?:a|aa)?` × 21 (63 positions) takes 380 ms, × 25 (75) 660 ms, × 33 (99) 5.5 s; 20 groups `(?:a|aa|aaa|aaaa)?` under `{0,}` took over a minute, and the review's 40 of them (720 characters) minutes. A loop counted once let `(?:(?:a|aa)?×20)*c` take 27 s under `i`; counted twice, the worst accepted pattern found, over 3,000 random and many hand-made shapes, takes 388 ms. re2js has no such states but scans at a cost per character that grows with the size.
    - **The charge:** the first search of a pattern in a run costs 128 × size² steps (524,288 at 64, about 0.4 s of state building on the server), so a run holds no more than nine of the largest; each search costs 1 + read × (4 + size) / 20 steps, where read is up to the match's end and on by the longest match the pattern can make, or, when it fails or has no longest, the rest of the text. *Why:* a global `replace` or `split` searches again from each match, and `/(?:a*c)?/` reads the rest of the text each time, which would be quadratic; weighting by size keeps a step at about 1 µs in re2js too (case-insensitive on non-ASCII text, it took 1.6 µs a step at a rate of /32). The worst full run measured takes 4.9 s in a tab. TS pays the first-use charge too, though re2js needs it less: the price of identical results.
    - The server keeps compiled patterns across runs (so a row, or the query run again, finds the states built), at most 256 patterns and 1,024 positions in all, about 70 MB at worst.
    - *Cost:* patterns RE2 runs are null here: `.{0,500}`, `^[a-z]{1,64}$` (66), the twelve month names written out (74), named groups, `\p{L}`, an escaped `_`. A long text split into many parts can be `too-large` where Obsidian gives a value (100,000 characters into more than a few hundred parts). A query can end in `too-large` where Obsidian would answer. Realistic patterns fit: `\d{4}-\d{2}-\d{2}`, an ISO date-time, `^[\w.+-]+@[\w-]+(?:\.[\w-]+)+$`, `\r?\n`, `[a-z]{1,64}` with `i`, `\bword\b`. A later refinement could size single-atom bodies apart (cheap in .NET, not in re2js), at the price of two sizes to keep equal.
29. **Known engine differences**, documented in the conformance README rather than pinned by a case:
    - `\b` and `\B` see a word character as Unicode on the server and as ASCII offline: `/caf\b/` matches "café" offline only. .NET's linear engine has no lookaround and no ECMAScript option to write RE2's boundary; the alternative was to refuse `\b`, which realistic patterns use.
    - Text outside the BMP (an emoji) is two UTF-16 units to `.` and a negated class on the server and one code point offline, so a match's place and length can differ on such text.
    - **.NET 10.0.15's NonBacktracking engine gives a wrong leftmost match** for some small patterns with an optional first part: `/a?b/` on "acbb" matches at 3 instead of 2, so `"acbb".replace(/a?b/, "X")` gives `acbX`; about 4 in 12,500 small accepted patterns, and no rewrite avoids it. `expressions/regex-leftmost-match.yaml` pins the right result as `pending: [cs]` until .NET fixes it; reporting it upstream waits for the maintainer's yes.
    - Obsidian's JavaScript differs from RE2 where neither engine can follow it (Unicode `\s`, `.` and `\r`, `ſ` under `i`, inline flags JavaScript hasn't); the cases pin RE2's reading.

## 8. Steps

1. Take over PR #338's cases and ADR (renumbered 0039), and mark the changed cases `pending: [cs, ts]` until each engine follows.
2. Both engines, C# first, then TypeScript, held to the cases. In order: rows (1–3) and file fields (8); values and YAML (4–7, 10); errors as values (9, 21, 22); operators (11–13); the function and method set (14–17); views (18–20). Done, with the limits of §7 (2026-11-26).
3. New cases for every reference function, `source: spec` until a run confirms them.
4. The probes. Their answers move cases to `source: obsidian 1.15.1`, or correct them.
