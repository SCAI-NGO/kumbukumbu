# The polish for 0.3.1

Date: 2026-11-03. Status: approved by the maintainer.

Six small things left by the hand tests of 2026-11-02 and the fixes for 0.3.0. Together with the console and the attachment wishes they make 0.3.1. This work becomes `v0.3.1-pre.2`.

## 1. Goals, non-goals, anti-goals

Goals: the six items of §2 to §7, each testable on its own, each its own commit. §7 can be left out without touching the others.

Non-goals:

- Pins, Options A and B, the owner lock-out they include, and L1 of the rename's security review (a rolled-back meta). They wait for an independent review, with no date.
- The console's open decisions (a rate limit for whole-vault reads, `cd` on a vault being re-encrypted, scrollback memory, the trash-restore gap).
- Plugin code. The plugin keeps its version; its 0.3.0 is separate work.
- A tab that was closed or offline when the rename happened (§2).

Anti-goals, which make this a failure even if it works:

- **A key used under the wrong era.** During a two-key period, no object made with the old vault key is served or writes (§7).
- **Text lost on a rename.** A second tab's unsaved text survives its move (§2).
- **Restored text lost.** The stored push of a restore stays: a later write in the same changeset coalesces, and without it the restored text would be gone (§5).
- **A device key revoked without the person asking.** Nothing is revoked automatically (§4).
- **Anything an agent sees changing,** except what §5 says about `history` and `activity`.

## 2. A second tab follows a rename

Today a second tab of the owner stays on `/notes/<old name>/…` and says "This note was moved or removed elsewhere" (`web/src/note/ChangedElsewhere.tsx:45`), because the socket's `changed` frame names only the new name (`src/Kumbu.Server/Sync/SyncHub.cs:677`) and nothing tells old from new.

Change:

- `SyncHub.VaultRenamed` gets the old and the new name when the rename's outcome is known, and sends each of the owner's connections to that vault a new frame: `{"type":"renamed","vault":"<new>","from":"<old>"}`, beside the existing hint. An outcome that isn't known (`NoteApi.cs:300,306`) sends the hint only, as today.
- `web/src/hooks/useSyncSocket.ts` handles the frame as `useRenameVault` does its own success (`web/src/api/sharing.ts:175-183`), through one shared function: `editor.moved(from, to)`, the active vault, `navigate(…, { replace: true })` if the open note is below `from`, and the same query invalidations.
- The renaming tab gets the frame too. It has already moved, so `from` matches nothing and it does nothing.
- API-key and device sockets get the frame too. The plugin, in its own repository, acts only on `changed` (`src/live_hints.ts:115`) and ignores it.

## 3. A copy button for the pairing code

In `web/src/shell/ConnectObsidianDialog.tsx:129` the code is a plain `<p>`, while the plugin's name and the server address have a `CopyButton` (`:104`, `:113`). The code gets one too, with `name="Copy the pairing code"`, shown only while the code is valid. A failed copy says nothing today for all three (`onResult={() => {}}`); that stays.

## 4. Offer to revoke an old device key

Pairing again leaves the old device key holding `maintain` until someone revokes it. Whether a device was replaced can't be known: devices have no identity, and two devices on one vault are normal (`ConnectObsidianDialog.tsx:157`). So the dialog shows and offers, and never decides.

Change, in the web app only: the dialog reads `GET /api/keys`, and for this vault's non-revoked keys of kind `device` shows a short list:

> Already connected: **Gartenarbeit – Laptop**, last used 2 days ago. [Revoke]
>
> Revoke one only if that device is gone or is being replaced.

- Listed: keys of kind `device` on this vault that aren't revoked or expired, as the Keys page offers Revoke only for those.
- Revoking uses `DELETE /api/keys/{id}` as Settings does, with the same confirmation as there.
- The list works for an owner and for a member: `/api/keys` holds the caller's own keys, unlike `GET /api/vaults/{vault}/access`.
- No keys: no list, and the dialog looks as it does today.

Decided by the maintainer: a list with a button per key, rather than one question after pairing, which would need a new status route and still couldn't tell a replacement from a second device.

## 5. A restored note's version says what happened

A restore from the trash writes the old state to history and makes it current as well (`src/Kumbu.Core/Notes/NoteWriter.cs:56-57`, `:321`; attachments `AttachmentWriter.cs:242-245`). So `history` shows the version twice with nothing to explain it, and `activity` shows `changed X->X` (`Activity.cs:105-106,131`).

**Nothing is hidden, by the maintainer's decision.** `history` has something of an audit log about it, and leaving a line out could read as hiding what happened. Both lines stay, and the push stays, since it protects restored text (§1).

**A stored flag, since the store can't tell otherwise.** A, B, A in one changeset also leaves A directly above A (`NoteWriter.cs:69-72`), and a false `(restored)` would be worse than none. So a restore from the trash sets a small additive flag, `Restored`, on the note or attachment, and any later write clears it. It is sealed with the rest of the record. A document without it reads as not restored, so earlier restores stay unmarked.

- `history` (`src/Kumbu.Core/Sh/Commands/History.cs`), single-note and folder form: the current state's line ends in `(restored)` while the flag is set. Its help says so.
- `activity`: the row of the current state reads as a restore of X, not `changed X->X`, while the flag is set. A rename in the same row takes precedence (`ActivityTests.cs:145,221`). `README.md:105` follows.
- After the next write the restore's line goes, as it does today (`NoteWriter.cs:71-72`), and one unmarked X remains. The maintainer accepted this: changing that rule would touch what protects text from loss, and use up a history slot.
- A version restore (`NoteWriter.cs:354`) doesn't set the flag and stays as it is (`ActivityTests.A_restore_is_a_row_of_its_own`).

This is the one change an agent can see. The rule "Anything an agent sees changing" allows it here on purpose.

## 6. The Settings entry after a re-encryption

The dismissible notice is already targeted (`MemberNotices.LeaveForRekeyAsync`). The Settings entry isn't: one event per vault with the sentence "…re-encrypted {vault}; your keys and apps for it were revoked. Give your agents {vault} again." (`src/Kumbu.Server/Sharing/VaultEvents.cs:203`), read by every member.

The server knows the answer only at the finish: `doc.RekeyEndedMembers` (`VaultCatalog.Rekey.cs:514-542`) is unset at `:584`, and the event (`:594`) keeps only the credential ids.

Change:

- The event also stores the ids of the memberships in `RekeyEndedMembers` (the field is the same data under the same protection as the vault document's).
- A member in that list reads today's sentence, unchanged. A member not in it reads: "{person} re-encrypted {vault}. Nothing of yours stopped working."
- An event from before this change has no list: it keeps today's sentence for everyone.
- The notice reuses this sentence (`MemberNotices.cs:106`), so it gets its own constant first, with the same text. `SharedRekeyTests.BobsRekeyNotice` stays as it is.
- The agent's sentence (`VaultEvents.cs:217`) stays: it reaches only a credential that no longer reaches the vault.

Left as they are: `:519` counts expired or revoked keys too, so someone may read the longer sentence although nothing of theirs was still working.
## 7. `_loading` isn't held across retrying transactions

`_loading` is process-wide, and every vault opening needs it. A re-keying's start and finish hold it across `WithTransactionAsync` (`VaultCatalog.Rekey.cs:318-343`, `:365-394`), which the driver retries for up to 120 s on a conflict. So a slow or conflicting finish of one vault stops every vault's opening. The fixes for 0.3.0 removed the conflicts a member could cause in a loop, and deferred this (`docs/superpowers/specs/2026-11-01-0.3.0-fixes-design.md` §1.3) because an old key could otherwise return to memory during the two-key period.

**What must stay true:**

1. From a start's first step on, no working set made with the old key is served, and no object made with it writes (`Rekey.cs:321-323`).
2. A load after a finish sees K′ as current (`:373`).
3. A load outside the period may clear `_pending` (`VaultCatalog.cs:1324-1326`) only if no start is under way.
4. Holders of `_loading` never wait for anything a gate holds (`VaultCatalog.cs:741`).

**Change: a per-vault transition.** A set `_inTransition`, of vault id and a completion, changed only under `_loading`.

- **Start:** under `_loading`, do today's `_open.TryRemove` and `_pending` mark, and add the transition. Release. Run the transaction. Under `_loading`, on failure undo the mark as today, and remove the transition. Complete it in every case, also when the run throws.
- **Finish:** under `_loading`, add the transition. Release. Run the transaction. Under `_loading`, update `_keyIds`, `_rekeyed`, `_open` and `_pending` on success, and remove the transition. A `MembershipsChangedException` removes it too, and the re-read at `:389` runs outside `_loading`.
- **`LoadAsync`** (`VaultCatalog.cs:1293`): after taking `_loading`, if that vault is in transition, release, await the completion with the caller's token, and take it again. Waiting happens with `_loading` free, so rule 4 holds.
- **Who waits:** whoever has a slot on that vault, for that request, as today: `OpenForUserAsync` loads all of a user's vaults in turn (`VaultCatalog.cs:215-225`), so a member or the owner waits on all their vaults while one is in transition. Everyone else no longer waits at all.
- **Deletion and rename keep plain `_loading`,** across their own transactions, and can't meet a transition: a rename is refused with 503 during a run (`VaultCatalog.cs:1094-1100`), and a deletion waits for the gates the run holds (`:724-727`, `Rekey.cs:290-295`). Their comments say so.

A load that read the vault document before the start committed can't publish its result afterwards: loads hold `_loading` throughout, so it finished before the transition began. This is the argument to test, not to trust.

**Tests, written first:**

- While a finish is stalled in its transaction (hook), another vault opens within a second. This fails today.
- While a finish or a start is stalled, a load of the same vault waits, then comes back under the right key, and no object with K is in the working set.
- A start that fails, a finish that fails, a cancelled run and a cancelled caller each complete the transition: nothing waits for ever.
- `After_a_run_stops_in_its_two_key_period_an_old_object_writes_nothing`, `A_key_or_code_prepared_before_the_finish_and_committed_after_fails`, `A_finish_that_matches_nothing_keeps_the_vault_pending`, `A_member_key_wrapped_with_the_old_key_during_a_finish_is_refused` and `A_rename_loop_during_a_run_is_refused_and_the_finish_commits` stay green unchanged.

**The way out:** this item goes last, in its own commit. If a review finds a hole, or the tests don't hold in the run's time, it comes out and the report says why. 0.3.1 ships without it: today's behaviour is safe, only slow.

`src/Kumbu.Server/Vaults/` is security-relevant, so this item gets a security review of its own. Items 2 to 6 get a normal one, and §6 is also checked for leaking who lost what to other members.

## 8. One example, end to end

Alice has `Gartenarbeit` open in two tabs, on `plan.md`, with unsaved text in tab 2, and Bob is a member.

1. In tab 1 she renames it to `Garten`. Tab 2 gets `{"type":"renamed","vault":"Garten","from":"Gartenarbeit"}`, moves to `/notes/Garten/plan.md`, and her unsaved text is still there. No "moved or removed" sentence appears.
2. "Connect Obsidian…" for `Garten`: the old device key is listed; she copies the new code with the new button, pairs the laptop, and revokes the old key by its button. Her other device stays.
3. She deletes `plan.md` and restores it from the trash. `history plan.md` shows the version twice, the upper line marked `(restored)`; the activity reads as a restore.
4. She re-encrypts `Garten`. During the finish, Dave, who has no slot on it, opens his own vault at once; Alice's second tab waits, as today, and then reads under the new key.
5. In Settings, Bob, who had no key on `Garten`, reads "Alice re-encrypted Garten. Nothing of yours stopped working." Carol, who had one, reads today's sentence.
