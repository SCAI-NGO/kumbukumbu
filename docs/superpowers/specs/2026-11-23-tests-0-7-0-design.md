# Tests of 0.7.0: the specific run, with search by meaning on

Status: approved by Chris, 2026-11-23.

## 1. Goal and decisions

0.7.0 is feature complete and on staging as `v0.7.0-pre.1` (`ad920a73`). Before it is released, one run in a cloud VM tests what 0.7.0 brought: in the browser with Playwright, and over MCP in the suite's browserless project `mcp`, as 0.6.0 did (`2026-11-19-tests-0-6-0-design.md`).

Decisions, each with its reason:

- **In the cloud VM, against a stack of its own**, not against staging or production. The reason of the 0.5.0 spec, unchanged: reproducible from a fresh install. Chris counts these runs as part of the dark factory.
- **The run reports; it doesn't fix the product.** A test that finds a real bug stays in the suite, marked `test.fail()` with the finding's id. The fixes follow in one fix run together with the audit's findings and the hand tests' points.
- **Search by meaning is on, with the real model** (Chris, 2026-11-23: "gern mit dem echten Modell"). Three of 0.7.0's features stand on the embeddings: the graph's measured edges, Similar notes, and `similar` with the `synthesize-knowledge` skill. With search off they could only be tested for their "off" lines, which says nothing about the feature. *How:* an overlay `web/e2e/stack/compose.search.yaml` turns search on with the internal model (arctic-m, downloaded by the server into its `models` volume on the first start), used only by the tags that need it (§3). The rest of the suite keeps running with search off, which also tests the "off" lines.
- **Deterministic despite a model.** The model and its revision are fixed, so its vectors are too. Tests assert order and membership between notes that are clearly related or clearly not (a note about decompression stops beside one about dive tables, a cake recipe far from both), never a score's value. The fixtures are written so that the clear cases are clear; if the model ranks a clear case wrongly, the fixture is unclear, not the product.
- **TensorX through the environment's secret.** Chris put a TensorX key into the cloud environment "Tidesson Communications" as a secret: the VM's egress proxy adds `Authorization: Bearer <key>` to requests to `api.tensorx.ai`, so the key never reaches the run's files, logs or the stack. This covers what 0.6.0 had to leave out: an external provider (`tensorx`) and BYOK with a real request. It is also the fallback if the model's download from huggingface.co is blocked (§3).

## 3. The stack with search on

- **The overlay** `web/e2e/stack/compose.search.yaml` sets `Kumbu__Search__Enabled: "true"`, configures the `tensorx` provider (below) and `Kumbu__Embeddings__Byok: "true"` with the default `internal`, and keeps the model in an external volume `kumbu-e2e-models` that `up.sh` creates, because `down.sh` runs `compose down -v`. *Why the model may be kept between runs:* it is a fixed download, not state; every stack is still fresh. `up.sh`/`run.sh` take it with `E2E_SEARCH=1`, placed after `compose.e2e.yaml`; without the switch nothing changes. `E2E_STACK=dotnet` doesn't take it. The tags marked "on" run in a phase of their own on it.
- **The scripts:** `e2e:0.7.0` runs the off phase, then the search phase without `@tensorx`, each on a fresh stack, and fails if either fails (not `&&`, so the second phase runs after a failing first). `e2e:0.7.0:tensorx` runs `@tensorx` on the search stack; it needs the proxy's TensorX secret and is therefore kept apart, so `e2e:0.7.0` stays reproducible anywhere.
- **Waiting for the index:** a test waits until its notes are embedded through the product's own signals (the `pending` counts of `semsearch`/`similar`, `state: "preparing"` of the endpoints), with a stated bound, never a fixed sleep.
- **The model's download** goes through the VM's proxy: the server's container needs the proxy's address (`HTTPS_PROXY`, `NO_PROXY` for the stack's own hosts) and its CA (`E2E_PROXY_CA`, as the build stages already get it in `compose.proxy-ca.yaml`), in the suite's compose files only.
- **huggingface.co is needed in any case:** the tokenizer comes from there for every provider (`ChunkTokenizer.cs`), falling back to a character bound after about 2.5 minutes. **If it can't be reached**, the run uses TensorX as the instance's default provider (`Kumbu__Embeddings__Default: tensorx`) for the "on" tags and says so in the report. The assertions don't change: they don't depend on the model.
- **TensorX in the stack:** the provider as in the README's example (`openai-compatible`, `https://api.tensorx.ai/v1`, `qwen/qwen3-embedding-8b`, 1024 dimensions, the `QueryPrompt`), `ApiKeyFile` a file holding a placeholder, as the proxy adds the real header. The run first checks from the VM with `curl` that a request with the placeholder reaches TensorX authorised (the proxy replaces the header) and from the stack's network through the proxy (the server image has no `curl`: a throwaway container on the stack's network does). If the proxy only adds a header beside the placeholder and TensorX refuses, a test-only forwarder in the server container's network namespace drops the server's header before the proxy adds the real one (the brief has the details); BYOK, whose address is built in, is then left out. *Decided with Chris on 2026-11-23, against a switch in the product that makes the server send no keys:* such a setting would be a misconfiguration waiting to happen in production, for a need only this VM has. If the forwarder fails too, `@tensorx` is left out with the evidence in the report.
- **The key stays out of everything:** never printed, never asserted, never in a screenshot, a log line or the report. The run never asks the proxy or the environment for it.

## 4. The tests

As the 0.5.0 spec §2 to §5 and the 0.6.0 spec §3 and §4 set out: the viewports, `@phone` at 375 px, `@serial` for global lists and discreet vaults, exact or structural assertions (never "contains no error" alone), a state read back through a second call, two people where sharing matters (Alice and Bob; a vault of its own shared at `write` or `read` in the spec file's `beforeAll`), `test.fail()` with `M-NN` or `F-NN` for a bug, one screenshot per tag and viewport.

- **Offline** uses `context.setOffline` as the existing tests do; a reload offline goes through the service worker.
- **Deactivation** (`@devices`): the admin deactivates a user made for the test (not Alice or Bob, whose sessions the other tests need), through the app's admin path; the test reactivates it at the end, and asserts that the copy did not come back.
- **The service worker** (`@sw`): the test changes a kept file in CacheStorage from the page (`caches.open(...).put(...)`) and asserts that the changed bytes are never served: online the file comes from the server, offline it isn't served.
- **BYOK** with a user made for it, not Alice (a saved key moves a person's new vaults onto it); the placeholder key is 8 to 512 printable characters without spaces (`Byok.cs`); saving it needs the password window.
- **The scripts** (§3) are written like `e2e:0.6.0` in `web/package.json` and can be run again unchanged.

## 5. What the run does with what it finds

Unchanged from the 0.5.0 spec §5: each failure is triaged as **bug**, **test** or **unclear**; each bug gets a severity on the audit's scale, a repro, the expected and the actual behaviour, and a screenshot where there is a page, written so the fix run's brief can link to it unchanged. MCP findings get ids `M-NN`, UI findings `F-NN`, counted from 01 in this run's report.

## 7. Out of scope

- Fixing anything the suite finds.
- CI integration; a full run of the features before 0.7.0 beyond the smoke set.
- Firefox beyond `@offline`, WebKit, real devices, outside clients (Obsidian, WebDAV).
- Testing against staging, production or any real host other than `api.tensorx.ai` through the proxy, and huggingface.co for the model.
- Changes to the server or the web app, apart from `data-testid` where no role or label finds an element (each one listed in the report).

## 8. Security boundary

The 0.5.0 spec §8, unchanged, plus the TensorX key:
- the stack listens on `127.0.0.1` only and runs without a dev token;
- secrets are random per run and never written down; the TensorX key is never seen by the run at all (§3);
- no product code is touched beyond `data-testid`;
- a test never loosens a security setting to pass: no `Development` environment, no trusted proxy for the app, no forged headers. If something works only with a weaker setting, that is a finding.
