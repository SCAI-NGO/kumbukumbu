# WebDAV access, storage quota, access tabs

Date: 2026-11-07. Status: approved by the maintainer on 2026-11-07.

## 1. Why

A new user took to Kumbu² from the first minute and asked straight away for one thing: to **mount it as a drive** and drag files in, from Dolphin, Windows Explorer or macOS Finder, the way one works with any other folder. The same path makes Kumbu² a folder inside Nextcloud (its "External storage" app mounts any WebDAV source), with Nextcloud's desktop and mobile clients for free.

Handing out a drive that invites dragging whole folders in needs a **storage quota** first; and a third kind of access needs the access page split into **tabs**. All three ship together.

## 2. Goals, non-goals, anti-goals

**Goals**

- A user creates **WebDAV shares**: each with a label, chosen vaults with a right per vault (`read`, `write`, `maintain`), an optional expiry; listed, last-used, revocable, like API keys. Several shares per user (a work PC gets one vault, the home PC many).
- A share is mounted with **one URL, a username and a password**, the same URL for everyone: `https://<host>/dav/`. Every client in §3.9 works with it.
- Files written over WebDAV are stored as the client sent them (with the single exception of line endings, §3.5); moving a note over WebDAV rewrites the links to it, as `sh mv` does.
- Editors' atomic saves (temp file, then `MOVE` over the original) are one content write of the original, keeping its history.
- A **storage quota** per user, with a server-wide default and a per-user override set by an admin; enforced on **every** write path, not only WebDAV.
- `df` and `du` in `sh`; the owner can **empty the trash** to free space.
- The access page gets three tabs: API keys, Apps (MCP via OAuth), WebDAV.

**Non-goals** (not in this work)

- A link index, pending link adjustments, a graph. Links are rewritten at once (§3.6), so nothing is pending.
- Rights on anything smaller than a vault (§3.1).
- Real locking. Locks are accepted and not enforced (§3.7).
- Opening a WebDAV mount as an Obsidian vault. The Obsidian plugin is the way for Obsidian.
- Storing file types Kumbu² doesn't keep today (Office files, archives …).
- Per-writer accounting in shared vaults.

**Anti-goals**: it fails, even if it works, if

- a share's secret appears in a URL, a path, an access log or a client's address bar;
- a share reaches a vault, or a right, its creator didn't give it;
- client junk (`.DS_Store`, `Thumbs.db`, temp files) reaches MongoDB, search, embeddings, history or another channel's view;
- a file dropped in silently disappears without the client being told (an unsupported type must fail visibly);
- a member learns anything about the owner's quota or usage beyond "this vault is out of space";
- an agent can delete anything permanently.

## 3. Decisions taken

These were decided with the maintainer on 2026-11-07 and are not open.

### 3.1 Design principle: rights are per vault, always

Every credential (API key, connection, device, WebDAV share) gets a right **per vault** and nothing finer: no folder scopes, now or later. Data that needs a different audience goes into its own vault. This is a fixed principle of Kumbu², to be written into `docs/concept.md` (§4 Data model, Vaults); it keeps the rights model, the cryptography (a vault key opens the whole vault) and link rewriting simple.

### 3.2 A WebDAV share

- Created in the web app only, by a signed-in user, with the same password confirmation an API key's creation has today. Not through `sh`/MCP.
- **Username**: generated by the server, the account's username, a dot and a 4-character Crockford Base32 share id: `chris.k7qm`. Not secret; it identifies the share, so two shares on one machine get two entries in the system keychain. Unique per server; on a collision the server draws another id.
- **Password**: a generated token of **256 bits**, shown as 52 Crockford Base32 characters in groups of four, shown once. Normalised as pairing codes are (`src/Kumbu.Server/Accounts/Pairings.cs` ~192–214: case, hyphens and spaces don't matter, `I`/`L` read as `1`, `O` as `0`).
- Both must match: a valid token with another share's username is refused like a wrong token.
- Rights: per vault, `read` / `write` / `maintain`, as `RightsPicker` offers for API keys (`web/src/routes/NewKeyDialog.tsx`). A share **never** has "May publish" (publish design §3.8, `docs/superpowers/specs/2026-11-05-publish-design.md`): the checkbox is not shown in the share dialog, and a share's slot payload has no such flag. A member may create a share for a vault shared with them, at most at their own role, derived through their membership as a member's API key is (`grantedVia`); ending the membership ends the share's access to that vault.
- Optional expiry, the choices an API key has.
- Revocation, expiry, deactivation of the user and a re-keying of a vault act on the next request, as for API keys.
- Writer label in history: the share's label marked with the tool, `Work PC (dav)` (`Writers.Marked`). The changeset timing is a person's (`Changeset.HumanIdle`, 2 minutes): an editor is behind it.
- Server switch: `KUMBU_DAV_ENABLED` (default `true`; `Kumbu__Dav__Enabled`). Off: `/dav/` answers 404, the WebDAV tab says WebDAV is switched off on this server, existing shares stay and work again when it is switched on.

### 3.3 Authentication

- HTTP Basic on `/dav/` and below, over HTTPS only. A request that didn't arrive over HTTPS (directly or, with `KUMBU_TRUSTED_PROXY`, as `X-Forwarded-Proto: https`) is refused with 403 and a plain-text reason, except in the Development environment.
- No or wrong credentials: 401 with `WWW-Authenticate: Basic realm="Kumbu²", charset="UTF-8"`. Wrong tokens count against `WrongKeyLimiter` (`src/Kumbu.Server/Auth/WrongKeyLimiter.cs`) as wrong API keys do; when it blocks, 429.
- `CallerMiddleware` (`src/Kumbu.Server/Auth/CallerMiddleware.cs`) resolves a share into a `RequestCaller` with its vaults and rights, as for an API key. Bearer tokens are not accepted on `/dav/`, Basic is not accepted anywhere else.
- `OPTIONS` needs no credentials (Windows probes before it authenticates).
- The token is never logged. Neither the `Authorization` header nor the token appears in any log line; a test checks it for a request to `/dav/`.

### 3.4 What a client sees

- `/dav/` lists the share's vaults as folders, under the name the user sees (a member's alias). Below each, the vault's working set: notes (`.md`) and attachments as files, folders and empty folders (`FolderMarker`) as collections. `FolderMarker` files themselves are never listed.
- Properties: `resourcetype`, `getcontentlength`, `getcontenttype`, `getetag` (the version token, `VersionToken`), `getlastmodified` and `creationdate` (the last write; Kumbu² keeps no creation time), `displayname`, `supportedlock`, `lockdiscovery`, `quota-available-bytes` and `quota-used-bytes` (RFC 4331) on the root and the vaults **the share's user owns**; omitted on a shared vault (§3.10).
- `PROPFIND` with `Depth: 0` or `1`; `Depth: infinity` gets 403 with `<DAV:propfind-finite-depth/>`. A missing `Depth` header means `infinity` (RFC 4918) and is refused the same way.
- `PROPPATCH` answers 207 with every property reported as set and stores nothing (Windows and Finder set times and their own properties; refusing breaks copies).
- Parked files (§3.8) appear in listings of **that share only**, while they are parked.

### 3.5 Writing

- `PUT` of a `.md`: the body must be UTF-8 (a BOM is kept as it came); otherwise 415. `\r\n` becomes `\n` as on every other write path (`NoteWriter.Normalize`, `src/Kumbu.Core/Notes/NoteWriter.cs:475`): one rule for the whole system. Nothing else is changed: no link normalisation, no rewriting. The response carries the ETag of what was stored. The text is parsed as any write's is (tags, links for `links`/`backlinks`).
- `PUT` of a supported attachment format (`AttachmentFormat.All`: PDF, PNG, JPEG, GIF, WebP): the existing attachment write path, with its format check.
- **An empty `PUT` of a supported attachment format** (Windows Explorer and Finder create a file with 0 bytes first, then `LOCK`, then `PUT` the content): parked as a placeholder (§3.8), listed for that share only. The next `PUT` with content goes the normal way and replaces the placeholder; without one, the placeholder goes with the parking TTL. An empty `.md` is stored as a note: an empty note is valid.
- `PUT` of a name matching the parking patterns (§3.8): parked.
- `PUT` of anything else: 415 with a plain-text body "Kumbu² keeps notes, PDFs and images (PNG, JPEG, GIF, WebP) only" (`AttachmentFormat.UnsupportedMessage`).
- Limits as today: 1 MiB per note (`NoteWriter.MaxBytes`), 15 MB per attachment (`AttachmentFormat.MaxBytes`); larger: 413. Quota exhausted: 507 (§3.10).
- `If-Match` is checked against the version token (412 on mismatch); `If-None-Match: *` against existence. Without `If-Match` a `PUT` overwrites. When a concurrent write wins the compare-and-swap, the server retries once on the new state and overwrites: WebDAV has no merge.
- A missing parent folder: 409 (RFC 4918). `MKCOL` makes a folder as `mkdir` does; on an existing path 405.
- `DELETE`: to the trash, a folder with everything below it, in one batch. Exception: §3.6 case 4.
- `COPY`: a new note or attachment with the source's content, no link rewriting; a folder recursively. `Overwrite: F` with an existing target: 412.
- A vault with `read`: 403 for every method that writes into it. Structural files (`Board.md`, and whatever `StructuralFiles` names) need `maintain` as on every other path.
- `MOVE` or `COPY` across vaults: 502 (the server won't do it; file managers fall back to copy and delete). A `Destination` must be on the same host and below `/dav/`; otherwise 502.

### 3.6 `MOVE` and atomic saves

Paths are checked with `ApiPaths`/`VaultPath` as everywhere else. Cases, in order:

1. **A note, attachment or folder to a free path**: `NoteMover` (`src/Kumbu.Core/Notes/NoteMover.cs`), rewriting every link the move changes, one batch, as `sh mv`.
2. **A parked file onto an existing note's path** (temp file over the original): a content write of that note, one version in its history, no link rewriting. The parked file is gone.
3. **A parked file onto a free `.md` path**: a new note. If the **same share** removed a note at that path in the last 60 seconds (editors that delete the original first), that note comes back from the trash with the new content instead, keeping its history.
4. **A note onto a parking-pattern name** (editors that rename the original to `note.md~` first): the note is hidden from this share's listing and held, not moved. If a file arrives at the original path within 60 seconds, that is a content write of the held note, as in case 2, and the held name disappears. Otherwise, after 60 seconds, the note goes to the trash as a `DELETE` would have done. A `DELETE` of the held name within the 60 seconds does nothing more.
5. **`Overwrite: F` and an existing target**: 412. **`Overwrite: T` (the default) and an existing target that is not case 2**: the target goes to the trash, then case 1, in one batch.

**Published notes** (publish design §3.7: only a caller who may publish, or the owner's Obsidian device, removes a published note; a share never may publish):

6. **`DELETE` of a published note, or of a folder with one below it**: held as in case 4. A file arriving at the note's path within 60 seconds is a content write of the note, and the publication stays, as with any edit. Without one, the deletion is **not carried out**: the note reappears in the share's listing, nothing goes to the trash, and the owner's activity records that the share tried to remove a published note. For a folder, the rest of the folder is removed and the published notes (with the folders above them) stay.
7. **`MOVE` of a published note onto a parking-pattern name**: case 4, with case 6's ending if nothing arrives. **`MOVE` of a published note into an unpublishable folder** (which would withdraw it): 403 with the reason from `Refusals.cs`. Any other `MOVE` keeps the publication, as `mv` does.

The 60 seconds and the patterns are constants in one place, with a comment saying why.

### 3.7 Locking

Class 1 plus **fake locking**, class 2 advertised: `DAV: 1, 2` and `MS-Author-Via: DAV` on every `OPTIONS` (on `/`, `/dav/` and below). `LOCK` returns a token (`opaquelocktoken:<uuid>`), a `Timeout` (default `Second-600`, at most what the client asked for) and `lockdiscovery`; a refresh extends it; `UNLOCK` answers 204. Locks live in memory with their timeout and are never enforced: `If` headers with lock tokens are accepted and ignored. A restart forgets them, which is harmless.

### 3.8 Parking

Files that are not content are accepted and **parked**: kept in server memory, for the share that wrote them, never in MongoDB, never in search, embeddings, history, `sh`, MCP, the web app or sync.

- Patterns (case-insensitive, on the last path segment): every name starting with `.` (`.DS_Store`, `._*`, `.gitignore`, `.editorconfig`, `.~lock.*#`, `.goutputstream-*`, `.*.swp`), and everything below a folder whose name starts with `.` (`.git/`, `.obsidian/`, `.vscode/`, `.trash/`); `Thumbs.db`, `desktop.ini`, `~$*`, `~*.tmp`, `*.tmp`, `*~`, `*.swp`, `*.swx`, `*.kate-swp`, `*.part`, `*.crdownload`, `.ocTransferId*.part`; `MKCOL` of a dot-folder is accepted and parked the same way.
- A parked file lives 10 minutes after its last write. Per share at most 64 MB parked; beyond that the oldest parked files are evicted (it's junk: an error would abort a Finder copy of a folder with a `.git` in it).
- Parked files can be read back, moved, renamed and deleted within their share as files; §3.6 says what moving one onto a real path does.
- Parked bytes don't count against the quota.

### 3.10 Quota

- **What counts**: everything the user's **own** vaults take in the database: notes with their history, trash, moves, embeddings, checkpoints, attachment records and blobs. Exactly the figure the admin's user list shows today (`Admin.BytesByVaultAsync`, `src/Kumbu.Server/Accounts/Admin.cs:170`), computed from what MongoDB holds in the clear, without opening a vault. Metadata and history are part of the quota by decision.
- Data in a shared vault counts against its **owner**, whoever writes it. No per-writer accounting: sharing is with people trusted not to fill the owner's quota on purpose; revoking is the remedy.
- **Default**: `KUMBU_QUOTA_DEFAULT` (`Kumbu__Quota__Default`), a size like `2GB` or `500MB` with binary prefixes (`2GB` is 2 GiB, as the code already calls 15 MiB "15 MB"); empty or `0` means unlimited. Default of the setting: unlimited, so an existing server changes nothing on update.
- **Override per user**, set by an admin in the user list: the default, a size of its own, or unlimited. Stored on the user document in the clear (it is an admin's setting, like the role).
- **Enforced on every write that adds data**: `NoteWriter` and the attachment writer for every channel (MCP, REST, web app, upload, import, sync, WebDAV), restores from history and trash, checkpoint creation, WebDAV `COPY`. Refused with 507 over WebDAV and the REST API, and with a refusal over MCP. The check is against the current usage plus the size of what is about to be written; it may be off by a write's worth under concurrency, which is accepted. **Always allowed**, even over the quota: `rm`, `mv`, `DELETE`, `MOVE` within a vault, emptying the trash, revoking, signing out, reading. The seeder (`KUMBU_VAULTS`) is not limited.
- Usage is cached per owner in memory, computed with the admin's aggregation on first need and after a start, and adjusted by every write and sweep; a periodic recount (at most every 10 minutes per owner, on demand) corrects drift.
- **What a refusal says**: to everyone, "This vault is out of space." To the owner (session, own key, own share, own connection) additionally "See `df`." in `sh`, and in the web app "Your storage is full (2 GB). Empty the trash or ask your admin for more." A member gets the neutral sentence only, with no numbers. Known residual side channel, accepted: a member learns that the owner's quota is full.
- **Web app**: Settings shows "Storage: 182 MB of 2 GB"; from 90 % a quiet notice in the web app's shell for the owner (not an `sh` notice). The admin's user list shows "182 MB / 2 GB" with a small bar and the override control.

### 3.11 Emptying the trash

- The owner of a vault, in the web app's `TrashSheet` (`web/src/shell/TrashSheet.tsx`): "Delete permanently" per entry and "Empty trash" for all, each confirmed with the password (or within an open password window, as the invitation dialog does). Notes and attachments alike; the blobs only a removed entry held go with the next `BlobSweep` run as today.
- Not for members, not for any key, connection, device or share, not in `sh`/MCP: no agent can delete permanently.
- No other history is touched. A note's trash entry carries that note's history (`TrashedNote`), so deleting the entry permanently removes its history with it, as the dialog says. Blobs a checkpoint still holds stay until the checkpoint goes. An entry deleted permanently is a vault event in the activity ("Emptied the trash: 12 entries").

### 3.12 `sh`: `df` and `du`

Output is always human-readable (B, KB, MB, GB, one decimal from MB on). `-h` is accepted and changes nothing, since agents type `df -h` and `du -sh` out of habit; `-b` gives exact bytes.

- `df [-h] [-b] [/vault]`: the caller's **own** vaults only; shared vaults are not listed at all, not even as "n/a". A caller without an owner behind it in a vault (a member's key) sees only their own vaults.

  ```
  Vault        Used     Notes  Attachments
  /Personal    182.0 MB   412           38
  /Work         41.3 MB   127            9
  ──────────────────────────────────────────
  Total        223.3 MB  of 2.0 GB (11 %)
  ```

  Without a quota: `Total 223.3 MB (no limit)`. `df /Work` gives one vault. `df` on a shared vault: "df shows only vaults you own; a shared vault counts against its owner." `help df` says what Used includes (history, trash, embeddings) and that shared vaults count against their owner.
- `du [-h] [-b] [-s] [-d N] [path]`: the size of the **current content** below a path (notes' text, attachments' bytes), in any vault the caller can read, shared ones included (it shows only sizes of what the caller may read anyway). Without `-s` the direct children of the path, folders summed, largest first, then a total line (like `du -d 1`); `-d N` goes deeper; `-s` the total only. A `*` in the path gets the shell's answer that there is no globbing, plus "du lists a folder's children itself". `help du` says why `du` of a whole vault is smaller than its `df` line.
- Both in `Manual.cs` and `help`, with examples.

## 4. Data and keys

- **Collection `dav_shares`**: share id (the 4 characters of the username), owner's user id, lookup value of the token (as `api_keys` keeps one), keyed name hash of the label, label sealed under the user key, created, last used, expiry, revoked. In the clear as for `api_keys` (`docs/security-architecture.md` §5.6), minus the key prefix (no part of the token is stored).
- **Slot kind `dav`** in `slots`, one per vault of the share: the vault key and the right, sealed under `HKDF(token, "kumbu/v1/dav-slot-kek", salt = vault id)` with associated data `slot:{vaultId}:dav:{shareId}`, as the API-key slot (`ApiKeySlotPayload`, `src/Kumbu.Server/Vaults/VaultCatalog.cs`). A member's share slot carries `grantedVia`.
- Re-keying a vault removes its `dav` slots, as it removes API-key slots (`VaultCatalog.Rekey.cs`): the share loses that vault and the WebDAV tab says so, as the key list does for keys. Deleting a vault, a membership or an account removes them.
- **User document**: `quota` (bytes, or null for the default, or −1 for unlimited) in the clear.
- Parking and locks: memory only.

## 5. Security and documentation

The security boundary:

- **Not touched**: the encryption scheme, the existing slot kinds and their derivations, sessions, OAuth, pairing, and the publish feature's rules (merged in #150): a share is a credential without "May publish" and is treated as one, apart from §3.6 cases 6 and 7.
- A share's token is a credential like an API key: 256 bits, never stored, never logged, never in a URL. Rights are server-enforced per vault.
- XML request bodies are parsed with DTD processing prohibited and no external resolution (`XmlReaderSettings { DtdProcessing = Prohibit, XmlResolver = null }`), at most 64 KB.
- Every path goes through `ApiPaths`/`VaultPath` (NFC, no `..`, no empty segments); `Destination` headers are checked for host and prefix.
- Responses to `/dav/` carry no cookies and are not cached by shared caches (`Cache-Control: private`).
- An independent security review of the finished work is part of the run, as in earlier overnighters.

## 6. End to end

Chris owns the vaults `Personal` and `Work`; the server's default quota is 2 GB. `Work/Ideas/Routing.md` links to `[[Questions]]`, which is `Work/Ideas/Questions.md`.

1. In the web app, **Access → WebDAV → New share**: label "Work PC", `Work` with `write`, no expiry, password confirmed. The connect page shows `https://kumbu.example.org/dav/`, `chris.k7qm` and a 52-character password. He copies them into his password manager.
2. On the work PC, Windows Explorer, **Map network drive** → `https://kumbu.example.org/dav/`, username `chris.k7qm`, the password. Drive `K:` shows one folder, `Work`. Explorer writes `desktop.ini` and `Thumbs.db`: parked, never seen anywhere else.
3. He drags `diagram.png` and `budget.xlsx` into `K:\Work\Ideas`. The PNG arrives (the web app shows it in the gallery, search finds nothing new, history names "Work PC (dav)"); Explorer reports an error for the spreadsheet (415).
4. He opens `Questions.md` in an editor, changes a line and saves. The editor writes `.Questions.md.tmp`, deletes nothing and moves the temp file over `Questions.md`: one new version of `Questions.md` in its history, and `Routing.md` is untouched.
5. In Explorer he renames `Questions.md` to `Open questions.md`: `Routing.md` now links to `[[Open questions]]`, and the history shows the move and the rewrite as one batch.
6. At home, Dolphin with a second share "Home" (`Personal` and `Work`, both `write`) mounts `webdavs://chris.h3x9@kumbu.example.org/dav/`; KWallet keeps both shares' passwords apart.
7. His agent runs `df -h`: the two vaults, 1.9 GB of 2 GB (95 %). It runs `du -sh /Work/Archive`: 1.4 GB in PDFs. Chris deletes the archive folder from Dolphin; `df` still says 95 %, since the trash counts. In the web app's trash he chooses **Empty trash**, gives his password; after the next blob sweep `df` says 25 %. The agent can't empty the trash: there is no command for it.
8. Had his usage reached the full 2 GB, a member of `Work` uploading a PDF would have been refused with "This vault is out of space.", without any number, while the member could still remove and move notes.
9. He revokes "Work PC". The next request from drive `K:` gets 401.

## 7. Left to the builder

- The XML writer and reader's structure; Go's `golang.org/x/net/webdav` is the reading reference for the protocol's corners. No .NET WebDAV library: none fits the store.
- Where the quota check sits so that every write path passes it (one place in the store or the writers is better than one per endpoint).
- How the usage cache learns of sweeps (trash expiry, blob sweep, history trimming).
- Wording of dialogs, refusals, help and the connect instructions, in British English, matching the app.
- Tests:
  - xUnit: authentication (right, wrong token, username of another share, expired, revoked, user deactivated, membership ended, re-keyed vault, HTTP refused, 401 and 429), rights per vault and structural files, every method's status codes in §3.4–§3.8, all seven cases of §3.6 with the link rewrite and the history they leave (published notes included), the 60-second windows (with `TimeProvider`), parking (patterns, isolation between shares, the 64 MB cap, TTL), the quota on every write path in §3.10 and what each refusal says to owner and member, emptying the trash (owner only, password, refused for every other caller), `df`/`du` and their flags, the token in no log, `Nothing_readable_reaches_the_database` covering `dav_shares` and `dav` slots.
  - **litmus** in CI (`.github/workflows/ci.yml`): a job that starts the server with MongoDB, creates a share and runs litmus's `basic`, `copymove`, `props` and `locks` suites against a dot-folder of a vault, `/dav/<vault>/.litmus/`: litmus creates resources without an extension (`res`, `copysrc`, `lockme`), which the real store refuses with 415 by design, so litmus tests the protocol layer through the parking area (§3.8), which therefore uses the same protocol layer as the real store (properties, `COPY`, `MOVE`, locks) rather than a shortcut of its own. The real store's behaviour is covered by the xUnit tests. No test-only switch in the server.
