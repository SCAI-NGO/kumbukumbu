# Tests of 0.6.0: an MCP suite and the specific UI run

Status: approved by Chris, 2026-11-19.

## 1. Goal and decisions

0.6.0 is feature complete and on staging as `v0.6.0-pre.4` (`63d3ca46`). Before it is released, one run in a cloud VM tests what 0.6.0 brought, in two parts:

- **(a) An MCP suite:** scripted, deterministic tests that speak MCP to a running server, the way an agent does, and check the answers. No model is involved.
- **(b) The specific UI run for 0.6.0:** Playwright against the web app, as the 0.5.0 run did (`2026-11-14-ui-tests-design.md`), for 0.6.0's new UI plus the smoke set.

What neither can reach is Chris's hand test afterwards. The security audit of 0.6.0 runs beside this run in a session of its own.

Decisions, each with Chris's reason:

- **No AI in the tests themselves.** Chris: the MCP tests must be automated, not AI-based, so they give the same result every time and can later go into CI.
- **In the cloud VM, against a stack of its own.** Not against staging or production. This is the reason of the 0.5.0 spec, unchanged: 100% reproducibility from a fresh install. Chris counts these runs as part of the dark factory.
- **The run reports; it doesn't fix the product.** Same rule as for 0.5.0: a test that finds a real bug stays in the suite, marked `test.fail()` with the finding's id. The fixes follow in one fix run together with the audit's findings and the hand tests' points. That way there is one fix run, one review and one pre-release to test.
- **The MCP suite lives in the existing Playwright suite**, as its own project `mcp`. It reuses the stack, the setup, the users and the `Mcp` helper in `web/e2e/support/api.ts`. There is **no new dependency**: the helper already speaks JSON-RPC over `POST /mcp`. Why: the e2e suite already holds everything a black-box test needs, and a second harness would duplicate it. The MCP SDK would add a dependency without adding a test.
- **iPhone steps stay out.** Chris has no iPhone. The community tests HEIC uploads, deep links on tap and the PWA against production after the release, and a problem found there gets a 0.6.1. The part is not critical.

## 3. The MCP suite

- **Where:** `web/e2e/mcp/*.spec.ts`, in a Playwright project `mcp` with no browser, which depends on `setup`. Tests call `Mcp.create(...)` and `mcp.sh(...)` / `mcp.call(...)`. The helper sends only `tools/call` today; it gains a `raw(method, params)` that returns status and body, and on it an `initialize` (instructions come only from `initialize` and `server/discover`, `src/Kumbu.Server/Mcp/HandshakeInstructions.cs`). The project gets `testMatch: /mcp\/.*\.spec\.ts/` and no device; the browser projects get `testIgnore: /mcp\//`, and `web/e2e/stack/run.sh` runs `--project=mcp` in its first phase. A project without a browser works as long as its tests use only the `request` fixture.
- **Assertions are exact or structural**, never vague. Each test checks:
  - the line or block an answer must contain;
  - the error text of a refusal;
  - a state read back through a second call (`cat` after `edit`, `history` after a write with `message`).

  "Contains no error" alone never passes a test.
- **Two people where sharing matters:** Alice and Bob as in the 0.5.0 setup. Where a test needs Bob as a write member, it uses a vault of its own that Alice shares with Bob at `write`. This is allowed now: the 0.5.0 run listed it as missing, and the setup may add it, through the app's invitation path.
- **The upload's HTTPS rule.** The stack runs as Production at `http://localhost:8080`, and over plain HTTP `src/Kumbu.Server/Auth/CallerMiddleware.cs` (around line 321) spends the link and answers 403 "Uploads need HTTPS; this URL was sent in the clear and is spent", before it looks at the ticket. So the suite tests the tool's answer (the URL, `expires`, the curl line, the size limit), its refusals (a note path, an existing file without a version, a read-only key) and that 403. Single use, expiry and "stored as the agent's write" are covered by `UploadTicketsTests` and `AgentUploadApiTests` and by the hand test from a claude.ai sandbox (§6). **Never loosen the rule to make a test pass:** no `ASPNETCORE_ENVIRONMENT=Development`, no trusted proxy, no forged `X-Forwarded-Proto`, no TLS added to the stack.
- **Hostile inputs are ordinary test inputs:** an XML file with a DTD, an HTML page with `<script>`, an XPath that would run long on a document of about 100,000 nodes (for example `//*[count(//*) > 0]`). They go in through the web API's file upload (`Api.putFile`) and are read through `sh`. Each test asserts that the reader refuses or bounds the input, within its stated limit.

## 4. The UI run

As the 0.5.0 spec §2 to §5 set out: the stack in `web/e2e/stack/`, the viewports, `@phone` at 375 px, `@serial` for global lists and discreet vaults, `test.fail()` with `F-NN` for a bug, and one screenshot per tag and viewport. New tags follow the table in §2.

- **Large files in the browser:** one upload of about 100 MB through the web app, with the progress bar, and its download compared by checksum. Playwright's `setInputFiles` refuses a buffer over 50 MB: write the bytes to `testInfo.outputPath()`, pass the path, and delete the file afterwards. 500 MB and a real proxy are a hand test (§6).
- **The script** `pnpm -C web e2e:0.6.0`, written like `e2e:0.5.0` in `web/package.json`, runs `@smoke`, every tag of §2 and the `mcp` project; each MCP test carries its tag in its title, so the `--grep` takes it. It can be run again unchanged.

## 5. What the run does with what it finds

Unchanged from the 0.5.0 spec §5:
- triage each failure as **bug**, **test** or **unclear**;
- give each bug a severity on the audit's scale, a repro, the expected and the actual behaviour, and a screenshot where there is a page;
- write each finding so the fix run's brief can link to it unchanged.

MCP findings get ids `M-NN`, UI findings `F-NN`.

## 7. Out of scope

- Fixing anything the suite finds.
- CI integration, a full run of everything before 0.6.0.
- Firefox, WebKit, real devices, outside clients.
- Testing against staging, production or any real host.
- Changes to the server or the web app, apart from `data-testid` where no role or label finds an element (each one listed in the report).

## 8. Security boundary

The 0.5.0 spec §8, unchanged:
- the stack listens on `127.0.0.1` only and runs without a dev token;
- secrets are random per run and never written down;
- no product code is touched beyond `data-testid`;
- a test never loosens a security setting to pass. If something works only with a weaker setting, that is a finding.
