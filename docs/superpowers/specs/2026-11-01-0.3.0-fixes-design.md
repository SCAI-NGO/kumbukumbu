# The fixes for 0.3.0

Status: **design**, 2026-11-01, for an unattended run on `feature/0.3.0-fixes`. Sources: two independent security reviews of the code (at `0f5ce45` and `1291d64`; the findings below are their content, the reports aren't in the repository), the first half of the hand test of vault sharing ([test-playbook-collab](../../test-playbook-collab.md), parts A to E) and [the collab design](2026-10-31-collab-design.md), whose §10.1 the web app doesn't yet fully meet.

No version bump and no tag: that stays with the maintainer. Parts F and G of the hand test run on the result. Plugin 0.2.0 has its own repository and is not part of this.

## 1. Security: must hold for the release

### 1.1 The sidecar client refuses redirects

`src/Kumbu.Server/Program.cs:74-75` builds the sidecar's `SocketsHttpHandler` without `AllowAutoRedirect = false`, so a compromised sidecar could send the server's requests, with decrypted files in them, to another address, and `SidecarPeers.ConnectAsync` (`Attachments/SidecarPeers.cs:79-106`) would connect there.

- `AllowAutoRedirect = false`; a 3xx from the sidecar is an error of the sidecar, handled like a malformed answer.
- `ConnectAsync` refuses any host or port other than those of `Kumbu:Pdf:Url`.
- A test asserts the handler's setting, as `ClientMetadataTests.cs:438` does for the metadata fetcher.
- `docs/security-architecture.md:54` and `:637` state what is now true.

### 1.2 Re-keying trusts only pins the owner vouched for

Today pins are sealed under the vault key alone (`Sharing/Memberships.cs:152-155`), and the finish (`:281-300`) wraps the new key to whatever a pin that opens under the **old** key names. A former member who kept the old vault key and can write the live database can therefore replace a pin, and the re-key meant to cut them off hands them the new key. The design (§5.4, §13 C1) names the residual but takes re-encryption for its remedy; it isn't.

Decided by the maintainer: **a pin carries a vouch only the owner can make.**

- `vouch = HMAC-SHA256(HKDF(ownerUserKey, "kumbu/v1/pin-vouch"), vaultId ‖ membershipId ‖ memberId ‖ publicKey)`, stored on the membership. Neither a holder of the vault key nor the database can compute it; a pin from before the fix has none, and nothing is released with those.
- **When it is made:** in the owner's session, whenever she has the user key at hand and a membership of hers has none or a stale one: on confirming a redeemer, on opening the access list, and at the start of a re-key run she drives. It trusts what the database says at that moment; the first-use window that leaves is documented as a residual.
- **The finish** wraps the new key only to a pin with a valid vouch under the driving owner key. A membership with none is treated as a redeemed unconfirmed one is today (design §7.1): declined at the start of the run and not given the new key, with the owner told by name and offered a new invitation. A vouch made at the run's start covers memberships already present then, so an owner re-keying right after an acceptance loses nobody.
- **Rotation:** the owner's user-key rotation and recovery recompute the vouches under the new key, in the rotation's transaction where it can open the pins. A member's rotation changes her public key, so her vouch goes stale until the owner's next session; if a re-key comes first, she is the case above, and is told.
- **A slot that doesn't match** at a member's own rotation (`UserKeyRotation.cs:393-417`) is reported to her, not deleted in silence.
- `docs/security-architecture.md:63`, and design §5.4 and §13 C1 by an amendment in §14, say what re-encryption ends now, and the residual.

Tests: a forged pin (right vault key, no vouch, another's public key) gets no new key and the owner is told; the normal paths keep access; the owner's rotation between vouch and re-key keeps access; mutations on the check and on each field of the HMAC.

### 1.3 A member can't stall a re-key or the whole instance

A member's alias rename (`VaultCatalog.Members.cs:161-204`) writes the slot the finish writes. In a loop it makes the finish's transaction conflict and retry for up to 120 s, and the finish holds the process-wide `_loading` semaphore (`VaultCatalog.Rekey.cs:318-330`, `:365-371`) that every vault opening needs (`VaultCatalog.cs:1150`). So one member, even a reader, can stop everyone's vaults during an owner's re-key, measured at 60 to 120 s per attempt.

- **While a run holds a vault or it is in its two-key period,** member writes to its memberships and slots (alias, provider seen) answer the existing 503 "being re-encrypted".
- **`_loading` isn't held across a transaction that retries,** at the start and finish of a run or in `DeleteVaultsAsync` (`VaultCatalog.cs:728`): mark the vault, run the transaction outside it, take `_loading` only for the switch in memory after the commit. A vault marked so answers "being re-encrypted" meanwhile. This is the delicate part of this run: the existing re-key tests must stay green unchanged, and every state between marking and commit needs a test of what a reader sees.
- **Retries are bounded:** the transaction gets a token that ends after a few seconds per attempt window; a failure leaves the run to the runner's existing back-off.
- **Alias renames are rate-limited** per user.

A test with renames in a loop, as the review measured it: the finish commits, and an unrelated user's opening stays under one second.

## 2. Vault sharing as designed but not delivered

- **Sharing events are never shown.** The server records them and returns `events` with the activity (`Api/HistoryApi.cs:306-320`); `web/src/shell/ActivitySheet.tsx` ignores it, and nothing calls `/api/vault-events`. So "Bob exported it", "Alice changed your role" and the rest stay unseen, though the export event is why members may export at all (design §3.3). The activity shows them in time order among the rows, as sentences from the server's `text`. A member gets her events across vaults, also of vaults she has lost, in a place of her own: **Settings, "Shared vaults"**, unless the code offers a better one.
- **Deleting an account doesn't ask about shared vaults.** The server takes `sharedVaults` (`Api/AccountApi.cs:86-94`), the web app never sends it, so 7 days apply unasked. Both dialogs (Settings, Admin) list the shared vaults and offer the two choices of design §7.3; the admin's receipt shows `sharedVaultsScheduled`.
- **Raising to maintain always asks for the password** (decided by the maintainer), by the access list's dialog, not only when the window is closed. Raising to write keeps the window rule.
- **A sweep of design §10.1 against the app.** Go through it point by point in the code. Fix what is small, and list the rest in the report; route-level use was checked, field-level wasn't.

## 4. An example from end to end

Alice shares *Garten* with Bob and Carol, Bob as write, and makes Bob's vouch when she confirms. Carol accepts a link that needed no confirmation; Alice's next look at the access list vouches for her too. Bob renames his name for the vault, and Alice raises him to maintain, typing her password. Bob exports; Alice's activity says so, among the notes that changed. Later Alice revokes Carol and ticks re-encryption. The run marks the vault, and Bob's rename and reads answer "being re-encrypted", while Alice's other vaults and every other user's open at once, even though Bob tries again and again. The finish finds Bob's vouch valid and wraps him the new key. Had someone replaced his pin, he wouldn't get the key and Alice would be told by name. Afterwards Bob reads on; his agents need the vault again, and his "Shared vaults" list says why. Carol's list says she lost access, and Carol's old key no longer opens anything new.

## 5. Order and risk

Security first: 1.1, 1.4, 1.2, 1.3, because 1.3 touches the most sensitive code and should have the others green behind it; then 2 and 3. If 1.3's move of `_loading` turns out unsafe in the time, the run keeps the three other parts of 1.3, leaves the semaphore as it is, and says so in the report: refusing member writes already closes this attack, and the semaphore is its general form.
