# Brief: the specific test run for 0.7.0, with search by meaning on

Hi, thank you for taking this one on! Kumbu² is a Markdown second brain served over MCP: a C# (.NET 10) server, a React/Vite web app, MongoDB. 0.7.0 is feature complete and on staging as `v0.7.0-pre.1` (`ad920a73`). Its new features:
- offline mode, read and write, with devices that keep a copy (and their renaming);
- the graph view out of preview, its edges measured by meaning;
- Similar notes (link prediction) with Add link and Not related;
- knowledge synthesis for agents: `similar` and the system skill `synthesize-knowledge`;
- the Published window with Compare;
- hardening: deactivation removes offline copies, the service worker serves only the build's bytes.

Only offline mode has end-to-end tests so far (`web/e2e/offline/offline.spec.ts`). This run writes the rest and runs the whole 0.7.0 set, in the browser and over MCP (the suite's browserless project `mcp`), with **search by meaning on and the real model** for the features that need it. **You report what you find; you don't fix the product.** A joint fix run follows.

Nobody is available to answer questions during this run, and that is intended: Chris has reviewed and approved the spec. Everything after it is yours, from the plan to the pull request. The decision rules below tell you how to settle what the spec leaves open.

## Open points for the run

All of these are yours to **decide** with the rules below; log each in the report.

1. **The search overlay** (spec §3): how `up.sh`/`run.sh` take it (`E2E_SEARCH=1` or a second compose file in `COMPOSE_FILE`), and how the server's container gets the proxy and its CA. The final stage (`aspnet`) doesn't carry the CA (`compose.proxy-ca.yaml`'s comment): mounting the CA bundle and pointing `SSL_CERT_FILE` at it, or a CA-carrying copy of the final base as the build stages get, are both fine. `SSL_CERT_FILE` replaces the system store, so the file must be a full bundle, readable by the `app` user. Changes stay in `web/e2e/stack/`; `compose.yaml` and `compose.build.yaml` are not touched.
2. **The fixtures for meaning.** Write small, clearly separated topics (for example: diving with decompression and dive tables; baking with a cake and bread; a garden) so the clear cases are clear for any reasonable model. Before asserting, look at what the model actually ranks for them once, and keep only assertions on cases that are clear by meaning. If a case that is clear by meaning comes out wrong, run it again on a fresh stack; if it stays wrong, it is a finding marked **unclear** (the model, not the product, may be the cause).
3. **The floor of 0.5 for Similar notes** (link prediction spec §3.5): if unrelated notes of the fixtures pass the floor with arctic-m, that is a finding (Medium, unclear) with the cosines seen, not a fixture to bend.
4. **Waiting for embeddings:** by the product's own signals (`pending`, `preparing`), with a bound stated in the test (several minutes for the first index after the download is fine); never `waitForTimeout`.
5. **TensorX** (spec §3): if the placeholder check shows that the proxy only adds its header beside the server's and TensorX refuses, use the **emergency path** (decided with Chris on 2026-11-23): a small forwarder in the suite's compose file, sharing the server container's network namespace (`network_mode: "service:kumbu"`), listening on `127.0.0.1` there, dropping the `Authorization` header and passing the request on to `https://api.tensorx.ai/v1` through the VM's proxy, which then adds the real one. The `tensorx` provider's `BaseUrl` points at it (plain `http://` is allowed to a loopback address, and then no key file is needed). No switch in the product: a setting that makes the server send no keys would be a misconfiguration waiting to happen in production, for a need only this VM has. BYOK can't take this path (TensorX's address is built in), so in that case BYOK is left out with the reason. If even that fails, leave `@tensorx` out with the evidence (status codes, no headers) and carry on. The search overlay carries both the `tensorx` provider and BYOK (spec §3), so "never compares two models" can run there. A key typed into Settings is a placeholder; that the check passes only because the proxy replaces it is worth one line in the report.
6. **Deactivation** (`@devices`) and **BYOK** (`@tensorx`): each with a user made for the test (an invitation through the admin, as the setup makes Alice and Bob), never Alice or Bob. Deactivating needs the admin's password window and saving a key the user's: count password checks against the limits (5 a minute per username).
7. **Tags** (spec §2): `@search` on every test that needs search on; the Published window is `@overview`. Check that `e2e:0.6.0`'s grep selects the same tests as before your change.
8. **Discreet vaults** (spec §2): one `@serial` test per new place; each runs in a session of its own and ends hidden.

## How to work

- **Subagent-driven**: one fresh subagent per tag task, then an independent review per task by a fresh subagent, checking each test against its spec (every promise covered or listed as left out; the assertions really check what "passes" says). Re-review after each fix round until clean. Subagents never merge, push or switch branches; you commit and push. Subagents that write tests run only their own tag (`--grep @tag`) while another runs anything heavy.
- **Test discipline:** no `waitForTimeout`; locators by role, label or text; a test is done only once it has been seen to fail: break its assertion once, watch it fail, restore it. Record this per tag.
- **Triage** (spec §5): run a failure again alone. If it passes, it is flaky: fix the waiting, never add a retry. If it fails again, decide **bug**, **test** or **unclear**. A bug gets `test.fail()` with `M-NN` or `F-NN` and a severity: High for data loss or a security breach (a read-only member writing, a discreet vault showing, a wiped copy opening, a changed file served), Medium for a feature not doing what its spec says, Low for wording, layout or a target under 44 px.
- **The run at the end:** `pnpm -C web e2e:0.7.0` (and `e2e:0.7.0:tensorx` once, if TensorX works) from a fresh stack **twice in a row**, with the same result both times (the second may reuse the model's volume). Record the times and counts. A test that differs between the two runs is flaky: fix it or take it out, and list it.
- **The web gate at the end:** `pnpm -C web test --run && pnpm -C web build` green. CI runs the rest; check with `gh pr checks`.
- **Commits:** after every task; imperative and free-form, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; files staged by name, never `git add -A`.
- **Style:** British English; new files start with `// SPDX-License-Identifier: AGPL-3.0-or-later` (`#` in shell and YAML); neutral names only: Alice, Bob, `Home`, `Work`. The repository names no customer or employer.

## Deciding without Chris

When the spec leaves something open, or something unforeseen comes up, choose the option that satisfies these, in this order:

1. **Breaks nothing.** The product is unchanged, the web tests and build stay green, the suite leaves no state behind.
2. **Reproducible from a fresh install.** Chris's reason for the whole setup: two runs give the same result.
3. **Deterministic.** Exact or structural assertions; with the model, order and membership of clear cases only, never a score's value; nothing that depends on timing beyond a stated bound.
4. **Opens no new security hole.** A test never loosens a setting to pass.
5. **True to the spec.**

If a question can only be answered by changing the spec's scope, don't guess: leave that part out and record it in `docs/superpowers/open-items.md`. Log every decision made this way, in the report and in the pull request under **Decisions made without Chris**, with the options you saw and why you chose this one.
