- **Mutation (e) survives, and the reviews agree it can't be observed.** A finish only ever runs after this run's own start has set or kept the `_pending` mark under `_loading`, also for a run resumed in a fresh process. While the mark is set, any object made with K is refused before its key id is even compared, and `Current()` is null. The security review confirmed this. It noted that it relies on `IsBusy` being checked before `HasCurrentKey`, and that no test pins the settle step after the commit. Setting `_keyIds` only after the commit is defence in depth.
- **Fix `7c2a89e` (the quality review's must-fix):** the transition tests left runs behind in the shared `app` fixture. A read that meets the vault in its period wakes `RekeyRunner`. Its attempt backed off for a minute and could later start a run during an unrelated test, firing that test's hook. The class now gets a host of its own per test, as `RekeyContentionTests` does, and disposing the host stops its runner.
- **Fix `cfe7246` (the security review's Low L1, a gap that predates this work):** `LoadAsync` cleared `_pending` before its reads and before recording the new key id.
  - After a finish whose commit answer was lost, a load under K′ opened a window: during its reads, an object made with K that a request still held passed `CheckWritable` and `MayIndex`.
  - The mark is now cleared just after `RecordKey(vault)`, and before the vault is put in the working set and announced.
  - A test hook `LoadBetweenReads`, made like `FindBetweenReads`, and the test `A_load_under_the_new_key_keeps_an_old_object_refused_until_the_key_is_recorded` cover it. Before the fix the test failed with "No exception was thrown".
  - After both fixes: `RekeyTransitionTests` 12/12; the regression set three times 96/96. Mutations (c) (9 of 12 failed) and (d) (4 of 12) were killed again.
  - A second, short security review of `cfe7246` also says keep (see "Phase gates and final verification").
- **Why each reader of the shared state is safe while `_loading` is free during a transaction.** For the vault being re-keyed, its state in memory during the transaction is the same as today: out of the working set, marked in `_pending` and `_rekeying`, `_keyIds` still K until the finish's end step. Only loads of other vaults now go ahead.
  - `CheckWritable`, `MayIndex` and `IsCurrentObject` refuse the vault because of `IsBusy`.
  - `Current()` is null, which covers the search index, `SyncHub.Shown`, the PDF runner and the rename's action.
  - Every opening path goes through `LoadAsync`.
  - A deletion can't meet a transition of its own vaults: the run holds both gates through its transitions, and a run that missed the deletion's look meets the tombstone before its start.
  - A rename is refused with 503 during a run.
- **Invariants stated in existing comments that the spec doesn't name; all are kept:**
  - The rename's "a load that read the meta before the commit has published by the time `_loading` is ours".
  - The deletion's "a request that read the slot and the vault document just before the commit can't put the vault back".
  - `RekeyAsync`'s "out of the run before the gates open", which needs `_keyIds` set before `_rekeying` goes.
  - The `_pending` doc comment.
  - "A vault in its two-key period is returned as a placeholder only".
- **Deviations and remarks:**
  - The spec says deletion and rename keep `_loading` "across their own transactions". The rename only ever took it after its commit. The comments describe the code as it is, and the spec is unchanged.
  - The argument that a rename can't meet a transition partly relies on `SemaphoreSlim` serving its waiters in order, which isn't documented. The comment therefore gives the fallback as well: `Current()` is null while a run holds the vault.
  - The new 5 s bounds for another vault's read are generous (that read takes `_loading` only briefly), but on a very slow CI runner they are the first thing to look at.

## The hand test

On a real instance running this branch's image. Each step says what to do, where to look and what passes.

### 1. The pairing code's copy button

1. Sign in as the owner of `Gartenarbeit`. Open the vault's menu and choose "Connect Obsidian…", then wait for the code.
2. Look under the code, below "valid for … · single use": there is a "Copy" button. **Passes:** clicking it says "Copied". Pasting into any text field gives exactly the code shown, for example `K7QM-4XDA`, with no spaces.
3. Leave the dialog open until the countdown reaches 0:00. **Passes:** the code and the Copy button are gone, and only "New code" remains. Click "New code": the button comes back with the new code.
4. Look at the spacing between the Copy button and "New code". **Passes:** it looks deliberate. If the two buttons touch, that is the optional point from the review: a `mt-1` on the button.

### 2. The pairing dialog lists connected devices (on a phone too)

1. Pair a first Obsidian device with `Gartenarbeit` (plugin, server address, code). Then open "Connect Obsidian…" again for the same vault.
2. Above "Each device gets its own key…" there is a line "Already connected: **<the device's key name>**, last used <date and time>." with a "Revoke" button, followed by "Revoke one only if that device is gone or is being replaced."
3. Check what doesn't appear. **Passes:** none of these is listed:
   - an agent key on this vault (created under Settings → API keys);
   - a device key on another vault, `Work`;
   - a revoked or an expired device key.
4. Click "Revoke". **Passes:** a confirmation asks "Revoke <name>?", and Cancel sends nothing. Confirming removes the line, while the pairing code stays and doesn't change. On the Keys page the key now shows as revoked, and the Obsidian device it belonged to stops syncing.
5. Repeat steps 1 to 4 on a phone (the mobile layout). **Passes:** a long key name wraps, the Revoke button stays visible and doesn't stretch, and the confirmation sits above the pairing dialog. The Escape key, or the back gesture, closes only the confirmation.
6. Do the same as a member (Bob, on Alice's shared vault, with his own device key). **Passes:** Bob sees only his own device keys on that vault, under his name for the vault.
7. With no device key on the vault, the dialog looks as it did before: no list, no sentence.

### 3. A second tab follows a rename (two real tabs, with unsaved text)

1. In browser tab 1 and tab 2, open `Gartenarbeit/plan.md`. In tab 2, switch to editing and type a line without saving.

4. **Passes in tab 1:** it moved as before, and nothing flickers or reloads a second time.
5. Open tab 2 on another vault, for example `Work`, and rename `Garten` back in tab 1. **Passes:** tab 2 stays where it is.
6. Rename twice quickly, A→B, then B→C. **Passes:** the second tab ends up on C.
7. With Bob as a member with the vault open: when Alice renames it, Bob's tab doesn't move, and his name for the vault stays.
