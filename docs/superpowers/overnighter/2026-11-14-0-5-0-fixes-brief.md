## How to work

- **Subagent-driven** (`superpowers:subagent-driven-development`):
  1. A fresh subagent per fix: red test, green, commit locally, then every mutation on its own (break, watch it fail, restore with `git checkout -- <file>`).
  2. Then a spec-compliance and code-quality review by a fresh subagent.
  3. **For a security fix, also the fix review** of private spec §1.
- Subagents never merge, push or switch branches. You commit and push.
- **Commit messages** are imperative and free-form, with no Conventional Commits prefix, and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. The commit author is Claude, which is intended. **On the public branch, a security fix's message carries no finding id, no "security" and no "fix S5-…"**: it says what the code now does. Product fixes may name F-01 to F-03 in the body.
- **Keep the public tree clean.**
  - Confidential notes, the tests that show a weakness, and the measuring harness live in the private clone or a scratch copy outside every public worktree.
  - Public tests for security fixes assert function only, with ordinary inputs; a finding's own input and timing bound never go public (private spec §1).
  - Stage files by name, never `git add -A`, `git add .` or `commit -a`.
  - Before every public push, run `git diff origin/feature/fixes-0-5-0 --stat` and check the files.
- **Time in tests** comes from the injected clock (`FakeTimeProvider`), never the wall clock.
- **Byte preservation:** every frontmatter write keeps every other byte, as `CalendarService` and the flag editor do today.
- **A UX check** by a fresh subagent with Playwright, before the final gate.
  - It runs against the e2e stack or a local server, never a real host.
  - It covers spec §2.1 to §2.6 at 1280 px and at 375 px with touch, in a light and a dark scheme.
  - It reports every place where the screen speaks of our fields instead of the person's wish, where the spec's wording isn't used, or where a target is under 48 px.
  - Fix what it confirms; record the rest.
- **Test commands.**
  - One core class: `dotnet test --project tests/Kumbu.Core.Tests --configuration Release --no-build -- --filter-class "*ClassName"`; build first with `dotnet build --configuration Release --no-restore`.
  - One server class: the same with `tests/Kumbu.Server.Tests`.
  - One web file: `pnpm -C web test --run <file>`.
- **The full gate**, as CI runs it, at the end of each phase and at the end:
  ```sh
  dotnet restore --locked-mode
  dotnet build --configuration Release --no-restore
  dotnet test --project tests/Kumbu.Core.Tests --configuration Release --no-build
  dotnet test --project tests/Kumbu.Server.Tests --configuration Release --no-build -- --filter-namespace Kumbu.Server.Tests.Api --filter-namespace Kumbu.Server.Tests.Mcp --filter-namespace Kumbu.Server.Tests.Auth --filter-namespace Kumbu.Server.Tests.Net
  ```

  - A web gate counts only if no agent was editing web files meanwhile.
  - At the very end, run the end-to-end suite twice from a fresh stack (`E2E_PROXY_CA=/root/.ccr/ca-bundle.crt pnpm -C web e2e:0.5.0`). Both runs must be identical, with F-01 to F-03 passing.

## Deciding without Chris

When a spec leaves something open, or something unforeseen comes up, choose the option that satisfies these, in this order:

1. **Breaks nothing.** Existing behaviour, data and interfaces keep working, apart from what the specs change. Prefer the reversible change.
2. **Gives nothing away.** Nothing about an unreleased weakness on a public branch.
3. **True to the spirit of the application.**
   - Campy: plain notes and frontmatter, no new stores.
   - Human-centric: the screen speaks of the person's wish.
   - Honest: a button does what it says, and nothing is hidden quietly. Chris: honesty is part of the security architecture.
4. **Opens no new security hole.**
5. **True to the specs.**

If a question can only be answered by changing a spec's scope, don't guess: leave that part out and record it. For a security finding, it goes into `audits/2026-11-14-0.5.0.md`, section "Open for Chris", on the private branch. For the rest, it goes into `docs/superpowers/open-items.md`.

Log every decision you made this way. Put it in the report and in the pull request's description under **Decisions made without Chris**, with the options you saw and why you chose this one. **No section of anything public** reveals a security finding's detail: the report, the pull request, `open-items.md` rows, deviations, dropped fixes, the UX check, or a Factory log line naming a failing area.
