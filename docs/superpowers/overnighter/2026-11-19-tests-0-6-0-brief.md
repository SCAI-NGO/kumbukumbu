# Brief: the MCP suite and the specific UI run for 0.6.0

Hi, thank you for taking this one on! Kumbu² is a Markdown second brain served over MCP. It is written in C# (.NET 10), with a React/Vite web app, on MongoDB. 0.6.0 is feature complete and on staging as `v0.6.0-pre.4` (`63d3ca46`). It is the largest version so far. Its new features are:
- project memory and start-up skills;
- the link graph for agents;
- SVG;
- deep links;
- agents' uploads;
- Publish 2.0;
- who wrote what (`blame`);
- every file type and large files;
- reading CSV, HTML and XML;
- the command palette with favourites;
- windows over the notes;
- list filters;
- the console's completion and peek;
- the workspace (side panel, link completion, split view, templates).

This run tests it in two parts:
- **(a) an MCP suite:** scripted and deterministic, no model involved, speaking MCP to a stack of its own;
- **(b) the specific Playwright run for 0.6.0.**

**You report what you find; you don't fix the product.** A joint fix run follows, together with the security audit's findings.

Nobody is available to answer questions during this run, and that is intended: Chris has reviewed and approved the spec. Everything after it is yours, from the plan to the pull request. The decision rules below tell you how to settle what the spec leaves open.

## Open points for the run

All of these are yours to **decide**: settle each with the rules below and log it in the report.

1. **Bob as a write member.** The spec allows a vault of its own that Alice shares with Bob at `write`, through the app's invitation path: `POST /api/vaults/<vault>/invitations` with `role: "write"` and `confirm: false` after `confirmPassword`, then Bob accepts in the browser, as `web/e2e/global.setup.ts` (around lines 123–138) does for `Work`. Make it in its own spec's `beforeAll`, not in the global setup, so the 0.5.0 tests' vault lists stay as they are. Every invitation and every key costs a password check, 5 a minute per username. Don't add more users.
2. **The upload's HTTPS rule** (spec §3, settled). Over plain HTTP the link is spent and refused with 403 before the ticket is looked at, so test the tool's answer, its refusals and that 403, as the spec says, and list the rest as covered by `UploadTicketsTests`, `AgentUploadApiTests` and the hand test. Never change the rule or the stack's security settings.
3. **Start-up skills in the handshake.**
   1. `initialize` (`protocolVersion: "2025-11-25"`, `capabilities: {}`, `clientInfo`) with Alice's key: `result.instructions` names `project-memory` under the head "Skills for the start of every session".
   2. A skill marked `metadata: { kumbu-when: session-start }` that Alice wrote in her own vault is listed under the same head, after `project-memory` (system skills first, then the vault `Skills`, then other vaults: `src/Kumbu.Core/Skills/SkillInstructions.cs`). A skill lives at `/<vault>/_skills/<name>/SKILL.md` or in the vault `Skills`, its `name` equal to its folder's name (`SkillPaths.cs`, `SkillManifest.cs`), and the key must be able to read that vault.
   3. The same kind of skill, written by Bob in the shared vault, is listed as an ordinary skill, for Alice and for Bob alike (`SkillDirectory.cs`).

   The skills section is left out silently if it takes more than 5 seconds (`HandshakeInstructions.cs`), so a missing section is a finding to look at, not a pass.
4. **Large files.**
   - MCP: a file of at least 15 MiB + 1 byte (15,728,641 bytes; the bound is `15*1024*1024`, `AttachmentFormat.cs`) through the web API (`Api.putFile`): `cat` and `img` say it is kept but not read, and a download gives back the same bytes (compare checksums). That it is stored in chunks can't be seen from outside; don't try.
   - UI: about 100 MB through the web app's upload, with its progress bar. `setInputFiles` refuses a buffer over 50 MB: write the bytes to `testInfo.outputPath()` and pass the path.
   - Generate the bytes in the test, never as a committed fixture, and delete them afterwards.
5. **Hostile inputs for `csv`, `html`, `xml`** (spec §3):
   - a DTD is refused: `xml: <file> has a DTD, which Kumbu² doesn't process`;
   - the 10-second bound of `html` and `xml` holds: an XPath such as `//*[count(//*) > 0]` on a document of about 100,000 nodes, asserting the refusal `xml: '<xpath>' took longer than 10 seconds on <path>; narrow the XPath` and that it came within the bound plus a margin. `csv` has no time bound; it is bounded by the output limit;
   - `<script>` in a page is never run.

   The files go in through `Api.putFile` and are read through `sh`; each test asserts that the reader refuses or bounds its input.
6. **Deep links.**
   - The link in a write's answer opens the note for Alice.
   - The same link opens for Bob in the shared vault although he calls the vault something else: Bob renames it with `PUT /api/memberships/{id}/alias` (a session only, 30 a minute), and the test renames it back at the end.
   - A link to a removed note leads to "Not here" (`web/src/routes/DeepLink.tsx`) with "Search for it". Search is off on the stack, so assert that the search opens with the note's name in it, not that it finds anything.
7. **Publish 2.0** (`@publish`):
   - `--dry-run` lists what would go and what stays, with reasons;
   - a note marked unpublishable is never taken, and the walk doesn't go through it;
   - removing a note later takes it out of the copy, along with the notes the stored edges reach only through it (spec of Publish 2.0, "Notes behind it leave too");
   - `Mcp.create` needs the `publish` argument for `publish add`, and the reader allows 60 reads a minute per address, all from 127.0.0.1 here;
   - the reader's Contents list links land on the right heading.
8. **Discreet vaults** (spec §2): one `@serial` test per new view. Each runs in a session of its own and ends hidden. Count sign-ins and PIN entries against the rate limits, as in 0.5.0.
9. **Workspace tests already exist.** Run them, and add a test only where a step of the spec has none. Don't rewrite them.
10. **If time runs short**, write in this order:

    2. `@memory`, `@files`, `@readers`, `@publish`, `@deeplinks`, `@blame`;

## How to work

- **Subagent-driven**: one fresh subagent per tag task, then **an independent review per task by a fresh subagent**.
  - The review checks each test against its spec: every promise covered or listed as left out, and the assertions really check what "passes" says.
  - Re-review after each fix round until the verdict is clean. Two or three rounds were normal on earlier nights: self-reviewed units always still held real defects.
  - Subagents never merge, push or switch branches; you commit and push.
  - Subagents that write tests run only their own tag (`--grep @tag`) while another subagent runs anything heavy.
- **Test discipline:**
  - no `waitForTimeout`;
  - locators by role, label or text;
  - a test is only done once it has been seen to fail: break its assertion once, watch it fail, then restore it. Record this per tag.
- **Triage** (spec §5): run a failure again alone.
  - If it now passes, it is flaky: fix the waiting, never add a retry.
  - If it fails again, decide whether it is a **bug**, a **test** problem or **unclear**.
  - A bug gets `test.fail()` with `M-NN` or `F-NN` and a severity:
    - High: data loss or a security breach, such as a read-only member writing, a discreet vault showing, or a note left out of a publication showing in it;
    - Medium: a feature doesn't do what its spec says;
    - Low: wording, layout, or a target under 48 px.
- **The run at the end:** `pnpm -C web e2e:0.6.0` from a fresh stack **twice in a row**, with the same result both times. Record the times and counts. A test that differs between the two runs is flaky: fix it or take it out, and list it.
- **The web gate at the end:** `pnpm -C web test --run && pnpm -C web build` must be green. CI runs the rest; check it with `gh pr checks`.
- **Commits:**
  - after every task;
  - the message imperative and free-form, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`;
  - files staged by name, never `git add -A`.
- **Style:**
  - British English;
  - new files start with `// SPDX-License-Identifier: AGPL-3.0-or-later` (`#` in shell);
  - neutral names only: Alice, Bob, `Home`, `Work`.

## Deciding without Chris

When the spec leaves something open, or something unforeseen comes up, choose the option that satisfies these, in this order:

1. **Breaks nothing.** The product is unchanged, the web tests and build stay green, and the suite leaves no state behind.
2. **Reproducible from a fresh install.** This is Chris's reason for the whole setup: two runs give the same result.
3. **Deterministic.** This is Chris's reason for part (a): no model in the loop, exact assertions, nothing that depends on timing beyond a stated bound.
4. **Opens no new security hole.** A test never loosens a setting to pass.
5. **True to the spec.**
