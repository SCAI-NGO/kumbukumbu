### 1. F-15: an upload cut off halfway

Commits: `985073f` Upload a change cut off by a lost network once the network is back, without a reload (F-15); `971b10f` Wake the engines only when the network is back (F-15); `e9d4b3d` Keep a full check owed until one has looked at every path (F-15); `2e4dd24` Pin that checks are incremental again once a full one got through; `51750bd` Expect a full retry after a start the network cut off, in the attachments test; `3ee4fa1` Let only a full check settle the full check owed (F-15).

What it does, in two causes found one after the other:
- On a reconnect, the engines that were already running now check at once instead of sitting out their back-off (5 s doubling, up to 5 minutes). `971b10f` moves that wake into `MirrorEngines.reconnected()`, so the path taken when a vault's name changes doesn't loop on requests (the first review's must-fix).
- The first end-to-end run still failed `gaps #13` in both browsers. Its trace showed the second cause: the engines started only after the network went, the first check after coming back was cut off before it reached the new note, and every later check was incremental (what changed on the server, and paths it had heard of), so a note only this device had waited for the hourly full check or a reload. Now a full check stays owed until one has looked at every path (`e9d4b3d`), and only a full check settles it (`3ee4fa1`, the review's must-fix: an incremental check queued behind the cut-off full one cleared it).

Red: `store.engines.test.ts` "on a reconnect, send what waits at once…": `expected undefined to be '# New\n'`; the loop's test `expected 6 to be 2`; `engine.test.ts` "a start cut off by the network finds every file changed while closed at the next check": `expected undefined to be 'created while closed'`.
Green: `engine.test.ts` 44 passed; `engine.test.ts` + `engine.attachments.test.ts` 79 passed after `3ee4fa1`; the Eidolon core 32 files, 823 passed; web, the whole suite, 252 files, 4,643 passed.
Mutations: refresh waking too, the reconnect not waking, the owed flag never set, never cleared and cleared by any check: each fails a test, except `3ee4fa1`'s, which the reviewer showed with a probe of their own (two notes only this device had, never uploaded) and which has no test of its own on the branch.
End to end: `gaps #13` passed on desktop and Firefox after `e9d4b3d` (the debugging run), and in the final run (below). Its `test.fail` is gone.
Residual (review): while one path keeps failing with a network-type error, every retry is a full check (at most about 12 an hour); the engine was stuck on that path before too.

Changelog: **A change cut off by a lost network uploads once you're back.** A new note whose upload was cut off halfway no longer waits for a reload: it goes up as soon as the connection is back.

### 9. Heartbeat

Commits: `f82bd98` Ask the server every 15 seconds while the tab is visible, so a quiet network loss shows the offline

`/api/version` needs no session, so no idle session is kept alive. No server change.

`expected false to be true` (a second tab stayed online); `expected true to be false` (still connected);

passed, build clean; web `src/offline src/routes src/api src/hooks src/shell src/state` 104 files, 1233 passed.

4. **Item 9, the heartbeat: `GET /api/version` without the cookie**, every 15 seconds while visible and at once on `navigator.connection`'s `change`. Options: a frame on the socket (the server answers none), a request with the session (would have to be kept out of the idle clock), or the anonymous version route. Chose the version route: anonymous, cheap, never answered by the service worker, keeps no session alive and carries nothing. A miss counts as one failed request in `useOfflineMode`'s existing logic; to make that switch the mode at all, the first miss also takes this tab's socket down and sets the other tabs' sockets aside until an answer (a socket on a dead link can look open for minutes). Price: a server slower than 5 seconds gives one offline spell per slow spell. The offline design says so now (§"The heartbeat").
5. **A `503` from Kumbu² itself counts as reached.** One with `X-Kumbu-Version` no longer takes the app offline; a gateway's without it still does: only a server that can't be reached takes the app offline. The offline design's "What counts as unreachable" says so.
