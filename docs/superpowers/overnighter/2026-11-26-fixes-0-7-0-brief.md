## How to work

- **Subagent-driven** (`superpowers:subagent-driven-development`):
  1. A fresh subagent per fix: red test, green, commit locally, then every mutation on its own (break, watch it fail, restore with `git checkout -- <file>`).
  2. Then a spec-compliance and code-quality review by a fresh subagent.
  3. **For a security fix, also the fix review** of private spec §1, and the finding's proof test from a scratch copy. The fix review also checks the public commit message and test names against the publication rule below.
- Subagents never merge, push or switch branches. You commit and push.
- **Commit messages** are imperative and free-form, with no Conventional Commits prefix, and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. **On the public branches, a security fix's message carries no finding id, no "security" and no "fix S7-…"**: it says what the code now does.
- **Keep the public tree clean.**
  - Confidential notes, the proof tests and the measuring harness live in the private clone or a scratch copy outside every public worktree.
  - Public tests for security fixes assert function only, with ordinary inputs (private spec §1).
  - Stage files by name, never `git add -A`, `git add .` or `commit -a`.
  - In every public text, security ids appear in numeric order only: never in the order they were fixed, never with a time, a commit or a gate.
  - Before every public push, run `git diff origin/<branch> --stat` and check the files.
  - **Before anything public is pushed at the end** (the report, the pull request's description, `open-items.md`): a fresh reviewer gets the public texts and the private record's summary and checks that nothing points to a confidential finding (no method paragraph that only makes sense if something was found, no id paired with a file, feature or test).
- **Byte preservation:** every frontmatter write keeps every other byte.
- **The full gate**, as CI runs it, **twice**: at the point the private spec names, and at the end; the report gives gate 1 without naming what came before it. In between, run only the classes and files a fix touches. The gate, each line under the lock:

## Deciding without Chris

When a spec leaves something open, or something unforeseen comes up, choose the option that satisfies these, in this order:

1. **Breaks nothing.** Existing behaviour, data and interfaces keep working, apart from what the specs change. Prefer the reversible change.
2. **Gives nothing away.** Nothing about an unreleased weakness on a public branch.
3. **True to the spirit of the application.** Campy: plain notes and frontmatter, no new stores. Human-centric: the screen speaks of the person's wish. Offline: what needs a connection says so before, dimmed, not hidden. Honest: a button does what it says, and nothing is hidden quietly; Chris: honesty is part of the security architecture.
4. **Opens no new security hole.**
5. **True to the specs.**

If a question can only be answered by changing a spec's scope, don't guess: leave that part out and record it. For a security finding, it goes into `audits/2026-11-26-0.7.0.md`, section "Open for Chris", on the private branch. For the rest, into `docs/superpowers/open-items.md`. If a soft constraint makes a fix many times bigger, leave the fix out and record why rather than forcing it.

Log every decision you made this way, in the report and in the pull request's description under **Decisions made without Chris**, with the options you saw and why you chose this one. **No section of anything public** reveals a security finding's detail: the report, the pull requests, `open-items.md` rows, deviations, dropped fixes, or a Factory log line naming a failing area.
