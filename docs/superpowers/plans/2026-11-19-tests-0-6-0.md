# Plan: the MCP suite and the specific UI run for 0.6.0

Spec: `docs/superpowers/specs/2026-11-19-tests-0-6-0-design.md` (approved). Brief: `docs/superpowers/overnighter/2026-11-19-tests-0-6-0-brief.md`. Branch `feature/tests-0-6-0`, code under test `master` at `63d3ca46`.

**Goal:** an MCP project in the Playwright suite (`web/e2e/mcp/`), browser tests for 0.6.0's new UI, both tagged per feature, run by `pnpm -C web e2e:0.6.0` twice from nothing with the same result. The run reports; it doesn't fix the product.

**Architecture:** one Playwright config, a new browserless project `mcp` beside `desktop`, `phone`, `serial`, `serial-phone`. MCP tests use only the `request` fixture and `web/e2e/support/api.ts` (`Api`, `Mcp`); browser tests use `web/e2e/support/test.ts`. One stack (`web/e2e/stack/`), Alice and Bob from `global.setup.ts`, and per spec a vault of its own when Bob must write.

## Rules every task carries (copy them into each subagent's brief)

- **Read first:** this plan's task, the feature's spec named in the task, the PR description(s) named (`git log -1 --format=%b <sha>`), `web/e2e/support/{api,env,session,test}.ts`, `web/e2e/mcp/fixtures.ts` (after Task 1), and one existing spec of the same kind (`web/e2e/smoke/smoke.spec.ts` for browser tests, `web/e2e/mcp/handshake.spec.ts` for MCP tests).
- **Where the spec and the code on `master` disagree, the spec decides.** If the spec doesn't settle it, the finding is *unclear*.
- **Promise table first.** Each new spec file starts with a comment listing the feature spec's promises in scope for this run and, for each, the test that covers it or why it is left out (needs a device, a restart, search by meaning, another user, product change).
- **Assertions are exact or structural** (spec §3): the line or block an answer must contain, the refusal's exact text, and a state read back through a second call. "No error" alone never passes a test.
- **Isolation:** every test works below `/Work/<folder>/` (the `folder` fixture) with names of its own; wiki links resolve vault-wide, so put the folder into note names that others could share. Tests that look at global lists or discreet vaults are `@serial`. Every test cleans up what it wrote where a later test could see it (vaults, keys, publications, favourites, memberships, aliases).
- **No `waitForTimeout`;** locators by role, label or text; `data-testid` only where nothing else finds the element, each one listed in the task's report.
- **Seen to fail:** break one assertion per tag, run, see the failure, restore. Report the break and the failure line.
- **Scope every list:** an MCP test is never `@serial` (the `mcp` project has no serial phase), so it scopes every vault-wide answer to what it made: a unique random `--tag` for `calendar` (which takes a whole vault), `graph --orphans|--hubs|--unresolved /Work/<folder>`, `publish ls /Work/<folder>`, `rg … /Work/<folder>`.
- **No secrets in a failure's output:** a failed `expect` prints its whole received value. Before asserting on an answer that holds an upload URL, a curl line, a reader link (`link (shown once): …`) or a key, pass it through `redact()` from `web/e2e/mcp/fixtures.ts`; assert a URL's parts (origin, path prefix, token length), never the raw value.
- **One screenshot per tag and viewport** in browser tests: `shot(page, testInfo, "<tag>")` (spec §4), taken where the feature is on screen and no secret is.
- **Triage** (spec §5): rerun a failure alone. Passes now → flaky, fix the waiting, never a retry. Fails again → *bug* (`test.fail()` with an id and severity, the finding's own assertion message starting `F-NN:`/`M-NN:`), *test* (fix the test), or *unclear* (same as bug, marked unclear). Ids: UI findings continue after 0.5.0's F-01 to F-04, so they start at **F-05**; MCP findings start at **M-01**. The coordinator keeps the register: write `F-xx`/`M-xx` placeholders and say so in your report; the coordinator assigns the numbers before committing.
- **Severity:** High: data loss or a security breach (a read-only member writing, a discreet vault showing, a left-out note showing in a publication). Medium: a feature doesn't do what its spec says. Low: wording, layout, a target under 48 px.
- **Running:** the coordinator keeps one stack up (`E2E_PROXY_CA=/root/.ccr/ca-bundle.crt web/e2e/stack/up.sh`, then `pnpm -C web exec playwright test --project=setup`). The saved sessions die after 30 minutes idle or 12 hours (`Sessions.cs:31-32`), and the setup can't run twice on one stack: when tests fail with 401 or land on the sign-in page, tell the coordinator, who runs `down.sh`, `up.sh` and the setup again. Run only your own tag, never the whole suite and never `run.sh`/`up.sh`/`down.sh`:
  - MCP: `cd web && pnpm exec playwright test --no-deps --project=mcp --grep @tag`
  - browser: `cd web && pnpm exec playwright test --no-deps --project=desktop --project=phone --grep @tag`
  - serial: `cd web && pnpm exec playwright test --no-deps --workers=1 --project=serial --project=serial-phone --grep @tag`
  - type check: `cd web && pnpm exec tsc -p e2e --noEmit`
- **Rate limits:** Alice's and Bob's password checks (every `confirmPassword`, every `Mcp.create` whose password window has closed, every invitation) go through `reservePassword`; sign-ins and PIN entries through `freshSession`/`enterPin`. 5 a minute each. Reader reads through `reserveReaderRead`.
- **Never:** touch `src/`, `web/src/` (apart from `data-testid`), `compose.yaml`, `compose.build.yaml`; loosen a security setting; add a dependency; commit, push or switch branches (the coordinator commits); log or assert a secret (passwords, recovery keys, API keys, invitation codes, upload links, reader codes).
- **Style:** British English; new files start with `// SPDX-License-Identifier: AGPL-3.0-or-later`; neutral names (Alice, Bob, `Home`, `Work`); match the surrounding test code's idiom and comment density.
- **Report back:** files changed, the promise table, the run's command and counts, the deliberate break and its failure line, findings (id, severity, kind, test, steps, expected, actual, likely place in code), `data-testid`s added.

## Task 4: `@readers` (MCP)

Spec `2026-11-19-reading-csv-html-xml-design.md`; PR #260 (`63d3ca4`). File `web/e2e/mcp/readers.spec.ts`. Files go in through `Api.putFile`, are read through `mcp.sh`.

- `csv`: shape (separator, rows, columns, header), the first rows as a table, rows/columns/range `B2:D20`, tab-separated output, `;` recognised. No time bound; bounded by the output limit (a large CSV's answer is cut, with the spec's wording).
- `html`: a CSS selector's text, a table as a table, an attribute (`href`); a page with `<script>`: the script is never run (its text may be printed as text; nothing executes, nothing is fetched: assert the answer is the selector's text and that a `<script>` that would alter the DOM didn't alter what `html` reads).
- `xml`: XPath with namespaces; a DTD is refused with exactly `xml: <file> has a DTD, which Kumbu² doesn't process`.
- The 10-second bound: a document of about 100,000 nodes and `//*[count(//*) > 0]` → exactly `xml: '<xpath>' took longer than 10 seconds on <path>; narrow the XPath`, measured to come within 10 s plus a margin (assert under 20 s); the same for `html`: a selector the spec names as expensive (`:nth-child()`, `:only-child`, `*-of-type`, `Html.cs:42-43`), e.g. `li:nth-last-of-type(n+1)` on about 100,000 sibling `<li>`, → exactly `html: '<selector>' took longer than 10 seconds on <path>; narrow the selector or the page` (`Html.cs:101`), under 20 s.
- Each test asserts the reader refuses or bounds its input. Delete the files afterwards.
