# Plan: the security review of 0.7.0

Spec: `docs/superpowers/specs/2026-11-26-security-audit-0-7-0-design.md`. Brief: `docs/superpowers/overnighter/2026-11-26-security-audit-brief.md`. Branch `audit/0-7-0-security`. The code under review is `2fee5ad2` against `v0.6.0`.

This plan is public. It names areas, files, methods and time budgets, and never a finding. The run finds and reports; it fixes nothing, merges nothing, tags nothing and deploys nothing. Blue team only: code review and behaviour tests of our own code, nothing against a live system.

## Rules that hold throughout

- **Two repositories, two branches.** Public: `audit/0-7-0-security` (this plan, later `docs/superpowers/open-items.md` and the report, nothing else). Private: `SCAI-NGO/kumbukumbu-security`, branch `audit/0-7-0` cut from `master` (`audits/` only). No force-push; a mistake comes out with `git revert`.
- **If the private repository can't be reached:** the confidential findings go nowhere public; they go in full into the session's final message, and the public report says only that this happened, with ids and severities.
- **Worktrees.** Every reviewer works in its own worktree of `2fee5ad2` under `/home/user/audit-scratch/<name>`, outside the public clone, with its own build and `pnpm -C web install --frozen-lockfile`, made only once it has a test to run (a reviewer that only reads needs neither). Nothing is committed from a worktree; it is removed once its tests and report are in the private clone. Reviewers `cd` into their worktree and use `git -C <path>`; they never merge, push or switch branches. The controller alone commits and pushes.
- **One heavy run at a time.** Every build, test run and measurement of every agent runs as `flock /tmp/kumbu-heavy.lock -c 'timeout 20m <command>'` (60 minutes for an end-to-end run), with `MSBUILDDISABLENODEREUSE=1`, `DOTNET_CLI_TELEMETRY_OPTOUT=1` and `-nodeReuse:false` on every `dotnet build`. At most four area reviewers at a time.
- **Tests.** Filters carry the namespace (`--filter-class "Kumbu.Server.Tests.Api.SimilarApiTests"`); the baseline is batched (several `--filter-class` or `--filter-namespace` in one call). One MongoDB container (`mongo:9`, single-node replica set, capped log) serves every reviewer through `KUMBU_TEST_MONGO`; `TESTCONTAINERS_RYUK_DISABLED=true`. After a container restart: start `dockerd`, `docker start kumbu-test-mongo`, wait for the ping and the primary, then resume the stopped agents with a message saying what was lost.
- **A real browser** only where a promise can only be shown in one: `pnpm -C web e2e --grep "<tag>" --grep-invert "@search"`, under the lock with `timeout 60m`. Never `E2E_SEARCH=1`, `pnpm e2e:0.7.0` or `pnpm e2e:0.7.0:tensorx`. The browsers are installed first (`pnpm -C web exec playwright install --with-deps chromium chromium-headless-shell firefox`); the stack is the run's own (`web/e2e/stack/up.sh`, Docker with buildx, else `E2E_STACK=dotnet`; behind the TLS proxy `E2E_PROXY_CA=<the proxy's CA file>`) and never leaves the container. A run that reports no passed test counts as not run; `run.sh` deletes `web/e2e/.results` on exit, so the evidence is kept from the console output. At most two browser runs in the whole review, decided by the controller and scheduled after the baseline.
- **Server tests fake the clock in 2037**, because MongoDB's TTL expires sessions by the real clock. The PDF sidecar is unchanged since 0.6.0: its install and tests are skipped, except for its advisory lookup, whose output must name the sidecar's own packages.
- **Never a real host:** not staging, production, TensorX, huggingface.co, or GitHub beyond reading pull requests. Allowed: the read-only advisory lookups (`pnpm audit` at the root, `pnpm -C pdf audit --ignore-workspace`, `dotnet list package --vulnerable --include-transitive`, GitHub's advisory database); one that fails behind the proxy is recorded, not guessed.
- **Tools** are installed without asking and noted in the report; no dependency is added to the project.
- **Evidence.** A weakness counts once it is shown: by a behaviour test that asserts what the code should do, beside a positive control, or by a precise trace with `path:line`. A suspicion that couldn't be shown is reported as a suspicion, with what would show it. Test inputs are the ordinary ones of spec §1. Measurements are taken in Release, beside a control under the same load, with the load average stated.
- **Rating.** The scale of the 0.4.0 spec §3: impact times reachability, the higher level when in doubt, with the doubt written down. For the browser (spec §3): a weakness that needs the device's disk without the password is rated by what it gives that holder beyond guessing the password; one that needs script running in the origin by what it adds to what such a script can do anyway while the copy is unlocked, ADR 0021 being the one place where 0.7.0 promises more. Reviewers of A1, A2 and C and every second reviewer get this rule.
- **Where a finding goes** (spec §4). Medium and higher: the private file only. A Medium-or-higher candidate that a second review refutes or rates down stays in the private file, with the verdict. A Low beside a confidential finding stays private too if describing it would point to that finding. The other Lows go into the public report in full.
- **The publication rule.** Nothing about a Medium-or-higher weakness reaches a public branch, a commit message, a pull request or the Factory card. A test that shows one lives only in a worktree and the private clone. Public staging is by file name, never `git add -A`; before every public push, `git diff origin/audit/0-7-0-security --stat` shows only the files meant. The public texts never name an id, finding or decision of the offline mode's scoped review.
- **Deciding without Chris**, in this order: gives nothing away; defensive only; honest (rate up when in doubt, and write the doubt down); true to the spec. A scope question is left out and recorded in `docs/superpowers/open-items.md`, by the finding's id or, without one, as "Security review 0.7.0: a scope question, see the private file". Every such decision is logged in the report and in the public pull request.
- **Style.** British English; neutral names (Alice, Bob, Carol, Dana, `Home`, `Work`). Commit messages imperative and free-form, ending with `Co-Authored-By: Claude Mythos 5.2 <noreply@anthropic.com>`; both pull requests' descriptions end with `🤖 Generated with [Claude Code](https://claude.com/claude-code)`. Test files start with `// SPDX-License-Identifier: AGPL-3.0-or-later`. No secrets in logs, assertions or reports.

## Phase 1: the area reviews (budget: to hour 5)

One fresh reviewer per area, in this order, at most four at a time: A, B, F, C, then D, E, I, H, G as places free up. Each gets: its area and files (below), the spec's trust boundaries for it, the classes of the 0.4.0 spec §4 step 2, the crossings it owns or touches, the reading list of the brief (the feature's spec, the security review in each pull request's squash commit, the ADRs, `docs/security-architecture.md` at `2fee5ad2`), the earlier scoped review's points from the private file so that none is reported as new, the lock's command and the rules above.

Each reviewer:

1. reads, and so knows what earlier reviews accepted and what they recorded as fixed;
2. models the area: every entry point new or changed since `v0.6.0`, the boundary each touches, what is promised;
3. reviews every entry point against the classes: authentication and authorisation for every role and credential kind, path handling, injection, outbound requests, resource use on bounded oversized and nested inputs, races, information leaks (existence, timing, error texts, logs), cryptography where keys, wraps or derivations are new, request forgery and origin checks, the CSP and response headers;
4. shows each candidate by a behaviour test beside a positive control, or by a trace;
5. checks its crossings and says "checked" or "not reached" for each;
6. writes its report (candidates with the fields of spec §4, what it checked and found sound, suspicions not shown) and its tests into the private clone's `audits/2026-11-26-0.7.0/`, and commits nothing.

A design decision (spec §8, the ADRs) is no finding unless it breaks a promise of `docs/security-architecture.md` or of the offline design §4; one that looks unsafe anyway is reported with "needs a decision from Chris". A point an earlier review accepted is not new; one recorded as fixed that isn't is new. A weakness in code older than 0.7.0 that no new feature reaches goes under "Older than 0.7.0", counted apart. A vulnerable dependency is a finding, rated by whether Kumbu² reaches the vulnerable code.

## Phase 2: the second reviews (rolling, budget: to hour 6.5)

Every candidate of Medium or higher, and every Low, goes to a second fresh reviewer who gets the claim (title, place, the behaviour claimed, the test) and the code, not the first reviewer's reasoning, and who tries to reproduce and to disprove it. It may confirm, rate up or refute; a Low is never rated down except to "refuted". A claim first made by a second reviewer gets a third, who gets only the claim. Where two disagree on severity, a third reviewer or a measurement settles it. Ids are `S7-NN` and `L7-NN`, going on after the highest of each in the private file.

**A High or Critical finding, as soon as a second review rates it so** (spec §6, on the higher rating at once): written in full into the private file and pushed, with the private pull request opened if it isn't yet; a `PushNotification` reading "Security review 0.7.0: a High (or Critical) finding, S7-NN, details in the private pull request"; the card moved to Waiting for Chris with the id, the severity and "Fix S7-NN now? Recommendation: yes, details in the private pull request". Without notifications, the pull request and the card are the signal. The run carries on and fixes nothing.

## Phase 3: the severity check (budget: 30 minutes)

One fresh reviewer measures every resource finding of Medium or higher against a control: what another user sees while the slow calls run, in Release, under the lock, with the load average stated. Where a doubt towards High remains, or the budget doesn't reach a finding, the measurement that would settle it is written down and the finding keeps the higher rating.
