# Publish v1, one note behind a link: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (or, if it is unavailable, emulate it with the plain Agent tool). One fresh subagent per task, then a spec-compliance review and a code-quality review, each by its own subagent. Subagents do red, green, commit and mutations; they never merge, push or switch branches. The controller pushes, with `git push -u origin feature/publish`. Steps use checkbox (`- [ ]`) syntax.

**Goal:** The owner of a vault publishes one note as a filtered, encrypted snapshot behind a secret link that anyone can read without an account. She sees when the copy is older than the note, updates it under the same link, and withdraws it. Agents do the same through `sh publish`, only with a "May publish" right given on purpose. Notes and folders can be marked unpublishable.

**Architecture:** A pure filter in Kumbu.Core makes the fair copy. The server strips image metadata itself, with no new library. A 160-bit share code gives, through HKDF, a lookup id and a reader key. Each publication is a mini vault: a random publication key seals the copy and its files, and two slots hold that key. One slot is sealed under the reader key. The other is the vault's own sealed publishing record, under the vault key, which also holds the code, the snapshot facts, the unpublishable marks and an append-only log. `EncryptedNoteStore` withdraws or refuses in the same transaction as a removal or move. An anonymous reader endpoint and a minimal reader page with its own entry and a strict CSP serve the copy. The web app gains the Publish dialog, a bar above published notes, the overview, the marks and the right.

**Tech stack:** .NET 10, minimal APIs, MongoDB transactions, xUnit v3 on Microsoft.Testing.Platform, Testcontainers with MongoDB; React with Vite, TanStack Query, react-markdown, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-05-publish-design.md` ("spec §n"), reviewed and approved by the maintainer. Don't edit it. Where the spec leaves a choice to the builder (spec §7), the table "Decisions this plan takes" decides it. Follow the table and don't reopen the choice.

**Line anchors** are from `e8be7ad` (`master`; `feature/publish` adds only documents on top). They may drift as you work; the sense counts.

## Security boundary

This work **touches crypto, credentials, anonymous endpoints and rights**. It adds a key hierarchy (share code, lookup id, reader key, publication key), a sealed vault-side record, a new right sealed into credential slots and metas, a new anonymous endpoint with a cookie of its own, a page on the web app's origin that strangers open, and a hook in every removal and move. **The repository's security-review expectation applies**, as in the read-only console and rename runs: Task 16 has a fresh subagent review the whole branch against spec §5 and spec §2's anti-goals; every finding goes in the report, fixed or not; the pull request says a review applies. **Not touched, on purpose:** `CallerMiddleware`'s refusal of the session cookie on `/mcp`, sessions and their password window (only used), pins, the vault keys' own handling in re-keying (one more collection is resealed, nothing else), `_loading`.

## Decisions this plan takes

The spec leaves these to the builder (spec §7) or doesn't reach them. Each was checked against the code at `e8be7ad`.

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | PDFs in v1 (spec §3.4) | **Not published.** An embedded PDF becomes plain text (its file name), and the dialog and `sh publish add` say "PDFs are not published yet". | The server has no PDF library (`src/Kumbu.Server/Kumbu.Server.csproj:8-15`). The sidecar has `pdf-lib` only as a dev dependency (`pdf/package.json:27`). Taking metadata out reliably means also handling incremental updates, object streams, page-level XMP and embedded files, and that isn't done in one night without a new dependency. |
| 2 | The tag rule (spec §3.3) | Outside code, a `#tag` **stands alone** when nothing but whitespace and other tags follows it to the end of its line. Standing alone, it goes, with the whitespace before it. Otherwise only its `#` goes. A line left empty by this goes too. | "Done. #todo #later" reads "Done.", and "We discussed #routing today" reads "We discussed routing today". |
| 3 | The title (spec §3.2) | If the first non-blank line after the frontmatter is an ATX level-1 heading (`# …`), its filtered text is the title, and the line goes from the body, with one blank line after it. Otherwise the title is the note's file name without `.md`. | Spec §6 shows "Questions on routing" for `Questions.md`, whose first line is `# Questions on routing #routing`. |
| 4 | What else the filter removes | Raw HTML tags go, with their text kept, outside code. Reference-style link definitions whose destination isn't `http:`, `https:` or `mailto:` go too, and their uses become plain text. Links with any other scheme (`obsidian://`, `file:`) become plain text. | The reader API's JSON carries the stored Markdown, so "not rendered" (spec §3.3) isn't enough: `<a href="Private/Plan.md">` or `[p]: Private/Plan.md` would carry a path out (spec §2's first anti-goal). |
| 5 | Where the marks live (spec §4) | In the vault's sealed publishing record, beside the publications. | One document per vault, resealed by a re-key and rewritten in the same transaction as a move. `VaultMeta` changes are delicate (rename plan, corrections 6 and 7). |
| 6 | The vault-side slot (spec §4) | The publication key is a field of its entry in the sealed record. | The record is sealed under the vault's content key, so the vault key reaches it, and a re-key reseals it with the record. No slot document of its own is needed. |
| 7 | The read-time owner check (spec §3.7) | The reader slot seals the publication key **and the owner's user id**. The endpoint opens it, checks `users.active`, and only then opens the copy. | `VaultDocument` names no owner (`Vaults/Documents.cs:8-43`). Spec §4's "does not name its user in the clear" holds. |
| 8 | History (spec §3.11) | Each publish, update and withdrawal adds an entry to the record's append-only `Log` (note path, time, who, reason) **and** a plain vault event (`note-published`, `publication-updated`, `publication-withdrawn`) holding only the log entry's id. The owner's text is resolved through the record. These kinds are in neither `MemberKinds` nor `VaultWide`, so members never see them. | Events are plain documents and may hold no path (`Sharing/VaultEvents.cs:12-17`). A path sealed into the event itself would stop opening after a re-key. History is an audit log: nothing is hidden, duplicates included. |
| 9 | The password (spec §3.5) | **Publish:** the body's `password` is checked as an invitation's is. Without one, the password window must be open (`Security.RequirePasswordWindow`). **Update:** behind `PasswordWindowMetadata`, so the web app's existing prompt asks only when the window is closed (`web/src/api/client.ts:76-93`). **Withdraw and marks:** session only, no password, as reducing access always is. | "One click" for Update (spec §2); the dialog asks for the password unless the window is open (spec §3.5). |
| 10 | The dev token | It can't publish, and it can't remove or move a published note. | Spec §3.7 lists who may remove one: the owner's session, her credential with "May publish", her device. The dev token is none of them. |
| 11 | The reader cookie (spec §3.12) | `kumbu_reader`, whose value is the normalised code. HttpOnly, Secure, SameSite=Strict, `Path=/api/s`, a session cookie (no Max-Age). | It grants exactly that publication. `Path=/api/s` doesn't path-match `/api/session` (RFC 6265 §5.1.4). |
| 12 | The overview (spec §3.11) | A section "Published notes" in Settings. | Beside "Shared vaults" (`web/src/routes/SharedVaultsSection.tsx`). |
| 13 | Answers of the reader endpoint | Wrong, malformed, withdrawn and deactivated-owner codes: one identical 404. The server switch: a 404 of its own sentence and type `publishing-off`. | The switch is a fact about the server, not about the link. |
| 14 | An attachment the copy holds is removed or changed | Nothing is withdrawn; the copy reads "older than this note". | The copy holds its own bytes (spec §3.4); a snapshot changes only when the owner says so. |
| 15 | Update | It keeps the code, the lookup id and the publication key, reseals the copy and replaces its files. The copy document's `at` stays the first publication's time. | Spec §3.1. |
| 16 | The console (spec §3.9) | `publish` goes into `ConsoleApi.Allowed`, plus a gate: a `publish` stage whose first operand isn't `ls` is refused. | `ConsoleApiTests.cs:231` wants every known command in exactly one of `Allowed` and `Refused`. |
| 17 | The reader page's technology (spec §3.12) | A client-rendered entry of its own, `web/s.html` → `web/src/reader/`, using react-markdown without raw HTML. The server stores Markdown only. | `MarkdownView.tsx` imports the app (`web/src/note/MarkdownView.tsx:6-19`), so it can't be reused. |
| 18 | The snapshot time on the reader page | Formatted in the reader's own time zone, `en-GB`: "Snapshot of 5 Nov 2026, 14:32". | Nothing of the owner's time zone is sent. |
| 19 | `rm` of a folder above a published note (spec §3.7) | `rm` takes notes and empty folders only (`Sh/Manual.cs:32`). A folder above a published note goes note by note, and each note meets the rule. `restore --checkpoint`, which trashes and moves notes in one batch, meets it too. | Same store hook. |

Claude's calls in the spec, to be listed in the pull request: §3.4 (stale includes attachments), §3.6 (marking an attachment withdraws the whole publication), §3.7 (account deletion withdraws at once, also in the closing period; deactivation hides, reactivation shows), §3.10 (members' view enforced by the server), §4 (the vault id in the clear).

## Review focus

Each has its test in the task that owns the code.

1. A `[[link]]` or `#tag` inside a code block or inline code stays as written. Outside code, no form of link leaves a path: not a reference definition, raw HTML or an embed of another note (Task 1, `No_path_leaves` and `Code_stays_as_written`).
2. An embed of an attachment that is unpublishable, missing, a PDF, or whose bytes don't parse: plain text, no bytes stored, named in the result (Task 6, `An_embed_it_cannot_copy_is_plain_text_and_stores_no_bytes`).
3. A reload after the page removed the fragment opens the copy through the cookie. A withdrawn publication's cookie answers as a wrong code and is cleared. The cookie never reaches `/api/session` (Task 10, `A_reload_reads_with_the_cookie_alone`; Task 11, `reloads_with_the_cookie_when_there_is_no_fragment`).
4. `mv` of a folder holding a published note and an unpublishable sub-folder: the link stays, the mark follows, nothing is withdrawn. Then a key without the right moving the note into that sub-folder is refused, and nothing moves (Task 7, `A_folder_move_keeps_the_link_and_the_mark`).
5. An agent with "May publish" on `Work` and only `write` on `Gartenarbeit` is refused on `Gartenarbeit`. A credential sealed before this release reads as "may not". A member-derived slot with a planted flag never may (Task 4 and Task 6).

**Interfaces:** produces

```csharp
namespace Kumbu.Core.Publishing;

/// The copy as stored: Files[n] is what "![name](f/n)" in Markdown shows; Plain names the embedded attachments that
/// became plain text, distinct, in order of first appearance.
public sealed record FairCopy(string Title, string Markdown, IReadOnlyList<VaultPath> Files, IReadOnlyList<string> Plain);

public static class FairCopies
{
    public const string FilePrefix = "f/";

    /// attachment: the attachment an embed's target names (by LinkResolver's rules), or null.
    /// mayCopy: whether that attachment goes with the copy (an image, not unpublishable, its bytes usable).
    public static FairCopy Make(VaultPath note, string content, Func<string, VaultPath?> attachment, Func<VaultPath, bool> mayCopy);
}
```

**The rules, in this order**, outside code (fenced blocks with backticks or tildes, inline code spans, indented code blocks as `TagReader` reads them), which stays byte for byte:

1. Frontmatter goes.
2. The title, per decision 3.
3. `%%…%%`, inline or across lines, and `<!-- … -->` go. An unclosed `%%` runs to the end of the note.
4. Raw HTML tags go, their text stays. Autolinks (`<https://…>`, `<mailto:…>`) are not HTML.
5. Tags, per decision 2.
6. Wikilinks `[[T]]`, `[[T#H]]`, `[[T|A]]`, `[[#H]]` become: A if there is an alias; for `[[#H]]` H; else T's last segment without `.md`. The subpath never shows.
7. Embeds:
   - `![[T]]` or `![[T|300]]`: if `attachment(T)` is p and `mayCopy(p)`, it becomes `![<p's file name>](f/<n>)`; otherwise the plain text of rule 6, which for an attachment is its file name with its extension.
   - Markdown links to vault targets (those `MarkdownLink.Parse` returns) become their text without brackets.
   - `![alt](dest)` to a vault target: copied as `![alt or file name](f/<n>)`, else the alt or, if empty, the file name.
8. Reference-style links, per decision 4.
9. Remote images `![alt](http(s)://…)` become `[alt](url)`, or `[url](url)` with an empty alt. Web links (`http`, `https`, `mailto`, autolinks) stay as written. Other schemes become their text.
10. A line that held something and is left empty by a removal goes with its line break; blank lines that were blank stay.
11. n counts from 0 in order of first appearance, and the same attachment twice gets one n.

**The minimal EXIF** (TIFF, big-endian, IFD0 with the orientation alone): `4D 4D 00 2A 00 00 00 08 | 00 01 | 01 12 00 03 00 00 00 01 00 0N 00 00 | 00 00 00 00`, 26 bytes. In JPEG it goes in an APP1 after `Exif\0\0`, in PNG as an `eXIf` chunk, and in WebP as an `EXIF` chunk. Only when N ≠ 1.

**What is kept:**

- **JPEG:** SOI; APP0 only if `JFIF\0` or `JFXX\0`; APP2 only if `ICC_PROFILE\0`; APP14 only if `Adobe`; every non-APP, non-COM segment, and the entropy-coded data after each SOS, as they are; EOI. Every other APPn and every COM goes, also between scans, and so does anything after EOI. The minimal APP1 goes right after SOI and the kept APP0.
- **PNG:** the signature, then only these chunks, in their order:

  - colour and size: `tRNS cHRM gAMA iCCP sBIT sRGB cICP mDCV cLLi bKGD pHYs hIST`;

**The rule:**

1. **Marks follow:**
   - a note mark M that the batch moves to T becomes T;
   - a folder mark M becomes N when three things hold: the batch moves at least one note or attachment from under `M/`; every one it moves from there lands under one `N/` with the same rest; and nothing of the vault stays under `M/` after the batch. Folder markers count as attachments here.

   - P moved to T: if the new marks cover T, withdraw, reason `unpublishable`; otherwise `Note = T`;

5. **Writes:** copies deleted, the record rewritten with its log entries, events recorded, all in the session. A log entry names the note by the path it had before the batch.
