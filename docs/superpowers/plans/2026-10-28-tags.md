# Tags Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Read tags as Obsidian does (frontmatter `tags` and inline `#tags`), list them with `tags` in `sh`, narrow `rg`, `semsearch` and `board` with `--tag`, serve them over REST, and show and filter by them in the web app.

**Architecture:** A pure extractor and matcher in `src/Kumbu.Core/Tags/`; a filter over `IReadOnlyList<Note>` that every reader shares (so `--checkpoint` works for free); a `tags` reader in `sh`; thin REST endpoints; chips and a filter in the web app. Nothing is stored: tags are read from the notes the unlocked vault holds in memory.

**Spec:** `docs/superpowers/specs/2026-10-28-tags-design.md`

## Global Constraints

- British English, SPDX headers, no organisation names; examples use `/Work`, `#research`, `#project/kumbu`.
- A tag is case-insensitive and nested: asking for `project` covers `project` and `project/…`, never `projects`.
- An asked-for tag no note below the scope carries is an error sentence, never an empty result: `no note below /Work carries #reserch; 'tags /Work' lists the tags`.
- Tags never change a note's text; no writing tools, no MongoDB index.
- Build and test: `dotnet test --solution Kumbu.slnx`; `pnpm -C web test --run`; `pnpm -C web build`.

## Review Focus

- False positives: headings, URL fragments, `#123`, `word#tag`, code (fenced, indented, inline), comments, the frontmatter itself. Task 1's table.
- Indented code versus nested list items (`    - #tag` under a list item is a tag, not code). Task 1.
- Performance on a large vault: measured in Task 2, a cache only if needed.
