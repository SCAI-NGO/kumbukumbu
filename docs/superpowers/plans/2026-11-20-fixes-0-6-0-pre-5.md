## Task 2: F-C, the reader opens a code from a changed hash (spec §2.2)

**Files:**
- Modify: `web/src/reader/Reader.tsx:464-500` (`Reader`)
- Test: `web/src/reader/Reader.test.tsx`

**Design:** a `hashchange` listener in `Reader`, added once in an effect of its own. On a change, it reads `location.hash`. It ignores an empty hash and every in-copy address: `#/<id>` (the bundle's note, `noteInAddress`, `Reader.tsx:235`; set with `pushState`, which fires no `hashchange`, but back and forward may), `#kn-<id>…` (`noteLink`, `Reader.tsx:58`), `#n<id>` anchors, (the three patterns `^#\/\d+$`, `^#kn-\d+(\/.*)?$`, `^#n\d+$`; no element-id filter: the reader renders no on-page anchor that changes the hash, `Reader.tsx:180-195`). Anything else is a code, taken as the first load takes it, `location.hash.slice(1)` without decoding: it is taken out of the address at once with `history.replaceState(null, "", location.pathname + location.search)` (as `Reader.tsx:483`), the state is set to `{ kind: "loading" }` and `wrong` to false, so the previous copy and its code leave the tree, and then `read(readWithCode(code), true)`. `read`'s `latest` counter already drops a late answer to an earlier request. The first-load effect (`Reader.tsx:477-490`) stays as it is. The listener is `useEffect(() => { const on = …; addEventListener("hashchange", on); return () => removeEventListener("hashchange", on); }, [])`, with no once-guard: StrictMode adds, removes and adds it again, and an unremoved listener would outlive the component across the test file's renders.

Third case: with a copy shown and a new code whose answer is held back (the file's `deferred()` helper, `Reader.test.tsx:60`), the old copy's title is gone and "Loading …" shows, and `replaceState` ran before the POST (as `Reader.test.tsx:88` checks).
