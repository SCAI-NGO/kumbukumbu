# Kumbu² — Security Architecture and Encryption at Rest

**Audience:** a technical decision-maker: whoever decides whether to run a Kumbu² instance for others, or whether to keep personal notes on one.
**Scope:** the code as built for release v0.2.0: accounts, API keys, the web app and the MCP endpoint, with the fixes to the recovery key file, HSTS, the CSP, and what a password change and a recovery revoke; external embedding providers (§5.5), API-key expiry, deletion of vaults and accounts, optional MongoDB authentication and pinned build inputs; connections, through which apps such as claude.ai sign in with OAuth 2.1, with Kumbu² as their authorisation server (§6), and new keys for an account and its vaults after a recovery or on request (§3); and v0.2.0's Obsidian sync (pairing codes, device keys, the version list and change hints, §6), export of vaults and checkpoints as ZIP and import from one (§6, "Export and import"), the welcome vault, deletion for privacy requests with a receipt and a list of deleted users (§6), automatic updates of the web app (§7), the activity of a vault and search in earlier versions (§4), and reading a checkpoint without restoring it (§4). Everything that is only planned is in §9, "What comes next", and nowhere else.
**How to check it:** every key claim names the file (and, where useful, the line) in `src/` that implements it. The project is open source (AGPL-3.0-or-later). No external security audit has been done; the reviews so far were part of development.

## 1. Summary for a decision-maker

Kumbu² is a self-hosted Markdown notes server. People use it through a web app, and can sync a vault with Obsidian on their own devices through a paired device key (§6, "Device pairing and sync"). AI agents and apps reach it in one of two ways, each made by the person for chosen vaults and rights: local agents (Claude Code and other MCP clients) with an **API key** on `/mcp`; apps that sign in with OAuth (claude.ai on the web, in the desktop app and on the phone, and others) through a **connection**, a connector URL of its own that the person pastes into the app and authorises there once, on Kumbu²'s consent page. Notes are personal: there is no sharing between users.

**What it protects well.** Everything in the database is encrypted: note text, its history, the trash, folder and file names, vault names, the search vectors and checkpoints. Each vault has its own random key, and that key is stored only *wrapped*: by its owner's user key, by each API key given that vault, and by each live token of a connection given it. The user key in turn is stored only wrapped by the owner's password, recovery key and web sessions. A database dump, a stolen backup or the disk of a compromised hoster shows no readable content and no paths, only metadata such as usernames and display names, the admins' notes on invitations ("for Alex"), sizes and times. Admins manage accounts but cannot read notes, cannot see vault or note names, and cannot reset passwords. After a suspected compromise a user can give their account and every vault new keys ("Re-encrypt my vaults"), and a recovery does so by itself. The vaults are re-keyed one after another in the background; once a vault's re-keying has finished, an old password, recovery key or API key reaches nothing written to that vault afterwards, apart from documents left damaged. Dev-token vaults are not covered (§3).

**What it does not protect against.** It is *encryption at rest*, not end-to-end encryption. To search, render and edit, the server decrypts a vault into memory while it is in use, and keeps it there until no caller has used it for 15 minutes (checked once a minute, so up to about 16). Signing out does not lock it, and an agent that keeps using a vault keeps it unlocked. Whoever controls the running server — the operator — can therefore read what is in use, and could change the server to capture passwords. The AI provider of a connected agent sees whatever that agent reads; for an app connected through a connection, the provider also holds the refresh token, key material to that connection's vaults (§2, §8). A vault that uses an external embedding provider (off by default; per vault by its owner's choice, or for the vaults whose owner never chose if the admin makes that provider the instance's default) sends the text of its sections and its search queries to that provider (§5.5). An export, and the notes the Obsidian plugin keeps on a device, are plain text outside the server (§2). These limits are by design and stated, not hidden.

**What that means for whoever runs or uses an instance.**

1. The decisive question is **who operates the instance**. The operator can read what is in use (above), so for personal notes it must be someone their owners trust with that content. For the people of an organisation that usually means the organisation's own team on its own infrastructure, not a third party; whoever trusts no available operator runs their own instance.
2. **Admins are not the threat** the design worries about: the admin role grants no access to content (§4).
3. **No password reset, by design.** A user who loses both password and recovery key loses their notes. This has to be accepted and communicated.
4. **AI use is a policy decision outside Kumbu².** What an agent reads goes to its model provider. Kumbu² limits *which* vaults an agent can reach (and whether it may write), not what the provider does with what it receives; whether that is acceptable for the content is for the users, and whoever the notes belong to, to decide. The same holds for an external embedding provider, if the instance offers one: the operator decides whether to configure one and whether it is the default for vaults whose owner never chose, and each owner whether a vault uses it (§5.5).
5. **Deletion is for good, but not from backups.** A departing user's account can be deactivated (`src/Kumbu.Server/Accounts/Admin.cs:54–90`), and an admin can delete any user but the primary admin and themselves, active or not, in one step, with the username typed out and their own password (for a privacy request, with a receipt that names no vault or note); a user can delete their own account (password and username) or a single vault (its name). Everything of it goes in one MongoDB transaction: vaults with notes, history, trash, checkpoints and search vectors, every slot, sessions, API keys and connections with their tokens (`src/Kumbu.Server/Accounts/Deletion.cs`, §6). Deactivating disconnects the user's apps as it revokes their keys. Backups taken before keep the sealed data, and with it whatever credentials were valid then (§7). Account deletions are listed outside the database, so that a restore that brings a deleted account back is noticed; a single deleted vault is not listed, on purpose: it comes back in its owner's own sidebar, where they can delete it again (§6).

## 2. Threat model and honest limits

### What is protected, against whom

| Threat | Protected? | Why |
|---|---|---|
| Database dump, stolen backup, hoster's disk | Yes, content and names | All content and paths sealed with AES-256-GCM under per-vault keys; keys stored only wrapped (§5). |
| Another user of the same instance | Yes | A user's vaults open only with their user key; other users' vaults are invisible, not merely refused (§4). |
| An admin (in the app) | Yes, content | The admin role carries no key material; admin screens show metadata only (`src/Kumbu.Server/Accounts/Admin.cs`). |
| A stolen API key | Limited to its vaults and rights | Slots per vault, right sealed into the slot; revocation deletes the slots at once (§6). Revoking alone does not re-key the vault; re-encrypting it does (§3). |
| Cross-site attacks in the browser | Yes, as far as tested | `SameSite=Strict` cookie, `Origin` check, CSP, HSTS, no raw HTML in rendered Markdown (§7). |
| Online password guessing | Rate-limited | Per username and per address (§7). The per-username limit lets anyone who knows a username keep that user from signing in, minute after minute (a targeted lockout; keys and live sessions keep working). |
| Guessing a pairing code | Bounded | 40 bits, valid for ten minutes; 10 tries a minute per network, and 100 wrong codes a minute server-wide, after which every redeem is refused (§6). The server-wide limit lets anyone hold off pairing for everyone, minute after minute: accepted on purpose, since an attacker gains only a delay, and codes long enough to need no server-wide limit would cost every user more typing at every pairing (§9). |
| Offline password guessing from a dump | Slowed, not prevented | Argon2id with 64 MiB per guess (§5); a weak password remains guessable. |
| A user filling the server's storage | No, a known limit | There are no quotas per user or per vault. A file is at most 15 MB and a note 1 MiB, but a path keeps up to 10 earlier versions besides its current one, the trash keeps removed files and notes for 30 days, and up to 10 checkpoints per vault by default (`Kumbu:Vaults:CheckpointLimit`) keep what they held; so one path can hold about 15 MB × 11 for a month, and any number of paths can be written. Identical bytes are stored once per vault (§5.4), which helps only with copies. A user (or an API key with write rights) can fill the database's disk; the admin sees the bytes stored per user (§4) and can deactivate or delete the account. |

### What is not protected

- **The operator of the running server.** While a vault is unlocked, its notes, paths, search vectors and the vault key itself are in the server's memory in plain form (`src/Kumbu.Server/Vaults/UnlockedVault.cs`, `VaultCatalog.cs:880`). The operator can read process memory, and can deploy a modified server or web app that records passwords, session cookies and API keys as they arrive (passwords are sent to the server and derived there; nothing is derived in the browser). Users who do not trust the operator must run their own instance.
- **The AI provider** of a connected client sees what the agent reads and writes. This is not end-to-end encryption and is never described as such (`README.md`, "Security").
- **The app's provider holds a refresh token.** For an app connected through a connection (claude.ai and others), the token endpoint answers the provider's servers, not the user's device, so the provider (Anthropic, OpenAI, xAI…) keeps the connection's refresh token: key material that, with Kumbu²'s database, opens exactly that connection's vaults with its rights, until the connection expires or its tokens are revoked. That is consistent with the threat model, since the provider sees whatever it reads anyway, but it means a breach at the provider reaches those vaults without the user's password. Revoking the connection in Kumbu², or a password change that disconnects the apps, ends it (§6, §8).
- **An external embedding provider**, for a vault that opted in, or never chose while that provider is the instance's default: it receives the text of every section and every search query of that vault, and what it keeps is its own promise (§5.5).
- **Copies outside Kumbu².** An export or a multi-file download (§6, "Export and import") and the notes and files the Obsidian plugin keeps on a device (§6, "Device pairing and sync") are plain text and plain files wherever they are stored: Kumbu²'s encryption at rest ends where they leave the server.
- **Rollback by someone with write access to the database.** An older genuine version of a document (from a backup) can be put back; it opens, because it is genuine. Detecting this needs a per-vault counter or manifest; not built (`docs/superpowers/specs/2026-10-23-encryption-design.md` §5).
- **Old copies of the database with old credentials.** Revoking a credential deletes its slot but changes no key; re-keying gives new keys, but cannot reach into a copy taken before it (§3). Whoever holds an old backup *and* a credential that was valid then (an old password, an old recovery key, a revoked API key) can open from it what it held. That reach is limited to data written before the vault's last re-keying: what was written afterwards is sealed under a key that no old credential opens, in a current dump or a later backup. A vault never re-keyed has no such limit. Restoring a backup brings back the credentials of that moment (§7).
- **Metadata.** The database holds, in the clear: usernames and roles, sign-in times, which vaults belong to which user, how many documents a vault has and their sizes, revision numbers and times (details in §5.6). An admin sees some of this by design.
- **Keys in memory are not zeroed.** Locking a vault drops the reference; the bytes stay until the .NET garbage collector reuses them (`VaultCatalog.cs:775`). The re-keying runner also holds a user key while one of that user's vaults waits for it (§3). An open pairing code holds a copy of its user's key for at most eleven minutes, and no longer than the user stays signed in; that copy is zeroed when the code goes (§6). Swap and core dumps of the server can hold plaintext; the operator should disable both on the host.

### How long plaintext lives in memory

A vault is decrypted **completely** the first time a request uses it (notes, history, trash, moves, embeddings, checkpoint index; `VaultCatalog.cs:880–953`) and served from memory afterwards. A sweep once a minute (`src/Kumbu.Server/Vaults/VaultSweeper.cs:9`) locks a vault after **15 idle minutes** (`Kumbu:Vaults:IdleMinutes`, `src/Kumbu.Server/KumbuOptions.cs:167`), so in practice after 15 to 16 minutes, and the least recently used vaults when all unlocked vaults together exceed a memory cap (default 512 MB, `KumbuOptions.cs:170`). A vault used in the last minute is never locked. Idle means *no caller* used the vault: the time counts across sessions and API keys together, so an agent that polls a vault keeps it unlocked (so does a visible web app tab with a note open, whose poll of the note's version reads it every 5 seconds, until its session ends, and an Obsidian device that syncs it, whose every version-list request touches the vault, `Api/SyncApi.cs:87`; §6), and signing out or the end of a session does not lock it (`Vaults/UnlockedVault.cs:102`, `VaultCatalog.cs:783`). A restart locks everything; but because sessions and API keys live in the database (§6), the next request with a valid cookie or key unlocks the vault again without the user doing anything.

The unlocked cache never replaces authorisation: every request derives its own lookups and unwraps its own slot, and a cached vault is handed out only if the unwrapped key matches it (`VaultCatalog.cs:886–892`).

## 3. Keys and slots

### The hierarchy

Every user has a random 256-bit **user key**. Every vault has a random 256-bit **vault key**. Neither is ever stored in the clear. Each is stored in **slots**: the key, sealed with AES-256-GCM under a key-encryption key (KEK) derived from one credential. Opening a slot needs that credential; revoking a credential means deleting its slot. This is the same idea as LUKS key slots.

    RT["Refresh token, 256 bit<br/>kumbu_rt_…, at the app"]

  AK -- "HKDF-SHA256, salt = vault id<br/>API-key slot: vault key + right" --> VK
  RT -- "HKDF-SHA256, salt = vault id<br/>connection slot: vault key + right" --> VK

  VK -- HKDF --> BK["Blob-id key<br/>HMAC-SHA256"]
  CK --> DATA["Notes with history, trash, moves,<br/>embeddings, checkpoints, vault name,<br/>attachment records and their bytes"]

Why a user key in between: with five vaults and three credentials, direct slots would be fifteen to keep in step on every change. With the user key, a password change rewraps one slot, and a new vault is wrapped once (`docs/superpowers/specs/2026-10-24-accounts-and-web-design.md` §3).

### The slots as built

(All paths relative to `src/Kumbu.Server/`.) Each derivation has its own label, so a value derived for finding a slot can never serve as a key for opening one. The per-vault and per-user salts mean one KEK opens exactly one slot. HKDF is used only for high-entropy secrets (random keys and tokens, and the dev token, which the operator chooses and which must therefore be random: the server checks only its length, `KumbuOptions.cs:8–17`, `Vaults/VaultCatalog.cs:99, 978`); Argon2id only for the password, the one low-entropy secret (`src/Kumbu.Core/Crypto/VaultCrypto.cs:54`).

**Finding a slot without storing the credential.** Sessions and API keys are found by a lookup value `HKDF(secret, "…-lookup")` stored next to the slot (`Sessions.cs:169`, `Accounts/ApiKeys.cs:366`); a user's vault slots by `HKDF(user key, "kumbu/v1/user-slot", salt = user id)` (`VaultCatalog.cs:983`). Since the secrets are 256 bits of randomness, a lookup value cannot be turned back into the secret, and guessing is pointless.

**Vaults of users have no recovery slot of their own.** The user's recovery key reaches them through the user key.

**The dev token** (a single server-wide bearer secret for local development, steps 1–7) has its own older slot kind on the vaults it created. It is optional: unset, it opens nothing (`KumbuOptions.cs:19–20`). It never had and cannot get a slot on a user's vault. A public instance runs without it (§7).

### Key rotation and re-keying

**Revoking a credential changes no key.** Revoking an API key deletes its slots (`Accounts/ApiKeys.cs:197–218`), a password change wraps the same user key under the new password (`Accounts/UserCatalog.cs:268–319`), and a new recovery key wraps the same user key (`UserCatalog.cs:224–243`). So an old backup, together with a credential that was valid when it was taken, opens what that backup holds, and a vault key exposed once opens every later copy of the vault until the vault is **re-keyed**. Re-keying comes in two stages, the user key and then each vault (design and measurements: `docs/superpowers/specs/2026-10-26-rekeying-design.md`).

**Stage 1: a new user key** (`Accounts/UserKeyRotation.cs`). A new random user key replaces the old one, in one transaction, with everything that hangs on it (`UserKeyRotation.cs:121–142, 195–286`):

- the password slot, sealed again under the password at hand with a new salt;
- a **new recovery key**, shown once. Outside a recovery the old recovery key isn't at hand, so its slot can't be sealed again, and left as it is it would open a user key that no vault slot uses any more;
- the current session's slot if one is kept; every other session ends;
- each vault slot of the user, with its lookup value and its vault name hash;
- the sealed names and rights of the user's API keys and connections, revoked ones included, with their name hashes;
- `users.keyId`, the credentials stamp, and every vault of the user in `users.rekeyPending`, for stage 2.

Argon2 and the resealing run before the transaction (`UserKeyRotation.cs:80–112`). Each write is conditional on the value it was prepared from, and the transaction checks that no slot under the old lookup value is left and that the user has exactly the API keys and connections that were prepared; on any mismatch it aborts and is prepared again, three times at most, then answers 409 (`UserKeyRotation.cs:150–177, 243–286`). A crash therefore leaves the password and the vault slots opening with one key: the old one before the commit, the new one after it. A slot that matched but didn't open, or an API key's or connection's sealed name that doesn't open, is left as it is and logged; it opened nothing before either.

**`users.keyId` guards every write under a user key.** A sign-in can read the old password slot just before a rotation commits, and then holds the old user key with a read time after the stamp. So each transaction that writes something under the user key and writes the user document requires `keyId` to be the one derived from the key it uses, else 401: starting a session, creating a vault, an API key or a connection, changing a connection's rights, and the consent's code issuance (`Accounts/Sessions.cs:49, 71`, `Vaults/VaultCatalog.cs:270, 1106–1113`, `Accounts/ApiKeys.cs:113, 142`, `Accounts/Connections.cs:110, 136, 237–243`, `OAuth/OAuthTokens.cs:187–188`). A password change or a new recovery key replaces its slot only if the password slot is still the one it opened, so neither wraps the old user key again after a rotation; a lost race answers 409 (`UserCatalog.cs:167–180, 224–243`).

**Stage 2: a new key for each vault** (`Vaults/VaultCatalog.Rekey.cs`). A vault gets a new random vault key K′, and everything sealed under its key K is sealed again under K′: notes with their history, trash, moves, embeddings, checkpoints and checkpoint texts, attachment records with their history and their trash, and the attachments' blobs, with their keyed hashes (`pid`, a blob's `bid`) recomputed, and the vault's name. One transaction would not fit a large vault: everything a MongoDB transaction rewrites must stay in the database's cache until it commits, and on a 256 MB cache a vault of 2000 notes (40–80 MB) is more than one transaction can rewrite. So a run has a **two-key period**, between two short transactions:

- **Start** (`VaultCatalog.Rekey.cs:333–405`): K′ goes into a `user-next` slot beside the owner's user slot (§3, "The slots as built"); the vault document gets `rekeyStartedAt`; every API key with a slot on the vault is revoked whole, its name freed and its slots on every vault deleted, since the server can't wrap K′ for a key it doesn't hold; every connection that lists the vault loses its tokens and needs a reconnect (`rekeyed`); every other slot on the vault but the owner's two is deleted; and the vault goes into `rekeyPending`. The start requires `users.keyId` to match the user key it runs with (`VaultCatalog.Rekey.cs:342–349`).
- **Batches** (`VaultCatalog.Rekey.cs:470–635`): each collection of the vault is read from MongoDB and sealed again under K′ in transactions of at most 500 documents or 4 MiB of sealed bytes (`VaultCatalog.Rekey.cs:94, 97`), each write conditional on the blob that was read (for an attachment's blob, on its `bid`: the bytes a `bid` names never change). Reads are bounded the same way, by the sizes MongoDB reports before the read: at most 100 documents and 4 MiB, a larger document alone, so a pass never holds a hundred blobs of 15 MB at once (`VaultCatalog.Rekey.cs:46, 503–530`). Passes repeat until one finds nothing to change, at most 10 (`VaultCatalog.Rekey.cs:52, 474–486`); past that the run gives up with "being re-encrypted", the vault stays in its two-key period, and the runner tries again after its backoff. A document that opens under neither key is **damaged**: it is left as it is, counted and logged (`VaultCatalog.Rekey.cs:653`).
- **Finish** (`VaultCatalog.Rekey.cs:413–464`): the user slot wraps K′, the `user-next` slot goes, the vault's name is sealed under K′, `rekeyStartedAt` is unset and the vault leaves `rekeyPending`.

**Blobs get new ids.** A blob's `bid` is a keyed hash of its bytes under a key derived from the vault key (§3), so K′ gives every blob a new one, and every record that names a blob must name the new one. Checkpoint texts and blobs therefore come first in a pass, and the pass over them learns, for each, its id under K and under K′, computed from what it holds, whichever key it is sealed under at that moment; the passes over attachment records, with their history, attachment trash and checkpoints (which reference the blobs of the attachments they hold) then name the new ids (`VaultCatalog.Rekey.cs:39–42, 638–658`, `MapBlobId` in `Vaults/UnlockedVault.cs`). A blob is resealed in place, `_id` kept, so two paths with the same bytes still share one blob. A record that names a blob the vault doesn't have, or one that opens under neither key, keeps the id it had and is logged. A re-keying releases no bytes a record needs: the only blobs it deletes are the second of two documents that claim one new id, which hold the same bytes (one is kept), and a document that opens under neither key yet claims a blob's id, which is logged as damaged (`KeepOneAsync`). A blob that nothing references is the blob sweep's, and the sweep doesn't touch a vault that a run holds or that is in its two-key period (it takes the vault's write lock and the same checks as a write, `Vaults/BlobSweep.cs`). Between a blob's batch and its records' batches the records under K name an id the blobs no longer have, as checkpoints under K name texts already resealed; but nothing reads the vault in its two-key period, and a resumed run learns the ids again from the blobs' bytes.

A crash at any point leaves every document under exactly one of K and K′, or damaged, and the next run resumes with the key in the `user-next` slot. Meanwhile the vault answers as a placeholder: name lists keep it, a request for it answers 503 "This vault is being re-encrypted; try again in a moment." with `Retry-After: 5`, and searches across vaults leave it out (`Vaults/VaultCatalog.cs:911`, `Vaults/EncryptedNoteStore.cs:579–594`, `Api/ApiErrors.cs:66–70`). A session's listing of its vaults that read a user slot just before a finish committed, and loads the vault just after it, holds K while the vault is under K′; it reads that slot once more and loads the vault with K′, so a list of vaults, keys or connections, or the consent page, doesn't answer 503 "This vault was just re-encrypted" right after a recovery, a sign-in or a re-encryption; a second failure does (`Vaults/VaultCatalog.cs:170–186`). API keys and connections have no such window: the start deleted their slots on the vault. The consent page also tries its request once more after a 503 (`web/src/routes/Consent.tsx:53–62`).

**Nothing in this process writes a vault during its run.** Every object of a vault shares one pair of locks, for writes and for indexing, and a run holds both from its start to its finish (`VaultCatalog.Rekey.cs:227–252`). Every write and every indexing checks, before waiting for its lock and again under it, that no run holds the vault, that the vault is not in its two-key period, and that the object was made with the vault's current key; else 503 (`VaultCatalog.Rekey.cs:123–132`). Against a writer outside the locks (another process, a bug), the writes and deletes of a note also filter on its `pid`, which a resealed note no longer has under K, so such a write matches nothing instead of destroying the note (`Vaults/EncryptedNoteStore.cs:566–567`). Old keys can't escape into new slots either: an API key or an app's code whose slots were wrapped from a user slot before a start or a finish is refused inside its own transaction (`VaultCatalog.Rekey.cs:149–169`), and a vault in its two-key period gives no key to a new slot at all (`Vaults/VaultCatalog.cs:323–355`).

**The runner** (`Vaults/RekeyRunner.cs`) runs stage 2 in the background: one vault at a time for the whole process, from one queue, so that runs don't multiply the cache their batches need (`RekeyRunner.cs:134–155`). An attempt that takes longer than 30 minutes counts as failed (`RekeyRunner.cs:37, 157–197`); after the n-th failure in a row the vault waits min(2ⁿ⁻¹ minutes, 1 hour) before it is tried again (`RekeyRunner.cs:206–236`). A trigger for a vault whose run is under way hands its user key to the next attempt; if that key is a newer one (a rotation committed mid-run, so the run under way fails with the replaced key), a failure is tried again at once with the newer key instead of backing off with the old one (`RekeyRunner.cs:113–121, 172–176, 221–227`). A restart loses the queue, not the state: `rekeyPending` and `rekeyStartedAt` stay in the database, and the user's next sign-in, or a request that meets the vault, starts it again (`Api/AccountApi.cs:168`, `Vaults/VaultCatalog.cs:189`, `Accounts/Rekeying.cs:82–99`).

**When it runs:**

- **A recovery** rotates the user key in the transaction that sets the new password and the new recovery slot, answers with the new recovery key at once, and hands every vault to the runner (`UserCatalog.cs:134–158, 300, 327–347`, `Api/AccountApi.cs:215–223`). Until its run starts, a vault keeps working under its old vault key, whose user slot the rotation already wrapped under the new user key.
- **"Re-encrypt my vaults"** in Settings (`POST /api/account/reencrypt`, with the password): stage 1, keeping the current session and ending every other one; then, before the answer, every API key of the user is revoked and the tokens of every connection (`rekeyed`); the answer carries the new recovery key; then the runner re-keys each vault (`Accounts/Rekeying.cs:27–56`, `Api/AccountApi.cs:139, 264–272`).
- **"Re-encrypt vault"**, per vault in Settings (`POST /api/vaults/{vault}/rekey`, with the password, which is checked before the name is looked up): the request waits for that vault's run, behind any other vault in the queue. Before the user confirms, the page lists the API keys and apps that will lose access (`GET /api/vaults/{vault}/access`; `Api/NoteApi.cs:143–144, 232–249`, `Accounts/Rekeying.cs:64–75, 103–115`).

**What it protects.** An old backup keeps what it held, and whatever opened it then still opens it there. But data written after a vault's re-keying is sealed under K′, which no old credential reaches: an old password or recovery key opens the old user key, which opens no current slot, and a revoked API key's slot never held K′. A vault key exposed once, through a revoked key's slot in a backup say, opens nothing written after the vault's re-keying.

**Limits and windows:**

- **The runner holds a user key in memory** while one of that user's vaults is queued, running or waiting after a failure, so that it can carry on without the user (`RekeyRunner.cs:46–65`). Otherwise the server holds a user key only while a request uses it, and while a pairing code is open: its record keeps a copy of the user key for at most eleven minutes, zeroed when the code is redeemed, replaced or expires, but not when the session that made it signs out (§6, "Device pairing and sync"). Keys in memory are otherwise not zeroed (§2).
- **A crash between stage 1's commit and the revocation** in "Re-encrypt my vaults" leaves the API keys and the apps' tokens live until stage 2 reaches their vaults: every key and connection has a vault, every vault is pending, and each start revokes what has a slot on its vault. The same holds if the revocation fails; that is logged as an error, and the new recovery key is answered all the same (`Rekeying.cs:32–54`).
- **Damaged documents may stay under the old key**, with whatever clear fields they have; whoever holds K might open one by restoring its original fields. They were already unreadable to the user, and the run logs each.
- **A password change alone does not rotate**: it wraps the same user key under the new password. After a suspected compromise, re-encrypt; if the password itself may have leaked, change it too.
- **Re-keying revokes API keys whole**, with their other vaults, and connected apps need a reconnect: the server can't wrap a new vault key for a credential it doesn't hold. The agents and apps still in use need new keys or a reconnect.
- **Dev-token vaults can't be re-keyed**: they have no owner's user slot (`VaultCatalog.Rekey.cs:337–340`).
- **Re-keying assumes a single server process.** The locks, the key checks and the runner live in memory, as the working set does (§9). A writer in another process meets the `pid` fences and fails instead of destroying a note, but a new document it inserts stays under K and shows as damaged.
- **While a vault is mid-re-key**, creating an API key or a connection for it, changing a connection's rights to include it, and Allow on the consent page for a connection that lists it answer 503, as reads and writes of it do (`Vaults/VaultCatalog.cs:350`, `Api/ConnectionApi.cs:107–108`).
- **The batch size was measured on mongod 7.0.14** with a 256 MB cache (2000 notes with history and embeddings, 49 MiB, re-keyed in 16 batches of at most 4 MiB in about 7 s), not on `mongo:8`, which the shipped Compose file runs (`compose.yaml:3`).

## 5. Encryption at rest in detail

### 5.1 Primitives

All from .NET itself (`System.Security.Cryptography`), except Argon2id:

| Purpose | Primitive | Parameters | Code |
|---|---|---|---|
| Sealing (encrypt and authenticate) | AES-256-GCM | 256-bit key, 96-bit nonce, 128-bit tag | `src/Kumbu.Core/Crypto/VaultCrypto.cs:27–36` |
| Deriving keys from random secrets | HKDF-SHA256 | 256-bit output, a distinct label per purpose, salt where a key must be bound to one vault or user | `VaultCrypto.cs:55–60` |
| Keyed hashes | HMAC-SHA256 | key derived from the vault key | `VaultCrypto.cs:65` |
| Password → KEK | Argon2id (Konscious.Security.Cryptography.Argon2 1.3.1) | **64 MiB memory, 3 iterations, parallelism 4**, 16-byte random salt per password slot, 32-byte output; NFC-normalised password | `src/Kumbu.Server/Accounts/Argon2Kdf.cs:11, 17–18, 69–76` |
| Random keys, nonces, secrets | `RandomNumberGenerator` (OS CSPRNG) | 32 bytes for every key and secret | `VaultCrypto.cs:20, 32` |

The Argon2id setting is the second recommended option of RFC 9106; it is above OWASP's current minimum. To keep sign-in floods from exhausting memory, at most one Argon2 run per CPU core happens at once across the process; the rest wait (`Argon2Kdf.cs:20–26`).

**Sealed blob format:** one format byte (`1`), the 12-byte nonce, the ciphertext, the 16-byte tag (`VaultCrypto.cs:18, 27–36`). The nonce is **fresh random for every seal**; nothing reuses a nonce deliberately. With random 96-bit nonces, the usual bound is about 2³² seals per key; one vault's content key is far from that in personal use.

### 5.2 Context binding (associated data)

Every blob is sealed with associated data that names what it is. A blob only opens in exactly that context:

| Document | Associated data |
|---|---|
| Note (with its history) | `note:{vaultId}:{documentId}:{revision}` |
| Trashed note | `trash:{vaultId}:{documentId}` |
| Move record | `move:{vaultId}:{documentId}` |
| Embeddings of a note | `embeddings:{vaultId}:{pathId}` |
| Checkpoint | `checkpoint:{vaultId}:{documentId}` |
| Checkpoint text | `cptext:{vaultId}:{textId}` |
| Vault name, with the vault's embedding provider | `vault:{vaultId}` |
| Slots | see §3 |
| API key's name and vaults (owner's list) / its writer label | `api-key:{keyId}:meta` / `api-key:{keyId}:writer`, for a key with an expiry `api-key:{keyId}:writer:{expiry in Unix milliseconds}` |

(`src/Kumbu.Server/Vaults/UnlockedVault.cs:118–227`, `VaultCatalog.cs:139, 989–994`, `Accounts/ApiKeys.cs:372–382`.)

Consequence: someone with write access to the database cannot move a note, its embeddings or a checkpoint into another document, another vault or another revision, nor swap their clear fields around: it fails to open. On opening, the path inside the sealed note must also match the clear path hash (`UnlockedVault.cs:122–131`), likewise for embeddings and checkpoints. A document that fails is reported as damaged, never shown. The clear fields of trash and move records (the path hash, the deletion or move time) are *not* bound into the seal (`UnlockedVault.cs:137–153`): changing them can mislabel an entry or make the TTL index remove it earlier, which amounts to deleting it, something write access to the database allows anyway.

### 5.3 Sealed paths and names

Paths, file names and folder names exist in the database only inside sealed blobs. For MongoDB's unique index and lookups each document carries a **keyed hash** of its path, `HMAC-SHA256(HKDF(vault key, "kumbu/v1/path-id"), path)` (`UnlockedVault.cs:115`). Equal paths give equal hashes within a vault; without the vault key nothing else can be learned, not even whether two vaults hold the same path. Vault names are sealed (`VaultCatalog.cs:259`); their per-user uniqueness uses a keyed hash under the user key (`VaultCatalog.cs:230`). API key and connection names are sealed under the user key (`ApiKeys.cs:121`, `Accounts/Connections.cs:117`), and their uniqueness also uses a keyed hash, one for both (`Accounts/WriterNames.cs:50–51`, label `kumbu/v1/api-key-name-id`): a user's names are unique across API keys and connections together. Each collection has its own partial unique index (`ApiKeys.cs:397–401`, `Connections.cs:434–438`), and each creation checks the other collection inside its transaction (`ApiKeys.cs:148`, `Connections.cs:140`), which also writes the user document, so two creations with one name at once conflict and the retried one sees the other (`tests/Kumbu.Server.Tests/Accounts/ConnectionTests.cs:108`). Checkpoint names are keyed hashes too (`UnlockedVault.cs:190`).

### 5.4 History, trash, moves and checkpoints

- **History:** up to 10 earlier versions per note are kept **inside** the note's sealed blob (`src/Kumbu.Core/Notes/NoteWriter.cs:19`; `UnlockedVault.cs:338–340`), so the database does not even show how many versions exist, only the blob's size.
- **Trash and move records** are sealed documents of their own, removed by MongoDB TTL indexes after 30 days (`VaultCatalog.cs:1038–1049`). They also carry, inside their seal, the changeset they belong to, so the Activity sheet can group a removal or a move with the writes around it; the database shows nothing new (`UnlockedVault.cs:137–153`). An attachment's move is a move record like a note's, written in the same transaction as the move itself and the link rewrites it causes (`EncryptedNoteStore.cs`, `TryCommitAsync`); a record doesn't say whether it moved a note or an attachment, beyond what the sealed paths say.
- **Attachments** (PDFs and images) keep their record where notes keep theirs, in the `attachments` collection: path, format, size, displayed pixel size, version token, writer, changeset and up to 10 earlier states, all inside one sealed blob, as a note's history is (`Vaults/UnlockedVault.cs`, `SealAttachment`). The bytes of each state are a document of their own in `blobs`, sealed under the content key with the blob's id as associated data, and stored **once per vault** however many paths, versions, trash entries and checkpoints name them; a record names its bytes only inside its seal. Blobs are read one at a time when a file is served, never into the working set of an unlocked vault (`EncryptedNoteStore.cs`, `OpenBlobAsync`).
- **Attachment trash** (`attachment_trash`) is sealed like a note's trash, but has no TTL index: the blob sweep (`Vaults/BlobSweep.cs`) removes entries older than 30 days itself, so that in the same step it can delete the blobs that only they held. A blob is deleted when nothing references it any more (current states, history, trash, checkpoints), checked against what MongoDB holds and not only the working set, and never within 10 minutes of being written (an upload whose record is not committed yet). A commit that names a blob the records it replaces didn't hold (an upload, a restore from a checkpoint, a new checkpoint) is refused if the blob is gone, read from an index that holds the blob's id and time, so no blob is fetched for it; a blob that nothing in the working set holds any more and that a sweep could release soon is also made young again in the same transaction, which a sweep deleting it at the same moment conflicts with. One the working set holds can't be released meanwhile: the commit holds the vault's write lock, which this process's sweep takes too (`EncryptedNoteStore.cs`, `RequireBlobsAsync`). Until the sweep runs, an unreferenced blob stays, sealed. The sweep runs once a minute, but only over the vaults that are unlocked at that moment (`VaultCatalog.cs`, `Sweep`), since it needs the vault key to read what references a blob. So, unlike a note's trash, which MongoDB's TTL index removes after 30 days whether or not anyone opens the vault, a trashed attachment of a vault nobody unlocks stays (sealed) past its 30 days, and goes, with the blobs only it held, at the first sweep after the vault is next unlocked. Until that sweep, within a minute of the unlock, it is still listed in the trash (with an expiry already past) and can be restored.
- **Checkpoints** (named snapshots of a folder) store each note text once per vault, under a keyed hash of the content (`UnlockedVault.cs:193`). Which checkpoint refers to which text is recorded only inside the sealed checkpoint (`UnlockedVault.cs:195–198`), so a database reader cannot tell whether two checkpoints share a text; visible are the number and sizes of the distinct texts per vault. A checkpoint holds its attachments by reference to their blobs, also only inside its seal.
- Deleting in MongoDB is not secure erasure: removed documents may persist in storage files and backups, but sealed. This holds for a deleted vault or account too (§6, "Deleting vaults and accounts").

### 5.5 Search and embeddings

Full-text search runs over the decrypted notes in memory. Search by meaning uses an embedding model. **By default, and for every vault whose owner has not chosen otherwise unless the admin set another default**, that is the internal model (Snowflake Arctic Embed, `arctic-m` or `arctic-l`), which runs **inside the server process** with ONNX Runtime: no note leaves the server to be embedded. The model is downloaded once from Hugging Face at a pinned revision and checked against a SHA-256 per file while downloading (`src/Kumbu.Server/Search/OnnxEmbedder.cs:79–122`, `ModelFiles.cs:20`). At later starts only the file sizes are checked (`OnnxEmbedder.cs:86`): a model file replaced on the volume by one of the same size would be loaded, so the model volume must be as trusted as the image. The vectors are stored per note as 16-bit floats inside a sealed blob (`UnlockedVault.cs:156–187`); embeddings can leak content if exposed, so they get the same protection as the text. There is no vector database and no external search service.

#### External embedding providers (opt-in per vault, or the admin's default)

The admin of an instance can configure external embedding providers, services with the OpenAI embeddings API such as TensorX (`Kumbu:Embeddings:Providers:<name>`, README "External embedding providers"). Configuring one sends nothing anywhere by itself. Each vault's **owner** decides, in the vault's menu, whether that vault uses one of them.

**The default is the admin's.** A vault whose owner never chose uses the instance's default, `Kumbu:Embeddings:Default` (`KUMBU_EMBEDDINGS_DEFAULT`): `internal` unless the admin sets it (`KumbuOptions.cs`, `EmbeddingsOptions.Default`), resolved each time the vault is unlocked or created (`Vaults/VaultCatalog.cs:153, 284, 907`). With an external provider as the default, sending is **opt-out, not opt-in**, for those vaults: their text goes to the provider without their owner having chosen it. What the owner can do is see it (the vault's dialog names the provider in use and marks the default) and switch back to `internal`; that choice is sealed explicitly (`UnlockedVault.cs:135`) and holds whatever the default becomes. Choosing the provider a vault already uses stores nothing, so a vault on the default keeps following it. A default that names no configured provider keeps the server from starting (`KumbuOptionsValidator.cs:84–89`). Up to 0.2.2 a choice of `internal` was stored as "no choice", so such vaults follow the default too. An admin who sets an external default should tell the instance's users, since a vault's owner is not asked.

- **What leaves the server, when, to whom.** For a vault that uses an external provider: the text of every section of every note (its note title, heading path and content, as `Chunker` builds it; the same text the internal model gets), sent when the vault is switched (all of its notes) and afterwards whenever a section's text changes; and **every search query** that covers the vault, when it is made. They go to the configured `BaseUrl` in a `POST …/embeddings` request with the configured model, over HTTPS (`Search/OpenAiCompatibleDriver.cs:112–117`). Nothing of the vault's other data goes there: no history, trash, checkpoints, file or vault names other than the note titles inside section texts, no user data. The vectors that come back are sealed and stored like the internal model's. The notes of other vaults, of the same user or others, are not sent (a search across vaults that includes this one does send its query, as above): each vault is indexed by its own provider's queue (`Search/SearchIndex.cs:34, 46`) and searched with its own provider's query vector (`Vaults/EncryptedNoteStore.cs:199, 275`).
- **The provider's retention is the provider's promise.** The admin can describe a provider (e.g. "EU, zero data retention"), and the web app shows that description before the owner switches, with the sentence that Kumbu² can't check or enforce it (`web/src/shell/EmbeddingsDialog.tsx`). What the provider keeps, logs or trains on is governed by its terms with whoever holds the API key (the operator), not by Kumbu². Switching back to internal stops further sending; what was sent stays under the provider's terms.
- **Who can choose.** For one vault, only a web session of the owner (`PUT /api/vaults/{vault}/embeddings` is session-only, and a session opens only its user's own vaults; `Api/NoteApi.cs:146, 188`). API keys, the dev token and admins cannot; an admin sets only the default for vaults without a choice (above). The choice is sealed with the vault's name in the vault's meta (`UnlockedVault.cs:135`, `VaultCatalog.cs:833`), so someone with write access to the database cannot point a vault at a provider; they could, as with any document (§2, rollback), put back an older genuine meta, which restores the choice that vault had then.
- **Only safe transport, failing closed.** At startup the server refuses a provider whose `BaseUrl` is not `https://` (plain HTTP only to a loopback address, a model on the same machine), whose key file is missing, unreadable or empty, or whose driver is unknown (`KumbuOptionsValidator.cs:99–149`).
- **The API key.** Read from a file (`ApiKeyFile`, e.g. a Docker secret under `/run/secrets/`), never from an environment variable or the configuration itself, once at startup (`KumbuOptions.cs:135`, `Search/IEmbeddingDriver.cs:115`); a new key needs a restart. It is sent only as the `Authorization: Bearer` header of requests to that provider's `BaseUrl` (`OpenAiCompatibleDriver.cs:113`), and never logged; validation errors name the file's path, never its content.
- **No text in logs or errors.** The driver logs the provider's name, the HTTP status or the kind of network error, and the attempt; it never reads an error response's body, which may quote the input (`OpenAiCompatibleDriver.cs:120`), and its exception messages carry no text. HttpClientFactory's per-request log lines are lowered to warnings, so the log does not record when someone searched (`Program.cs:35`). Tested in `tests/Kumbu.Server.Tests/Search/OpenAiCompatibleDriverTests.cs` (`Neither_the_key_nor_a_text_reaches_the_log_or_an_error`).
- **When the provider fails.** For indexing, timeouts, 408, 429 and 5xx are retried with exponential backoff (honouring `Retry-After`, at most 16 s a wait). A search waits at most 5 s for a provider, with one retry after half a second unless the provider asks to wait longer, and asks all providers in its scope at once; then it ranks that provider's vaults by words. When indexing keeps failing, the provider pauses for a minute (a failed search pauses only the searches, so it never holds up the index): its vaults' notes are ranked by words, also in a search across vaults, where they are merged with the other vaults' ranking by meaning by reciprocal rank fusion (`src/Kumbu.Core/Search/SectionSearch.cs`, `FuseByRank`), with a notice naming the vaults (a search by meaning only leaves them out and says so); its notes wait in its queue (`OpenAiCompatibleDriver.cs:152, 185`, `SearchIndex.cs:105`). A provider the admin removes leaves its vaults without search by meaning, never silently switched to another provider, until the owner picks one.

`Kumbu:Search:Enabled=false` switches off the internal model only; vaults that use an external provider still search by meaning.

## 6. Sessions, API keys, revocation and recovery

### Sign-in and sessions

Sign-in sends username and password over TLS. The server runs Argon2id, opens the password slot and gets the user key. An unknown username runs Argon2 against a dummy salt, so it takes as long as a wrong password, and all failures answer the same (`Accounts/UserCatalog.cs:95–119`).

A **session** is a slot: the server makes a random 32-byte secret, puts it in the cookie and stores the user key wrapped under a KEK derived from it (`Accounts/Sessions.cs:45–80`). The server keeps neither the secret nor the user key; a request can use the user key only if it brings the cookie. Sessions survive a server restart. Each request checks (`Sessions.cs:88–137`):

- idle timeout **30 minutes**, absolute limit **12 hours** (`Sessions.cs:18–19`); MongoDB's TTL index also deletes the slot at the absolute limit. The web app's poll of the open note's version (`GET /api/version/{vault}/{path}`, every 5 seconds while the page is visible, `web/src/api/history.ts`) does not count as use (`Api/HistoryApi.cs:107`, `Auth/CallerMiddleware.cs:101`, `Sessions.cs:126`), so a tab left open still ends its session after 30 idle minutes; the next poll then answers 401 and the app goes to sign-in, which takes the note off the screen. Unsaved Write-mode text stays in the tab's memory, never in storage, and is offered again only to the same user once they are signed in again (`web/src/note/MarkdownEditor.tsx:16–21, 36–40`);
- the user is still active;
- the session started after the last password change, recovery or re-encryption of the account (which keeps the session it was asked from, §3).

Signing out deletes the slot; "sign out other sessions" deletes the others; a password change or recovery deletes all, and re-encrypting the account all but its own. None of them locks a vault that is in memory: it stays there until idle (§2).

The cookie `kumbu_session` is `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, with `Max-Age` of 12 hours (`Api/AccountApi.cs:411–426`). It is accepted **only under `/api`**, never on `/mcp`, so a page on a sibling subdomain cannot drive the MCP endpoint with a user's cookie (`Auth/CallerMiddleware.cs:95–105`). That holds for a connection's URL, `/mcp/c/{id}`, too: its path is decided before the cookie is looked at (`Auth/CallerMiddleware.cs:51–55`).

### API keys

- Format `kumbu_` plus 32 random bytes in Base62 (43 characters), shown once (`Accounts/Secrets.cs:20`, `Accounts/ApiKeys.cs:106`).
- Rights per vault: `read` or `write`. A key without a vault cannot be created (`ApiKeys.cs:97`). Each vault gets its own slot sealing the vault key **and the right together**, bound to the key's id; changing the right in the database makes the slot fail to open (`VaultCatalog.cs:323–379, 475–505`). The read-only rule itself is enforced in the server before any write (`src/Kumbu.Core/Notes/ICaller.cs:16–19`, called by every write path); a read-only key still lets the server unwrap the vault key, as it must to read.
- Only a signed-in session can create, list or revoke keys, and the same holds for connections and for authorising an app for one (the consent). A key, or a connection's access token, can never manage keys, connections, the account or users (`Api/Security.cs:117–122`), so a leaked key cannot make more keys. A stolen *session* can make both, and those keys, and the refresh token of a connection it authorised, outlive it until revoked (§4). A creation whose session was checked just before a password change, recovery or deactivation cannot slip in after it: the key's transaction checks the user again (active, credentials unchanged since the session's sign-in) and writes the user document, so it either commits before the change's revocation, which then finds the key, or is refused with 401 (`ApiKeys.cs:127–167`). The same check guards creating a connection and changing a connection's rights (`Accounts/Connections.cs:134–138, 237–243`).
- The key's name becomes the writer label in the history, so the user can see which agent changed what; the web app shows changes by agent keys and connections since the previous sign-in. A paired device's writes count as the user's own and are not highlighted, unless the device wrote nothing for more than 14 days before ("Device pairing and sync" below); the Activity sheet still names the device (`web/src/note/AgentBanner.tsx:41–52`, `Api/WriterKinds.cs:23–52`).
- **Revoking** marks the key revoked and deletes its slots in one transaction; it opens nothing from then on, also for a vault still in memory, since every request opens its slots afresh (`ApiKeys.cs:197–218`, `VaultCatalog.cs:480–505`). A request that opened them just before (an MCP call in progress, say) may still finish; the next one is refused. It does not change the vault key: a copy of the database taken before the revocation still opens with the revoked key, and re-encrypting the vault limits that to what was written before (§3, "Key rotation and re-keying").
- **Changing the password** revokes all the user's keys too, and disconnects every app, unless the user unticks "Also revoke all API keys and disconnect apps" in Settings (`revokeApiKeys`, true when left out, so an older client gets the safe behaviour; `Api/AccountApi.cs:35–38, 240`, `web/src/routes/Settings.tsx:178`). A **recovery** always does both (`UserCatalog.cs:154`), and so does "Re-encrypt my vaults", after its rotation (`rekeyed`, `Accounts/Rekeying.cs:33–41`). Both mark every key revoked and delete its slots in one transaction, as revoking one key does, retrying a write conflict with the `lastUsedAt` update of a key in use (`ApiKeys.cs:220–237`); right after, the tokens of every connection that isn't revoked are revoked the same way, in a transaction of their own, and the connections need a reconnect, `password_changed` or `recovery` (`UserCatalog.cs:284–289`, `Accounts/Connections.cs:267–284`; "Connections (OAuth)" below). The revocation runs twice. First after the user's credentials are stamped as changed and before the new password is written (`UserCatalog.cs:279–289`): a fault in between leaves the keys revoked and the old password in place, the safe way round. Then again after the final stamp (`UserCatalog.cs:307–315`): a sign-in with the old password that read its slot between the two stamps passes the first one, and a key it made at once, or a code an app got through it, may land after the first revocation; no key or code can come from it after the second stamp, since the consent's transaction checks the stamp as a key's creation does (`OAuth/OAuthTokens.cs:188–189`).
- **Deactivating a user** ends all their sessions, revokes all their keys and the tokens of all their connections (`deactivated`) in one transaction, retried on a write conflict with a key or connection in use; reactivating revokes once more, for a key or code whose creation raced the deactivation, and so revives none of them: the apps need a reconnect (`Accounts/Admin.cs:54–90`). While the user is inactive, an access token is refused anyway, since every request checks the user (`OAuth/OAuthTokens.cs:710–711`).
- **Expiry** is optional and chosen at creation: 30, 90 or 365 days, or none (`ApiKeys.cs:67, 98–101`); the web app proposes 90 days for an agent's key, none for a paired device. From that moment the key answers 401 like a revoked one (`ApiKeys.cs:296–300`). The expiry is stored in the clear for the list, and bound into the seal of the key's writer label (`ApiKeys.cs:381–382`): moved or removed in the database, the label no longer opens and the key is refused (`tests/Kumbu.Server.Tests/Accounts/ApiKeyTests.cs`). The first time an expired key is presented again, its slots are deleted and its name is freed (`ApiKeys.cs:271–282`); the user's next key does the same for every expired key of theirs, in its own transaction (`ApiKeys.cs:261–269`). An expired key that is never presented again keeps its slots, which open nothing without the key and are refused anyway, until then. A key without expiry stays valid until revoked: one by one, by a password change that asks for it, by a recovery, by a re-keying of one of its vaults or of the account (§3), or by deactivation.
- **Checks are per request.** A request, or an MCP stream, that was authenticated before an expiry, a revocation, a deactivation or a deletion may still finish with the credential it was checked with; every later request checks again and is refused.

### Connections (OAuth)

A **connection** is a credential for an app that signs in with OAuth 2.1 (claude.ai and others) instead of being given an API key: the user creates it in Kumbu² with its vaults and rights, and pastes its connector URL, `/mcp/c/{id}`, into the app. Kumbu² is its own authorisation server, built here rather than with a library such as OpenIddict (Ruling 1 of the OAuth plan): OpenIddict has no support for client metadata documents, and its stores cannot share the MongoDB transaction that wraps the slots when a code or token is issued; the endpoint set is small. This part covers the authorisation request, the consent, the token endpoint with its refresh rotation, revocation by the app and the requests a connection's app makes.

- **The authorisation request is anonymous.** `GET /oauth/authorize` never reads the session cookie: claude.ai's navigation to it is cross-site, so the `SameSite=Strict` cookie is not sent anyway (Ruling 8). It checks the request, stores it server-side and sends the browser on with `303` to the web app's page `/consent?request={id}`, whose own `fetch` calls are same-site and carry the session (`OAuth/OAuthEndpoints.cs:167–225`). Its answers carry `Cache-Control: no-store` and `Referrer-Policy: no-referrer` (the URL holds the `state` and the PKCE challenge; the security headers keep a stricter policy a handler set, `Api/Security.cs:73`) and no CORS header (`OAuth/OAuthEndpoints.cs:171–173`).
- **Nothing goes to a redirect URI before it is trusted.** An unknown client, or a metadata document that is unusable, ends on Kumbu²'s own page, `/consent?error=unknown_client`; a `redirect_uri` that is missing or isn't one of the client's (matched exactly, except the port of an `http` loopback redirect, Ruling 6) ends on `/consent?error=invalid_redirect_uri`, whatever else is wrong with the request (`OAuth/OAuthEndpoints.cs:177–191`). A parameter sent twice counts as missing (RFC 6749 §3.1). Only then are protocol errors redirected to the app, with `error`, `error_description`, `state` if it sent one and `iss` (RFC 9207): `response_type` other than `code` (`unsupported_response_type`), and a missing or malformed `code_challenge` or a `code_challenge_method` other than `S256`, a missing one counting as `plain` (`invalid_request`, `OAuth/OAuthEndpoints.cs:193–210`). A `state` longer than 1024 characters is refused, not stored (`OAuth/OAuthEndpoints.cs:156, 196–206`).
- **A `resource` that is no connection's URL is explained, not redirected** (Ruling 7). When it is missing, or its canonical form is not exactly `{origin}/mcp/c/{id}` of an existing connection (someone pasted the plain `/mcp` URL, whose fallback finds the authorisation server's metadata on the origin), the request is stored with the problem `not_a_connection`, and the consent page says to create a connection and use its URL; its "Back" link denies with `error=invalid_target` (`OAuth/OAuthEndpoints.cs:212–224`, `Api/ConnectionApi.cs:117`). Scopes are hints only: `kumbu:read` without `kumbu:write` caps every right of the grant to read, and the page shows the capped rights; anything else changes nothing (Ruling 3, `OAuth/OAuthEndpoints.cs:216–217`, `OAuth/OAuthTokens.cs:729–735`).
- **A pending request lives 10 minutes** in `oauth_requests`, under a random 128-bit id; the expiry is checked in code, and the TTL index only tidies up (`OAuth/AuthorizationRequests.cs:30, 40, 53, 64, 91`).
- **The consent is bound to the session and to the request.** The consent API, `GET /api/oauth/requests/{id}` and `POST /api/oauth/requests/{id}/decision`, is for a signed-in session only: an API key gets 403, no cookie 401 (`Api/ConnectionApi.cs:69–71`). The decision is a `POST`, so the `Origin` rule is its CSRF guard (§7, `Api/Security.cs:124–134`); it returns the URL to go to, and the page navigates there itself (a form post would be stopped by `form-action 'self'` on the cross-origin redirect). The page shows the app's name and host, whether it identified itself with a metadata document or registered itself, where the browser returns, and the connection with the rights this grant gets. The connection must be the signed-in user's: for another account's, the view says `other_user` and shows nothing of it, neither name nor vaults; a revoked or expired one says so (`Api/ConnectionApi.cs:153–172`). With any such problem, Allow is a 409 and leaves the request in place so the page can still lead back; Deny always works (`Api/ConnectionApi.cs:96–105`). The decision takes the request as it reads it (`FindOneAndDelete`), so a request is decided once and of two decisions at once one gets it and the other a 404 (`Api/ConnectionApi.cs:112`, `OAuth/AuthorizationRequests.cs:62–64`). An Allow for a connection with a vault being re-encrypted answers 503 before the request is taken; one refused for that reason inside the code's transaction, which issued nothing, puts the request back unless it expired (`Api/ConnectionApi.cs:108, 133–140`, `OAuth/AuthorizationRequests.cs:71–82`).
- **Allow issues a one-time code that carries the vault keys.** The code is `kumbu_ac_` and 32 random bytes in Base62, like an API key (`Accounts/Secrets.cs:20`, `OAuth/OAuthTokens.cs:65, 137`). With the user key at hand, the server opens the connection's vault keys and wraps each, together with its (possibly capped) right, under `HKDF(code, "kumbu/v1/oauth-kek", vault id)`, bound to the vault, the connection and the code's record id (§3; `VaultCatalog.cs:391–399, 437–451, 996–1000`). The slots carry the code's expiry, **60 seconds**, for MongoDB's TTL index (`OAuth/OAuthTokens.cs:72, 141`, `VaultCatalog.cs:1077`). The code's record in `oauth_tokens` holds a lookup value `HKDF(code, "kumbu/v1/oauth-token-lookup")` (unique), the client, the exact redirect URI and the PKCE challenge it is bound to, and its grant (the connection's name, the `resource` and the connection's expiry) sealed under `HKDF(code, "kumbu/v1/oauth-grant")` with the associated data `oauth:{tokenId}:code`; the record stays 10 minutes past the code's expiry so that a reuse can be recognised (`OAuth/OAuthTokens.cs:76, 154–169, 744–755, 766–770`). Neither the code nor anything it could be recovered from is stored (`tests/Kumbu.Server.Tests/OAuth/AuthorizeTests.cs`, `The_code_wraps_the_vault_keys_for_a_minute`). The record, the slots and the app's name, host and verification sealed into the connection's meta are written in one transaction, which checks again that the connection is the user's, neither revoked nor expired, with the rights the slots were made from, and that the user is active with credentials unchanged since the session's sign-in, as for a new API key (`OAuth/OAuthTokens.cs:173–204`). The code goes back to the app only in the redirect, with `state` and `iss` (`Api/ConnectionApi.cs:143–145`); a self-registered client that got this far no longer expires (Ruling 14).
- **The token endpoint exchanges a code once.** `POST /oauth/token` is anonymous, with `Access-Control-Allow-Origin: *` and no credentials (Ruling 16). It takes only `application/x-www-form-urlencoded`, at most 16 KiB, each parameter once (else `invalid_request`), and only `grant_type=authorization_code` or `refresh_token` (else `unsupported_grant_type`); a missing `client_id` is `invalid_client` (401). Every answer carries `Cache-Control: no-store` and `Pragma: no-cache` (`OAuth/OAuthEndpoints.cs:36–104, 128–149`). Failures of either grant are limited to 20 a minute per `client_id` and address together (§7, `OAuth/OAuthEndpoints.cs:47–71`). The exchange is one transaction (`OAuth/OAuthTokens.cs:221–337`). The record found by the code's lookup value must be a code, unexpired (checked in code, against the record's expiry and the one sealed into its grant), not revoked and unused; it is marked used before anything else is checked, so the first request that presents a code spends it whatever the outcome, and an intercepted code tried with a wrong verifier is burnt (`OAuth/OAuthTokens.cs:259–261`). The client id and the redirect URI must equal the stored ones exactly, the verifier must satisfy `BASE64URL(SHA256(verifier)) == code_challenge`, compared in fixed time (`OAuth/OAuthTokens.cs:668–674`), and a `resource`, if sent, must be canonically equal to the connection's URL (else `invalid_target`, `OAuth/OAuthTokens.cs:282`); the connection must still be live and its user active. A code presented again after it issued tokens revokes the connection's tokens and leaves it needing a reconnect (`code_reused`); one burnt by a failed attempt issued nothing and revokes nothing, nor does a code that was revoked with its connection's tokens (`OAuth/OAuthTokens.cs:244–257`). Two exchanges of one code at once conflict on its record; one gets the pair (`Two_exchanges_of_one_code_at_once_give_one_pair`).
- **One token family per connection, each token a set of slots.** A successful exchange deletes the slots of the connection's earlier access and refresh tokens and turns their records into tombstones (below), deletes the code's slots, and issues `kumbu_rt_…` and `kumbu_at_…` (32 random bytes in Base62 each, `Accounts/Secrets.cs:20`). Each gets slots of its own, re-wrapped from the code's: opened with the code, then sealed under `HKDF(token, "kumbu/v1/oauth-kek", vault id)` with the same right, bound to the vault, the connection and the token's record id (§3). The refresh token lives until the connection's expiry, the access token for `Kumbu:OAuth:AccessTokenMinutes` (default 60) but never past the connection's expiry, and each token's slots carry its expiry for the TTL index. The expiries come from the connection's expiry sealed into the code's grant, and each token's own expiry is sealed into its grant too and checked on every use, so an `expiresAt` changed in the database, on the record or on the slots, extends nothing (`OAuth/OAuthTokens.cs:295–322, 707`; tested in `A_changed_expiry_in_the_database_extends_nothing`). Each record has its own lookup value and grant, sealed with the associated data `oauth:{tokenId}:{kind}`, so a refresh token's grant can't be read as an access token's. The connection is marked authorised and its `tokensRevokedAt` and reason are unset, so it lists as connected again after a reconnect (`OAuth/OAuthTokens.cs:324–326`, `Accounts/Connections.cs:386–394`). The answer's `scope` is `kumbu:read` if every right is read, else `kumbu:read kumbu:write` (`OAuth/OAuthTokens.cs:653–655`).
- **Every refresh rotates both tokens and the refresh token's slots** (spec §5). `grant_type=refresh_token` takes `refresh_token` and `client_id` (`OAuth/OAuthEndpoints.cs:93–98`); a `scope` is ignored, since the rights are the slots' and can't be widened, and a `resource`, if sent, must be canonically the connection's URL (else `invalid_target`, `OAuth/OAuthTokens.cs:536–542`). The refresh is one transaction (`OAuth/OAuthTokens.cs:353–489`). A refresh token of another client is `invalid_grant` and changes nothing, so naming a stolen token under one's own client id neither uses nor revokes it (`OAuth/OAuthTokens.cs:384`, `A_refresh_token_belongs_to_its_client`). An unused one, unexpired both by its record and by the expiry sealed into its grant, its connection live and its user active, is marked used only if it is still unused, its grant is dropped and its record stays 30 days to recognise a reuse; its slots are deleted, and a new refresh token and access token get slots re-wrapped from its own, with the same expiries as at the exchange (`OAuth/OAuthTokens.cs:95, 434–465`). The old access token lives out its hour. The connection's document is written in the same transaction, so a revocation of its tokens at the same moment conflicts with the refresh and one of them retries after the other: no new pair slips past a revocation (`OAuth/OAuthTokens.cs:470`).
- **A retried refresh gets the same pair for 30 seconds** (Ruling 11): Claude's refresh request times out after 30 s and is retried, and a client whose answer was lost must not end up revoked. So the new pair is kept in the old record's `successor`, sealed under `HKDF(old refresh token, "kumbu/v1/oauth-successor")` with the associated data `oauth:{oldId}:successor`: only the holder of the old token can open it, and it can't be moved to another record (`OAuth/OAuthTokens.cs:91, 99, 445, 659–666`). A used token presented again within the grace period gets that pair back, with the access token's remaining lifetime, while the pair's refresh token is still unused and neither it nor the access token revoked, and the checks of a refresh pass for the new pair's grant and the connection; otherwise `invalid_grant` (`OAuth/OAuthTokens.cs:401–412, 494–532`). Parallel refreshes of one token conflict on its record: the first commits, the others retry, find it used within the grace period and get the same pair (`Parallel_refreshes_of_one_token_get_the_same_pair`). The kept pair lives no longer than needed: when the new refresh token is itself used, its parent's `successor` is unset (`OAuth/OAuthTokens.cs:467–468`, `No_successor_outlives_its_use`), and every revocation drops it with the grant (`Accounts/Connections.cs:579`).
- **A reuse revokes the connection's tokens.** A used refresh token presented more than 30 seconds after its use means that someone else holds a copy (the token was stolen, or the legitimate client is the one replaying): every token of the connection becomes a tombstone and loses its slots, and the connection needs a reconnect, `refresh_reused` (`OAuth/OAuthTokens.cs:401–408`; `Reuse_after_the_grace_period_revokes_the_connection`). A reconnect through the same URL renews it with the same name and rights (Ruling 2). A refresh token that is already a tombstone is `invalid_grant`; if it was revoked with every other token of its connection, there is nothing left to revoke, but if the connection has a live family again (a new consent replaced the old family, or the owner reconnected after a revocation) and the token was spent more than 30 seconds ago, an old family's token turning up beside the new one is a reuse like any other and revokes the new family too (`OAuth/OAuthTokens.cs:387–399, 570–571`; `A_replaced_refresh_token_presented_again_revokes_the_new_family`, `A_revoked_refresh_token_is_refused_and_revokes_nothing_more`). A used refresh token's record keeps its 30 days when it becomes a tombstone (`Accounts/Connections.cs:573–582`), so a reuse after a revocation and a reconnect is still recognised for that long; after that the token is unknown and only refused.
- **The app can revoke its tokens** (RFC 7009). `POST /oauth/revoke` takes a form with `token` and optionally `token_type_hint` and `client_id`; the token's prefix says what it is, so the hint isn't needed. A refresh token, used or not, revokes all of its connection's tokens and leaves the connection needing a reconnect, `client_revoked`; an access token becomes a tombstone and loses its slots, the refresh token stays; a code, a revoked token or a string that is no token changes nothing (`OAuth/OAuthTokens.cs:580–617`). Holding the token is the proof: clients are public and their ids no secret. The answer is always 200 with an empty body, also for an unknown token, a missing one or a body that isn't a form, so it tells nothing about a token; it carries `Cache-Control: no-store` and `Access-Control-Allow-Origin: *` (`OAuth/OAuthEndpoints.cs:23, 112–125`; `The_client_can_revoke`, `Revoking_an_access_token_revokes_only_it`).
- **An access token works only on its connection's URL.** `CallerMiddleware` looks up a bearer starting `kumbu_at_` only on `/mcp/c/{id}` (`Auth/CallerMiddleware.cs:135–190`). On `/mcp` and the REST API it is just an unknown bearer and answers 401, since only the dev token and API keys (`kumbu_` and exactly 43 characters) are looked up there (`Auth/CallerMiddleware.cs:218–232`, `Accounts/ApiKeys.cs:290`). On a connection's URL it is valid only if its record is an access token, unexpired (checked in code), of exactly that connection, its grant opens with the token and names that URL (canonically), the connection is neither revoked nor expired and its user active (`OAuth/OAuthTokens.cs:683–724`). A refresh token or a code is refused there like an unknown one. Each request then opens the token's slots afresh, refusing one past its expiry in code, so a revoked or expired token opens nothing, whatever is in memory (`Vaults/VaultCatalog.cs:409–432, 458–468`); a token whose slots are all gone is refused with 401 (`Auth/RequestCaller.cs:75–80`). Writing is allowed only where a slot's right says so: `RequestCaller.CanWrite` asks every credential that carries rights, so a new kind of credential with rights can't slip past it (`Auth/RequestCaller.cs:55`, `Vaults/Credentials.cs:36–39, 71–86`). Writes carry the connection's name, from the grant, as writer label. The connection's `lastUsedAt` is written at most once a minute (`OAuth/OAuthTokens.cs:83, 713–721`).
- **Expired and revoked access tokens are not wrong keys** (Ruling 12). Every claude.ai user of an instance arrives from Anthropic's one egress range, and access tokens expire hourly, so an expired or revoked one must not feed the per-address wrong-key limit: that would lock every claude.ai user of the instance out. An expired token's record stays for 24 hours after it expired, its slots don't (`OAuth/OAuthTokens.cs:80, 313`). Revoking a connection's tokens (the owner's Revoke, a reused code or refresh token, the app's revocation, a password change that revokes the API keys, a recovery, a deactivation, a rights change, a re-keying of one of its vaults or of the account, a vault deletion that leaves it no vault) and replacing its token family keep each code's and token's record as a **tombstone** for 24 hours: its slots are deleted, `revokedAt` is set, the lookup value stays and the grant is dropped, so it is recognised but opens nothing (`Accounts/Connections.cs:487–582`). Only deleting the account removes the records outright. A `kumbu_at_` bearer on a connection's URL is looked up under the wrong-key limit: a token that is known (expired, revoked, of another connection) gives its permit back; an unknown or malformed one uses it up, so lookups without a valid token stay bounded at 20 a minute per address (`Auth/CallerMiddleware.cs:146–182`). An unknown id is a 404 before any token is looked up. Tested in `Expired_access_tokens_do_not_count_as_wrong_keys` and `Revoked_access_tokens_do_not_count_as_wrong_keys`.
- **Two kinds of revocation** (Ruling 2). The owner's **Revoke** in the list is final, like an API key's: in one transaction the connection is marked `revoked`, its name freed and its tokens revoked, and its URL can't be authorised again (the consent page says `revoked`) (`Accounts/Connections.cs:179–204`, `Api/ConnectionApi.cs:170`). So is a connection that a vault deletion leaves with no vault (`vault_deleted`, "Deleting vaults and accounts" below). Everything else that revokes a connection's tokens leaves it **needing a reconnect**, with its reason, and the app's Reconnect on the same URL renews it after a fresh consent: a reused code (`code_reused`) or refresh token (`refresh_reused`), the app's revocation (`client_revoked`), a password change that revokes the API keys (`password_changed`), a recovery (`recovery`), a deactivation (`deactivated`; a reactivation revives nothing), a rights change (`rights_changed`; the next consent shows and grants the new rights) and a re-keying of one of its vaults or of the account (`rekeyed`, §3; `Accounts/Connections.cs:214–260, 267–288`, `Vaults/VaultCatalog.Rekey.cs:390–397`). Each deletes every slot of the connection's tokens and turns their records into tombstones in the same transaction that marks the connection (`Accounts/Connections.cs:505–520`); as for API keys, a request checked before may finish, the next one is refused (§6, "Checks are per request"). Tested in `tests/Kumbu.Server.Tests/OAuth/RevocationCascadeTests.cs`, each case also for the refresh, which then gives `invalid_grant`.
- **The flow is logged by step**, one line each, `OAuth {step} {outcome}`, with the connection id, the client's host (a metadata document's host, or a registered client's first redirect host, `OAuth/OAuthClients.cs:92–99`) and the request id, never a code, token, verifier, challenge, `state` or anything of a metadata document but its host (`OAuth/OAuthEndpoints.cs:244–247`): `authorize`, `consent`, `token` (the code exchange), `refresh` and `revoke`, each with its outcome (`OAuth/OAuthTokens.cs:611–627`). So a report of an app that "connected but never used it" can be followed: `OAuth token issued` for the connection, and its `lastUsedAt` still empty, means the app got its tokens and never called the connection's URL (tested in `tests/Kumbu.Server.Tests/OAuth/SdkFlowTests.cs`, `The_flow_is_logged_without_secrets`, `A_token_issued_but_never_used_can_be_followed`, and `Nothing_of_a_token_reaches_the_log_or_the_database`).
- **The issuer is `KUMBU_PUBLIC_URL`.** Unset, the origin of every OAuth address (the issuer, the metadata's endpoints, the `resource`, the `iss` of a redirect) is taken from the request's scheme and `Host` header (`OAuth/OAuthUrls.cs:32–33`), and the two metadata documents carrying it are served `Cache-Control: public, max-age=300` (`OAuth/Discovery.cs:15`): a request with a forged `Host` could leave another origin in a shared cache in front of the server for 5 minutes. A public instance must set `KUMBU_PUBLIC_URL` (README).
- **Tested end to end with the MCP SDK's own OAuth client** (ModelContextProtocol 2.3.0), once identifying itself with a metadata document and once registering itself: from the 401 on the connection's URL through both metadata documents, the authorisation with the owner's consent and the token exchange, to a tool call; and both handshakes, the legacy `initialize` and the 2026-07-28 `server/discover`, on a connection's URL (`tests/Kumbu.Server.Tests/OAuth/SdkFlowTests.cs`).

```mermaid

    participant DB as MongoDB

    C->>M: POST /mcp/c/{id} (probe, no token)
    M-->>C: 401, WWW-Authenticate: resource_metadata

    O-->>C: resource = /mcp/c/{id}, authorization_servers
    C->>O: GET authorization-server metadata
    O-->>C: endpoints, S256, CIMD supported
    opt client_id is a metadata URL (CIMD)
        O->>C: GET https://claude.ai/oauth/mcp-oauth-client-metadata
        C-->>O: name, redirect_uris (cached, checked)
    end

    Note over U,W: Authorisation and consent
    U->>O: GET /oauth/authorize (client_id, redirect_uri, PKCE S256, resource, state), anonymous
    O->>DB: store the request (10 min)
    O-->>U: 303 /consent?request=id
    U->>W: open the consent page
    opt no session

        O-->>W: 503, the request stays usable
    else
        O-->>W: app, rights, "Connect" or "Renew"
    end
    U->>W: Allow
    W->>O: POST /api/oauth/requests/id/decision
    O->>DB: vault keys wrapped under the code (slots, TTL 60 s)
    O-->>U: redirect_uri?code, state, iss

    Note over C,DB: Tokens
    U->>C: redirect with code
    C->>O: POST /oauth/token (code, code_verifier)
    O->>DB: one transaction: re-wrap to refresh and access slots, delete the code's slots, earlier tokens become tombstones
    O-->>C: access_token (60 min), refresh_token
    C->>M: tool calls, Bearer access token
    M->>DB: open the token's slots, per request
    M-->>C: results (writer label = connection name)

    Note over C,DB: Refresh
    C->>O: POST /oauth/token (refresh_token)
    O->>DB: rotate both tokens and the refresh slots, mark the old one used
    O-->>C: new pair
    C->>O: the same refresh_token again within 30 s (retry)
    O-->>C: the same pair
    C->>O: the used refresh_token again after 30 s
    O->>DB: revoke the connection's tokens (refresh_reused)
    O-->>C: 400 invalid_grant

    Note over U,C: Revocation
    U->>W: Revoke (final) or Change rights
    W->>DB: slots deleted, records kept as tombstones for 24 h
    C->>M: tool call with the old access token

Revoked wins over expired, which wins over the rest; a connection never authorised stays *waiting* whatever revokes its tokens meanwhile (`Accounts/Connections.cs`, `StateOf`). ### Device pairing and sync

The Obsidian plugin syncs a vault with an ordinary API key of the kind **device** (sync design §4, §5a). Nobody types or sees that key: the web app shows a pairing code, and the plugin exchanges it for the key. The plugin lives in a repository of its own, [SCAI-NGO/kumbu-obsidian](https://github.com/SCAI-NGO/kumbu-obsidian). What this section says about the device was checked against its code on the branch `first-release` at commit [`b279b38`](https://github.com/SCAI-NGO/kumbu-obsidian/blob/b279b38e5d2c7efc6bfc73f2ae14c625a840d2c2/) (PR #1 there, not yet released; `master` holds only the plan), cited as `kumbu-obsidian: path:line`.

- **Making a code needs a session, not the password.** `POST /api/vaults/{vault}/pairing` (sessions only, the user's own vault, `Api/PairingApi.cs:30, 36–43`) makes a code of 8 Crockford Base32 characters, 40 random bits, valid ten minutes (`Accounts/Pairings.cs:47–52, 220–229`). The web app asks for one as soon as the Connect Obsidian dialog opens, and proposes a key that never expires (`web/src/shell/ConnectObsidianDialog.tsx:32, 61`). So a stolen session can pair a device of its own (§4).
- **What a pairing record holds, and for how long.** The record holds the user, a **copy of the session's user key** (`Api/PairingApi.cs:41`), the time the session read the password, the vault and the chosen expiry: a key can only be made with the user key, and a key's name and meta are sealed under it, so they can't be filled in later. The record lives in this process's memory only (`Accounts/Pairings.cs:56`) and goes, with the copy zeroed (`Pairings.cs:265`), when the code is redeemed, when it is replaced by a new code for the same vault (`Pairings.cs:83–92`), within a minute of its expiry (a sweep runs every minute, whether or not anyone pairs, `Pairings.cs:36–40, 231–238`), or when the process ends: at most eleven minutes in all. Signing out, ending the other sessions, a password change, a recovery, a re-encryption, a deactivation and a deletion remove every open record of that user at once, its copy zeroed (`Pairings.DropAll`, called from `Api/AccountApi.cs`; tested in `Signing_out_or_ending_the_other_sessions_drops_the_open_code`). A code made from one of the user's sessions goes with any of them: records aren't tied to a session, and a new code takes a moment. A redeem that meets a vault being re-encrypted or a failing database puts the record back for the device's retry (`Pairings.cs:147–152`).
- **Why not MongoDB or Redis.** 40 bits are enough against guessing online, rate-limited, within ten minutes; they are not enough against an offline guess at a stored record that holds a user key. So the record is never written anywhere: not to MongoDB, not to a log, not to a second process such as Redis, which would add a place where it might reach a disk to gain only codes that survive a restart. This assumes a single server instance, as the hints and the vault cache do.
- **Redeeming** (`POST /api/pairing/redeem`) is anonymous and exempt from the `Origin` check (`OriginExemptMetadata`, `Api/PairingApi.cs:33`, `Api/Security.cs:13–18, 124–125`): it carries its own secret and no ambient credential, so a forged cross-site request has nothing to ride on, and Obsidian sends no `Origin` of ours. A code works once (the record is taken out before the key is made, so two redeems at once make one key, `Pairings.cs:112–113`), and only while the user's credentials and user key are what they were: a password change, a recovery or a rotation since the code was made makes it invalid (`ApiKeys.CreateAsync` checks both; `Pairings.cs:137–146`). The key it makes is named `<Vault> – Obsidian <device>`, has **write on that one vault and nothing else**, and is sealed as a device key (`Pairings.cs:124–126`). Redeeming is limited to 10 attempts a minute per client network, and refused for everyone, a right code too, while the server has seen 100 wrong codes in the last minute (the server logs a warning when that starts; `Api/PairingApi.cs:48–61`, `Api/Security.cs:162–163, 192–211`): letting open codes through would check every guess and undo the bound on guessing from many addresses. So at most about a thousand guesses fall into one code's lifetime, against 2⁴⁰ possible codes; the price is that anyone can hold off pairing for everyone, accepted on purpose (§2, §9). A wrong code says only that it isn't valid. The log names the user and the new key's id, never the code (`Pairings.cs:127`). One check runs only for a code that exists: the device name is checked against the rules for key names (`Pairings.cs:107–111`). In theory its answer could tell an open code from an unknown one. The device name's own rules are checked before the code is looked up, and the key name built from it always fits, so this check refuses nothing in practice; a test pins that every device name, valid or not, gets the same kind of answer for an open code as for an unknown one (`A_device_name_gets_the_same_answer_for_an_open_and_an_unknown_code`).
- **Device and agent keys.** The kind is sealed into the key's meta under the user key, and bound into the seal of its writer label under the key itself (the associated data ends in `:device`), so it can't be changed in the database (`Accounts/ApiKeys.cs:109, 121–122, 305–325`). It gives no right, but it decides how a write is shown: the web app's notice of changes by agents leaves a device's writes out, and "changed elsewhere" and the Activity sheet name the device as the user's own, "You changed this note in Obsidian (Laptop)", "You in Obsidian (Laptop)", and the history adds "Obsidian device" to the key's name (`web/src/note/AgentBanner.tsx:41–52`, `web/src/note/ChangedElsewhere.tsx:66`, `web/src/api/activity.ts:41–67`, `Api/WriterKinds.cs:23–30, 43–52`). So a stolen device key's writes are not flagged as an agent's. *A device back after a long pause stands out instead* (#43), since by default the key never expires: after a write by any API key commits, the key's `lastWriteAt` is written, in the clear and at most once a minute (`lastUsedAt` can't tell, as a device asks for the version list all the time; only a write says that someone wrote with it), and a write more than 14 days after the previous one records the return, `quietSince` (the last write before the pause) and `resumedAt` (`Vaults/EncryptedNoteStore.cs:707–712`, `Accounts/ApiKeys.cs:458–487`). The device's writes since then are in the notice of changes, as long as the user's previous sign-in came before the return (`Api/WriterKinds.cs:32–41`, `Api/NoteApi.cs:612–636`), as a warning that names the device and the pause and leads to Access, where the device is revoked: "Obsidian on Pixel 9 wrote here 2 hours ago, for the first time in 3 weeks. If that wasn't you, revoke the device in Access." (`web/src/note/AgentBanner.tsx:84–132`; tested in `tests/Kumbu.Server.Tests/Api/WriterKindTests.cs`, `web/src/note/NoteView.test.tsx`). Its limits: a key's first write starts the record and warns of nothing, so a key that has never written (paired before this was built, or one that only read) is first flagged after a pause following its first write; a thief who writes within 14 days of the device's last write, or only reads, is not flagged; and nothing is sent, the warning waits for the user to open the note. It also decides how long the key's changeset stays open: 2 idle minutes for a device, as for a session, and 10 for an agent (`Auth/RequestCaller.cs:48`, concept §4). A device key paired before this was bound into the writer seal counts as an agent there only.
- **On the device.** The plugin needs Obsidian 1.11.4 or newer and does nothing without `app.secretStorage` (`kumbu-obsidian: src/main.ts:48–51`, `src/obsidian/secret.ts:5–8`). The redeemed key goes straight into `SecretStorage` under an id `kumbu-<vault>-<hash>-<device>` (`src/main.ts:134–135`, `src/engine/paths.ts:47–55`); the plugin's own comment there notes that `SecretStorage` is shared by every vault of the Obsidian app. The plugin's `data.json` holds no key: the server URL, the Kumbu² vault, the device name, the secret's id and whether pairing stored it (`ownsSecret`), and the sync state (each path's base version, the `since` cursor, the times of the last full and last sync; `src/main.ts:18–22, 157–159`). What `SecretStorage` does at rest on each platform has not been checked, and the plugin's code can't show it, so this document promises nothing about how the key is protected on the device's disk (§9). The synced notes are ordinary files in the Obsidian vault: outside the server's encryption at rest (§2).
- **Where the device sends the key.** Only to the server URL in its settings, as `Authorization: Bearer` (`kumbu-obsidian: src/api/client.ts:113–116`), through Obsidian's `requestUrl` (no CORS, so no `Origin` of ours; `src/obsidian/http.ts:10–18`). The URL must be `https://`, or `http://` for `localhost` and `127.0.0.1` only (`src/engine/paths.ts:70–86`); this is checked before pairing and again before every start, because `data.json` can be edited by hand or synced from elsewhere (`src/main.ts:90–96, 121–126`), so the WebSocket is `wss://` except on those two hosts (`src/live/hints.ts:35–41`). The plugin acts on a hint only for its own vault (`src/live/hints.ts:115`).
- **What the device sends.** The path and text of every `.md` file outside dot folders; other files ("attachments") and anything under a dot folder (`.obsidian`, `.trash`) stay on the device (`kumbu-obsidian: src/engine/paths.ts:23–27`). Pairing sends the code and the device name (`src/api/client.ts:121–125`). A conflict copy, `<note> (conflict <device> <date> <time>).md`, holds the device's text with a callout naming the device and the other writer, and is an ordinary `.md` file, so it syncs to the server like any note (`src/engine/paths.ts:32–36`, `src/engine/conflict.ts:14–31`, `src/engine/engine.ts:34, 449–463`).
- **What stays on the device after a delete.** A note trashed in Kumbu² is trashed on the device with Obsidian's own trash, as the user set it up (system trash, the vault's `.trash`, or deleted; `kumbu-obsidian: src/obsidian/vaultFiles.ts:72–82`). Choosing "Keep Kumbu²" for a conflict always puts the device's text in the vault's `.trash` first (`src/obsidian/vaultFiles.ts:66–70`). So plain text can outlive a delete on the device.
- **Disconnecting and a lost key.** Disconnect, a cancelled first sync and a key the server refuses (`401`/`403`, or a `404` for the vault on the version list; a socket closed with `4401` makes the plugin check, and that request meets the refusal) make the plugin forget the connection; it blanks the secret it stored by pairing, since the 1.11.4 API has no delete (`kumbu-obsidian: src/main.ts:188–199, 262–265`, `src/obsidian/secret.ts:20–23`, `src/api/client.ts:36, 164–167`, `src/live/hints.ts:124–139`). Since the plugin's change for this (`kumbu-obsidian` issue #2, not yet released), Disconnect and a cancelled first sync first revoke a key the plugin got by pairing: `DELETE /api/key`, with which any API key revokes itself and nothing else (`Api/SyncApi.cs`; its sockets close at the next 30-second check). If that fails (no network, a server older than 0.2.5), the plugin forgets the connection all the same and says that the key still works and where to revoke it. A key typed in by hand (below) is never revoked. Until a device runs that version, a device key stays valid after Disconnect until the user revokes it on the API keys page.
- **A key typed in by hand.** Under "I have an API key already" the user can pick any key from `SecretStorage` instead of pairing (`kumbu-obsidian: src/obsidian/settingsTab.ts:65–84`, `src/main.ts:140–143`). It is then an ordinary agent key with whatever vaults and rights it was made with, not a device key: its writes show as an agent's, and the plugin never blanks it (`ownsSecret` false).
- **The version list** (`GET /api/vaults/{vault}/versions`, `Api/SyncApi.cs:79–116`) answers any caller for exactly the vaults its credential opens, as every other endpoint does, with the same `404` for a vault it doesn't open as for one that doesn't exist. Each request touches the vault, so a syncing device keeps its vault unlocked as a polling agent does (`SyncApi.cs:87`, §2). The change record behind `since` is a per-path time on the unlocked vault in memory (`Vaults/UnlockedVault.cs:49`); it goes with the vault when it is locked, and a cursor from before gets the full list.
- **Hints.** `POST /api/ws-ticket` gives an API key a ticket (`kumbu_wst_` and 32 random bytes) for one WebSocket within 30 seconds; the server keeps only its SHA-256 (`Api/SyncApi.cs:50–60`, `Sync/SyncTickets.cs:20–42, 53`). The ticket is bound to the key and to the vaults the key opened when it was made. On `GET /api/ws?ticket=…` the key is checked again before the upgrade (`Api/SyncApi.cs:46, 63–70`), and the hub (`Sync/SyncHub.cs`) sends `{"type":"changed","vault":"<name>"}` for those vaults only, and for no other; a hint names the vault and nothing else, and the connection holds no vault open. Every 30 seconds each connection's key is checked again: revoked, expired or its owner deactivated, the socket is closed (`4401`); a vault deleted is dropped (`SyncHub.cs:26, 94–111`). A re-keying revokes the keys with the vault, device keys included (the plugin has to be paired again), so their sockets close at the next check. Each send has a 10-second limit and a close is bounded (`SyncHub.cs:30, 33`), so a client that stops reading can hold up neither its own close nor anyone else's, nor the check itself. The server pings every 30 seconds and drops a peer that answers none within a minute (`Program.cs:192`). Each socket costs a MongoDB lookup every 30 seconds, so a key holds at most 10 open tickets and 4 sockets: a new ticket beyond that drops the key's oldest, and a new socket closes the key's oldest with `4409` (`Sync/SyncTickets.cs`, `Sync/SyncHub.cs`). The newest wins rather than being refused, so a socket the client gave up on, not yet noticed by the ping, never locks out its reconnect. The ticket appears in the proxy's access log, single-use and worthless after 30 seconds (§7).

### Export and import

- **Export.** A signed-in session can download one or more vaults, or one checkpoint, as a ZIP: `GET /api/vaults/{vault}/export`, `GET /api/export?vault=…&vault=…` and `GET /api/vaults/{vault}/checkpoints/{name}/export` (`Api/ExportApi.cs:36–54`). API keys, connections and the dev token get 403 (`ExportApi.cs:38`). The ZIP holds the current notes, verbatim, and the current attachments (PDFs, images), byte for byte, at their paths, without history, trash, checkpoints or settings; a note (or file record) whose stored data doesn't open can't be exported, and is counted per vault in a `MISSING.txt` at the ZIP's root instead (its path is sealed with it, so it can't be named); a checkpoint's ZIP holds its notes and files as the checkpoint has them (`ExportApi.cs:22–33, 94–151`). Every vault is checked and its notes read before the first byte, so a refusal is a status, not a broken ZIP; of the attachments only their records are read then. The ZIP is then streamed, never held whole in memory: each file's bytes are opened only when its entry is written, one file at a time, and go out in pieces of 64 KiB. A file whose bytes don't open by then is never left out: the download is cut off with an error in the log naming its blob id, so the browser shows a failed download rather than a ZIP that looks complete; a damaged note, by contrast, is never listed, so the export completes without it and counts it in `MISSING.txt` (`ExportApi.cs:234–305`).
- **Several files as a ZIP.** The gallery's multi-select downloads up to 100 attachments of one vault in one request, `GET /api/files/{vault}/zip?path=…&path=…`, or the same fields (`path` once per file, `tz`, `ticket`) as a form, `POST /api/files/{vault}/zip` with an `application/x-www-form-urlencoded` body, which the web app submits (a hundred paths would make the GET's request line too long for servers and proxies). Both share one handler, so the checks, limits and logging below are the same; the POST, being state-changing in HTTP's terms, also passes the `Origin` check (§7, `Api/Security.cs:124–134`), which a same-origin form post meets and another site's doesn't; it reads the form by hand, with no antiforgery token, the Origin check standing in for one. The web app posts it into a hidden frame of the gallery (`target`), so a ZIP goes to disk and an error answer, the server's JSON, loads into the frame, where the gallery reads it (same origin) and shows the sentence; for that frame, and only for this route, the responses carry `frame-ancestors 'self'` (security headers, below). The files are at their paths in the vault (checked as every API path is: no `..`, no empty segment, so no entry unpacks outside its folder), each checked to exist before the first byte (`ExportApi.cs:51–58`, `159–207`). It is treated as an export: session-only, a ticket from the password by default, and logged with the user's id, the vault's id, the number of files and their bytes, and whether the password was asked, once the whole ZIP is out (a cut-off download is logged as such instead). Each user can turn the password off for their own multi-file downloads in Settings, "Ask for my password when downloading several files" (default on; stored on the user only when off, `Accounts/UserDocuments.cs:101–104`; `GET`/`PUT /api/account/preferences`, session-only, `Api/AccountApi.cs:154–155`). Turning it off needs the password (limited like a password change) and is logged; turning it on doesn't. The log line of every download stays either way. Downloading one file never needs the password, as opening a note doesn't.
- **What an export gives up.** The ZIP is plain text and plain files: it leaves Kumbu²'s encryption at rest, and what the browser saves is the user's to protect (§2). Export is a `GET`, so the `Origin` check doesn't apply; a page on another site can't start one with the user's cookie, since the cookie is `SameSite=Strict` (§7). An export is a heavyweight operation, so it asks for the password again, as deleting a vault does: `POST /api/export/ticket` checks it (limited like a password change) and answers a ticket (`kumbu_ext_` and 32 random bytes) for one export by the same user within 30 seconds, kept by its SHA-256 only, one per user (`Api/ExportTickets.cs`, `Api/ExportApi.cs`). The download carries it as `?ticket=`, since a browser download is a plain `GET` and a password never goes into a URL; without a valid ticket every export answers 403 before anything is read. So a stolen session alone can't take the notes out. Each export is logged with the user's id, the vaults' ids and the numbers of notes and files, never a name (§7). The request line names the vaults or the checkpoint, or the files of a multi-file download, and the browser's time zone (`web/src/data/exportUrl.ts:10–18`), and the answer's `Content-Disposition` the vault's name (`ExportApi.cs:212`), so the proxy's access log holds them (§7).
- **Import.** A ZIP is unpacked in the browser, not on the server: the file itself never reaches the server (`web/src/data/readImport.ts`, with fflate 0.8.3, `web/package.json:20`). A first pass reads only the ZIP's directory; only entries that are notes by name and declared size are inflated, at most 1 MiB each and 256 MB per import, summed from the sizes the ZIP declares (`readImport.ts:61, 98–106, 148–152, 166–169`, `web/src/upload/planUpload.ts:7`); notes that aren't UTF-8 are skipped. That bound on memory relies on fflate allocating each entry at exactly its declared size; tests with ZIPs that lie about their sizes pin it (`web/src/data/readImport.test.ts`): a note that unpacks to more than it declares is cut at the declared size, never grown, and a stored entry is cut at its compressed size, so it is never larger than the ZIP itself, and the 1 MiB check still refuses it. Only the user's own tab is at stake. The notes then go up through existing endpoints: creating a vault (`POST /api/vaults`, session-only, `Api/NoteApi.cs:141`), its version list, and the ordinary upload endpoint (`web/src/data/runImport.ts:50–61`, `Api/UploadApi.cs:45`), whose limits and path checks apply to every note (§7).

### Deleting vaults and accounts

All in `src/Kumbu.Server/Accounts/Deletion.cs`, from a signed-in session only (API keys and the dev token get 403):

- **A vault**, by its owner, with the current password (checked before the vault is looked up, so without it nobody learns whether the name exists; the password-check limit applies, 429) and the name typed out exactly (`Deletion.cs:49–60`, `POST /api/vaults/{vault}/delete`, `Api/NoteApi.cs:142, 221–229`). Only the owner's user key finds a vault by name, through the keyed name hash of its slot; no vault is unlocked to find it (`VaultCatalog.cs:291–314`).
- **One's own account**, with the current password (it must open this very user key, `Accounts/UserCatalog.cs:209–215`, and counts against the password-check limit) and the username typed out (`Deletion.cs:66–81`, `POST /api/account/delete`, `Api/AccountApi.cs:114`). The primary admin's can't be deleted: there is always one.
- **Any other user**, by an admin, active or not, in one step, for a privacy request say, with their username typed out and the admin's own password (the same password-check limit; a stolen admin session alone deletes nobody) (`Deletion.cs:89–108`, `POST /api/admin/users/{id}/delete`, `AccountApi.cs:147, 329–337`). Never the primary admin (checked again in the transaction) and never the admin themselves: that answers 403 and points to Settings, where their own deletion needs their own password and username anyway. An active user needs no deactivation first: their session slots, API keys and connections go in the same transaction as the rest, so their next request finds no session and is refused (401), and a request already under way writes nothing, since its vaults are tombstoned (tested in `Deleting_an_active_user_ends_their_session_and_writes`).
- **The receipt** the admin gets (`DeletionReceiptView`, `AccountApi.cs`; shown and downloaded as text by `web/src/routes/admin/DeletionReceipt.tsx`) holds the user id, the username, the deleting admin's username, the time, the counts of vaults, notes (documents in `notes` of the deleted vaults, counted by vault id, so no key is needed), files (documents in `attachments`, one per PDF or image, counted the same way; their versions and trash not counted), API keys, connections and erased invitations (that of the invitation the user joined with, below; `Accounts/Deletion.cs:8–11`, `Api/AccountApi.cs:89–100`), the labels of every external embedding provider the instance has configured (which one a vault used is sealed with it, and a vault may have switched back, so the receipt can only say they *may* have received text), the configured privacy contact, whether the id went into the list of deleted users (`listed`), and that backups are not reached. No content, no vault or note name: the server can't read those without the user's key, and the receipt is built from what it reads without one (tested in `The_receipt_names_no_vault_or_note`).

What goes, in **one transaction** (`Vaults/VaultCatalog.cs:528–681`, `Deletion.cs:156–202`): each vault document, every slot on those vaults (the owner's, the new key's of a re-keying under way, API keys', the dev token's, recovery), the vaults' ids in their owners' `rekeyPending` (`VaultCatalog.cs:645`), every document in `notes` (with the history inside), `trash`, `moves`, `embeddings`, `checkpoints` and `checkpoint_texts`, `attachments`, `attachment_trash` and `blobs` (the files' bytes); for an account also the user, their password, recovery and session slots, their API keys and the keys' slots, and their connections with every code and token record (tombstones included), the tokens' slots and the pending authorisation requests (`Accounts/Connections.cs:552–563`), and the note and the link to the user (`usedBy`) of the invitation they joined with (`Deletion.cs:177–185`). An API key that had slots on a deleted vault and none elsewhere can open nothing any more: it is revoked in the same transaction, its name freed (`VaultCatalog.cs:574–584, 661–681`); a key with other vaults keeps them. A connection loses the deleted vaults from its list of vault ids (in the clear, Ruling 17, so this needs no key), and the slots of its tokens on them go with every other slot on them; one left with no vault is revoked for good, `vault_deleted`, its name freed and its tokens revoked, and one with other vaults keeps them, its tokens still opening those (`VaultCatalog.cs:582–585`, `Accounts/Connections.cs:529–546`). Its sealed rights still name the deleted vault, so the list and the consent show and grant only the vaults still in its list (`Accounts/Connections.cs:403`, `OAuth/OAuthTokens.cs:729–735`). Keys, codes and tokens are wrapped from vault keys opened before their transaction, so a vault deleted meanwhile must not end up in a new slot: the issuing transaction re-reads the connection and wraps only the vaults still in its list, and increments a counter on the connection's document (`wraps`), which the deletion writes too, so the two conflict and the one retried sees the other. A counter, because MongoDB writes nothing, and so conflicts with nothing, for an update that changes nothing, such as the exchange's `$unset` of revocation fields a connected connection doesn't have; the exchange and the refresh also delete the slots of the code or token they spend, the one on the vault included, which the deletion deletes too (`OAuth/OAuthTokens.cs:190–201, 289–292, 308, 324–326, 428–431, 451, 470, 544–566`). A key or connection created, or a connection given new rights, checks inside its transaction that its vaults still exist, and writes the user's document, which the deletion writes as well (`vaultsDeleted`), so the same holds (`VaultCatalog.cs:628–659`, `ApiKeys.cs:149–151`, `Accounts/Connections.cs:141–143, 234–244`; raced in `A_vault_deleted_while_apps_connect_leaves_no_slot_and_no_connection_naming_it`). A fault leaves everything or nothing. Nothing brings a deleted vault back or writes for it afterwards (`VaultCatalog.cs:528–704`): the ids are tombstoned in the process first, which every load and write checks, and an indexing before each embedding call and before it stores anything; an embedding call of the vault under way is cancelled, so no more of its text goes to an external provider and a provider that hangs does not hold the deletion up; the vault in memory is then taken off writes and indexing (both its gates) and marked deleted after the commit; and loading is held off only after the gates, for the transaction, so a request that read the slot and the vault document just before the commit cannot put the vault back into the working set, while requests on other vaults never wait for a slow provider (`VaultCatalog.cs:885`, `EncryptedNoteStore.cs:462`, `Search/SearchIndex.cs:134, 157–163, 181`), so an older object of the vault, locked meanwhile but still held by a request or waiting in the search queue, writes nothing either. After the commit the content collections are swept once more, for a write of such an older object that passed its check just before the tombstone was set and committed during the deletion. One that commits only after that sweep, a window of milliseconds between a check and its write, would leave sealed documents of a vault that no longer exists: unreadable without its key, and counted nowhere. A new vault and a new session each write the user's document in their own transaction (`vaultsCreated`, `sessionsStarted`, as an API key does with `keysCreated`), so one that races the account's deletion either commits first and is caught by the deletion, or conflicts with it and then finds no user and is refused (`VaultCatalog.cs:261–275`, `Accounts/Sessions.cs:61–77`); a vault made between the deletion's first read and its transaction is deleted right after, in a second transaction (`Deletion.cs:192–200`).

**The list of deleted users** (`Accounts/DeletionList.cs`): after the transaction commits, an admin's deletion and a user's own both append the user id (random, no name) to `<Kumbu:Deletions:Path>/deleted-users` (Compose: `/deletions`, a volume of its own), created `0600` in a `0700` directory and flushed to disk, one writer at a time (`DeletionList.cs:34–46`). It lives outside MongoDB because a list inside it would be rolled back by the restore it must detect. If it isn't configured or can't be written, the deletion still stands; the receipt says it wasn't listed and the error is logged (tested in `An_unwritable_list_never_blocks_a_deletion`). At start, and on the admin's users page (`GET /api/admin/deletions`), the server looks for listed ids that exist in `users` again (`Accounts/RestoredDeletions.cs`): it logs a warning with their ids, and an admin can delete them again in one step with their password (`POST /api/admin/deletions/repeat`, `Deletion.cs:117–148`), one transaction per user, never the primary admin or the admin themselves. Only lines that are user ids count; a malformed file is read as the ids in it. The list is a check, not a guarantee: whoever can write the volume can shorten it. Only account deletions are listed (`Deletion.cs:75, 103`); deleting a single vault is not (`Deletion.cs:49–60`), on purpose: a restored account is seen by nobody (its user is gone, and an admin sees no content), but a restored vault appears again in its owner's sidebar, and the owner is the one who may and can delete it again. Deleting it automatically after a restore would undo a restore the operator may have meant, and a warning in the log would name a vault id the admin can't place. A privacy request goes through deleting the account, which is listed (§7, §9).

What stays: **the invitations the user created**, and the one they joined with as a used invitation without its note or its link to them. The ones they created are the instance's record of who invited whom (their `createdBy` is the deleted user's id; their notes name the invitees, not the user); the accounts they made exist on their own; an open one stays usable until it expires and any admin can revoke it, as after a deactivation. The one they joined with keeps its role and dates, so it still counts as used, but its note (admin-typed, often the invitee's name or address) and `usedBy` are unset in the same transaction, so nothing left in the database names or points to the person (tested in `Deleting_a_user_erases_the_note_and_link_of_the_invitation_they_joined_with`); the receipt says so. Backups taken before (§7), and removed documents that MongoDB has not yet overwritten in its files (§5.4), keep the sealed data. So does an external embedding provider, for what a vault that used one sent it (§5.5): deleting the vault recalls nothing from there. A vault deletion's log line names its owner, the vault id and counts; an account deletion's names the deleted user by id only (and the deleting admin), with counts; never a vault name or content. Lines written earlier, while the user existed (sign-ins, the invitation they used), keep their username (`Deletion.cs:58, 76, 104, 139`).

### Invitations and the first admin

Accounts exist only by invitation: single-use, expiring (7 days by default, at most 30), revocable, with a role (`Accounts/Invitations.cs`). The code is 32 random bytes; the database holds only its keyed hash. The code travels in the link's fragment (`/join#…`), which browsers do not send, so it reaches no request line, proxy log or `Referer`. The first (primary) admin is created with `docker compose exec kumbu kumbu bootstrap-admin`, which prints a 24-hour link on standard output, never to the log, and refuses once a primary admin exists (`src/Kumbu.Server/Cli/BootstrapAdmin.cs`). So the first account goes to whoever has a shell on the container, not to whoever first finds a fresh server. A new account gets one vault, *Welcome*, created when it joins under the user's key like any other vault and filled with the embedded welcome notes as writer `seed` (`src/Kumbu.Server/Welcome/WelcomeVault.cs`); if that fails, the join still succeeds, the server logs only ids and the error's type, and a half-written vault is deleted again. Creating it gives up after 10 seconds and the clean-up after 5 (`Welcome/WelcomeVault.cs:33, 36`); like every new vault it uses the internal embedding model, so nothing of it leaves the server.

### Passwords

At least 12 characters (counted as characters, not bytes), not one of the 10,000 most common passwords, nor such a word padded with digits or punctuation (`Accounts/PasswordPolicy.cs`). The sign-up form warns that username and password are less safe than GitHub with a passkey, which come later (v3, §9) (`web/src/components/PasswordField.tsx:47`).

### Recovery, and why there is no password reset

At sign-up the user gets a **recovery key** (32 random bytes, Base32 with a `kumbu-rk-` prefix, `src/Kumbu.Core/Crypto/RecoveryKey.cs`), shown once, to download (as `kumbu-recovery-key.txt`, without the username) or copy. The join screen does not let the user continue until it was downloaded or copied and they ticked that it is stored. (The account itself already exists at that moment; the confirmation is a step of the web app, not a server-side condition.)

The recovery key opens the user key. With username and recovery key, the "forgot password" screen sets a new password. This ends every session, revokes every API key, disconnects every app (`recovery`), **replaces the recovery key**: the used one opens nothing from then on, and the answer carries the new one, and **rotates the user key**: the vaults are wrapped under a new user key in the same transaction, and each is then re-keyed in the background, after the answer (§3; `UserCatalog.cs:125–158`, `Api/AccountApi.cs:213–223`). The screen shows it once, under the same rules as at sign-up, and says that the old key no longer works, that agents need new API keys and that apps need to reconnect (`web/src/routes/ForgotPassword.tsx:35`). Regenerating the recovery key needs the current password and invalidates the old one at once (`UserCatalog.cs:190–205`), so a stolen session alone cannot make a recovery key and lock the owner out.

The writes of a recovery come in an order that a crash cannot turn into a lock-out or a dead key: the credentials stamp, then the revocation of the API keys and of the connections' tokens, then one transaction that rotates the user key and writes the new password slot and the new recovery slot with it (§3), then the final stamp and a second revocation, as for a password change (`UserCatalog.cs:268–319, 327–347`). The rotation is prepared, Argon2 included, before that transaction; if it keeps meeting concurrent changes, the recovery answers 409 and wrote nothing but the stamp and the revocations, so the recovery key still works. The recovery slot is replaced only if it is still the one that was opened, so of two recoveries racing with the same key exactly one gets through; the other gets 401 and sets nothing, and nobody is shown a new key that no longer works. A crash before the transaction leaves the old password and recovery key working (the API keys may already be revoked), so the user simply recovers again; a crash after it, before the answer arrives, leaves the user the password they just chose. The forgot-password screen says so after a server fault or a lost connection: try to sign in with the new password and, if that works, make a new recovery key in Settings (`web/src/routes/ForgotPassword.tsx`).

What this means for a stolen recovery key: whoever uses it first holds the account, and the other's copy no longer works. That was already possible before, with one more step (the thief could make a new recovery key with the password just set); what the change removes is the back and forth, and the thief's API keys and apps surviving the owner's recovery. The owner's recovery also rotates the user key and re-keys the vaults (§3), so what the thief may have copied from the database, with the old recovery key, reaches nothing written afterwards.

**There is no password reset by an admin or the operator, by design.** Nobody but the user holds a credential that opens their user key. Without password and recovery key, the vaults cannot be decrypted by anyone, and the web app says so at sign-up. The alternative — an escrow key held by the instance — would give the operator or an admin a way into every vault and defeat the point of §4.

### Deployment shape

The server speaks plain HTTP on port 8080 inside its container and relies on a TLS-terminating reverse proxy: Docker Compose behind Traefik with Let's Encrypt, say, or a Kubernetes ingress. Whoever runs an instance is its operator in the sense of §2 and §4.

`compose.yaml` as shipped is a local set-up: the server's port is published on localhost (`127.0.0.1:${KUMBU_PORT}:8080`), and server and MongoDB share one default network, MongoDB listening on all its interfaces, without authentication unless `KUMBU_MONGO_PASSWORD` is set (below). With `KUMBU_TRUSTED_PROXY=true` and that port published, any local process could send its own `X-Forwarded-For` and pick the address rate limits count against. The public shape is the Traefik override, `compose.traefik.yaml` (README, "Behind Traefik"), used with `compose.yaml`:

- **No published port for the server** (`ports: !reset []`): Traefik, on a network of its own with the server (`kumbu-proxy`), is its only way in, and only Traefik publishes ports, 80 and 443.
- **TLS**: Traefik terminates it with a Let's Encrypt certificate for `KUMBU_HOST` (TLS-ALPN challenge) and redirects HTTP to HTTPS. Traefik sets no security headers; HSTS and the others come from the server (above), which sees the public URL as `https://`.
- **The trusted proxy**: the override sets `KUMBU_PUBLIC_URL=https://${KUMBU_HOST}` and `KUMBU_TRUSTED_PROXY=true`. Traefik's entry point trusts no forwarded headers (no `forwardedHeaders.trustedIPs`), so it drops a client's `X-Forwarded-For` and `X-Forwarded-Proto` and sends its own: the client's address as the only `X-Forwarded-For` entry, the one the server reads (`Program.cs:161–173`). Checked against a running stack: 24 wrong bearer keys, each with a different made-up `X-Forwarded-For`, got `401` 20 times and then `429`, while a request from another address still got `401`.
- **MongoDB on an internal network**: the default network, which only MongoDB and the server are on, is `internal`, so Traefik never reaches MongoDB and MongoDB has no route out; the server reaches the internet through the proxy network ("Outbound connections", above).
- **Request bodies and timeouts**: Traefik sets no body size limit, so the server's own (15 MB for a file, above) applies: through the override a 14 MB upload is stored and a 16 MB one gets the server's 413. Reading a request may take 10 minutes rather than Traefik's default of 60 seconds, which would cut off a 15 MB upload slower than about 2 Mbit/s; the sync WebSocket is not bound by it and passes without configuration.
- **Not set by the override**: the dev token, which a public instance leaves unset (`.env`); Traefik's access log stays off (its default, and below). IPv6 clients reach Traefik through Docker's userland proxy unless the proxy network has IPv6 (`enable_ipv6`, left to the operator), and then share one address for the rate limits. Traefik reads the labels through the Docker socket, mounted read-only, which still gives it the whole Docker API.

### Supply chain: the server image

The server image is built by GitHub Actions from the repository (`.github/workflows/docker.yml`) and published as `ghcr.io/scai-ngo/kumbukumbu`. Every third-party action in the workflow is pinned to a commit hash, not a movable tag. Pull requests are built but never pushed. A push to `master` publishes branch- and commit-tagged images; `:latest` and the version tags move **only** on a `v*.*.*` release tag, so a merge alone never changes what a server tracking `:latest` runs. Every pushed image is signed with cosign, keyless, through GitHub's OIDC identity for that workflow run; the signature is recorded in Sigstore's public transparency log. To verify an image before running it (the README, "Images and releases", has the same command for any build of the workflow):

```sh
cosign verify ghcr.io/scai-ngo/kumbukumbu:latest \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp '^https://github.com/SCAI-NGO/kumbukumbu/\.github/workflows/docker\.yml@refs/tags/v'
```

The identity names the repository, the workflow and the ref it ran for (`@refs/tags/v` accepts release builds only; `@` alone also accepts `master` builds). A valid signature shows that the image was built by this workflow in this repository; it says nothing about the review of the code it was built from. Pinning by digest (`ghcr.io/scai-ngo/kumbukumbu@sha256:…`, `KUMBU_IMAGE` in `.env`) after verifying makes the deployment immune to a later re-tag. What the build pulls in is pinned too: the base images by digest, with the tag beside it (`node:22-slim`, `mcr.microsoft.com/dotnet/sdk:10.0` and `aspnet:10.0`, `Dockerfile`), the npm packages by `web/pnpm-lock.yaml` (`--frozen-lockfile`), the NuGet packages, transitive ones included, by a `packages.lock.json` per project (`RestorePackagesWithLockFile`, `Directory.Build.props`), restored in locked mode by CI and the image build, which fail if a project's packages differ from its lock file (`.github/workflows/ci.yml`, `Dockerfile`). Dependabot proposes updates to the actions, the base images' digests and the NuGet packages weekly (`.github/dependabot.yml`); each is a pull request to review, not an automatic change. The MongoDB image (`mongo:8`, `KUMBU_MONGO_IMAGE`) is pulled by tag at deployment, not built in; pin it by digest in `.env` the same way. The build gets `VERSION`, `GIT_SHA` and `BUILT_AT` from the workflow (`.github/workflows/docker.yml:86–89`) and builds them into the web app, the server's version and `/app/VERSION` (`Dockerfile:12–14, 24–28, 32–39`); that is what `X-Kumbu-Version` reports. A second workflow publishes the project's static site to GitHub Pages, its actions pinned by hash and with `persist-credentials: false` (`.github/workflows/pages.yml`); it never touches the server image.

Points for the operator, not handled by the code:

- **Proxy access logs** contain what the server's own log leaves out: request lines under `/api` name vaults and note paths (`/api/notes/Work/plan.md`) and carry search queries (`/api/search?q=…`, `/api/search/earlier?q=…`), checkpoint names (`/api/vaults/Work/checkpoints/before-cleanup/tree`), which the database keeps only as keyed hashes (§5.3), the vaults of an export (`/api/export?vault=Work`) with its ticket (`&ticket=…`), and the sync WebSocket's ticket (`/api/ws?ticket=…`), both used once and worthless 30 seconds after they were made. Disable the access log for `/api` or strip paths and query strings (README, "Security notes for a public instance").
- **MongoDB** runs in Compose without TLS, and without authentication unless `KUMBU_MONGO_PASSWORD` is set. With it, MongoDB starts with a key file it generates once inside its data volume (a replica set with authentication needs one), its health check creates the root user `kumbu` through MongoDB's localhost exception, which holds only while no user exists, and the server signs in with `Kumbu:Mongo:User` and `Kumbu:Mongo:Password` (or `Kumbu:Mongo:PasswordFile`, a file holding it), kept apart from the connection string (`compose.yaml`, `src/Kumbu.Server/KumbuOptions.cs:190–213`). This also works on an existing data volume (README, "Security notes for a public instance"). The password sits in both containers' environment, unless it is given as a Docker secret instead (`Kumbu:Mongo:PasswordFile` for the server, `KUMBU_MONGO_PASSWORD_FILE` for MongoDB's start and health check, README), as the embedding providers' keys are (§5.5); the server refuses to start with both a password and a file, or with a file it can't read or that is empty (`KumbuOptionsValidator.cs:38–49`). Without it, MongoDB is protected only by being on an internal network (in the shipped `compose.yaml`, the same network as the server; see above). Traffic between proxy and server, and between server and MongoDB, is unencrypted inside the host. On Kubernetes, use network policies and MongoDB authentication.
- **Swap and core dumps** of the server process can hold plaintext and keys; disable them.
- **Backups** of MongoDB are safe to store in the sense of §4 (sealed), but contain the metadata of §5.6 and the password slots that offline guessing works on. An old backup opens with any credential that was valid when it was taken, but only what it held. Per vault, once that vault's re-keying has finished, such a credential opens nothing written to it since, neither in a later backup nor in the database; documents the re-keying found damaged may stay under the old key, and dev-token vaults are never re-keyed (§3). **Restoring a backup brings back the credentials of that moment:** old passwords and recovery keys work again, and API keys revoked since are valid again, with their slots (`Accounts/ApiKeys.cs:295`). After a restore, users should change their passwords, make new recovery keys and review their API keys. A restore also brings back the vaults and accounts deleted since, with their data and the credentials of that moment. Accounts are on the list of deleted users, and the users page offers to delete them again (§6); a single deleted vault is not listed, on purpose: it is back in its owner's sidebar, and they delete it again (§6). It undoes the re-keyings since, too: re-encrypt again.

## 8. AI providers

- **How agents and apps connect:** in one of two ways, each made by the user for chosen vaults and rights (§6). A local agent (Claude Code, Hermes and other MCP clients on the user's machine) uses an **API key** (`Authorization: Bearer kumbu_…`) at `/mcp`; the connection goes from the user's machine to Kumbu², and the key sits in the user's local configuration. An app that signs in with OAuth (claude.ai on the web, in the desktop app and on the phone, and others) uses a **connection**: the user creates it in Kumbu², pastes its connector URL `/mcp/c/{id}` into the app, and allows the app once on Kumbu²'s consent page; the app's provider then calls that URL from its own servers with short-lived access tokens. The plain `/mcp` URL has no OAuth and takes no access token; a connection's URL takes nothing else (§6, §7).
- **What the provider sees:** whatever the agent reads (tool results enter the model's context) and whatever it writes. Kumbu² controls *which* vaults and *whether* the agent may write; it cannot control what the provider keeps. Users should give agents keys or connections only for vaults whose content may go to that provider under whatever rules apply to it (their own, or those of whoever the notes belong to), and read-only rights where writing isn't needed.
- **What the provider holds, with a connection:** the connection's refresh token and its current access token. Each carries slots on the connection's vaults (§3), so this is key material at the provider, for exactly those vaults and rights, until the connection expires or its tokens are revoked (§2). That is consistent with the threat model, since the provider sees their content anyway. The refresh token rotates on every use and a spent one used again revokes the connection's tokens (§6), so a copy taken from the provider stops working at the next refresh of either side. The user ends it at any time with Revoke in Kumbu²'s Access page; a password change that disconnects apps (the default), a recovery, a deactivation, a rights change or a re-keying of one of its vaults ends it too, and the app then has to Reconnect, after a fresh consent.
- **What the provider does not get:** other vaults, the user's password, user key or recovery key, and no session. With an API key in the Claude Code set-up, the key itself is not normally sent to the provider either; that holds by design of the set-up, not by enforcement, since the agent can read its own configuration.
- **Embeddings** are computed inside Kumbu² (§5.5), not by an AI provider, unless the vault's owner opted in to an external embedding provider the admin configured, or the admin made such a provider the default and the owner never chose. Then that provider receives the text of every section of that vault and every search query over it (§5.5); whether that provider is acceptable for that content is a decision for whoever configures the instance (including whether it is the default) and for each owner, not something Kumbu² checks.
- **A checkpoint's note for the AI.** "Copy for the AI" on a checkpoint's note copies where the note is and the command to read it, not its text (`web/src/note/copyForAi.ts:6–13`); the agent fetches it with its own key and rights, which need only read on the vault (`Api/HistoryApi.cs:111–113`).
- **The Obsidian plugin is not an agent.** It uses a device key against the REST API (§6) and sends nothing to an AI provider.

## 9. What comes next

None of this is built. The roadmap (`docs/concept.md` §12):

- **v2.5 (0.2.5):** Kanban boards, markdown links in `links`, `backlinks` and `mv`, and attachments (images and PDFs). Attachments get a design of their own, with the same care as the text core; how a short-lived download ticket for one attachment squares with "no secrets in URLs" (§7) is part of it.
- **v3 (0.3.0):** OKF bundles, opt-in per directory; TOTP as a second factor for password accounts; single sign-on through any OIDC provider, GitHub first, as identity only: the provider says *who* someone is, holds no key material and cannot open a vault (concept §8); passkeys with the PRF extension as a further slot on the user key, so that the identity provider identifies and the passkey unlocks. A passkey without PRF cannot unlock; such a user sets a passphrase instead, and the UI says why.
- **v4 (0.4.0):** sharing vaults between users. It extends the key model (asymmetric keys, slots for other users, revocation), gets its own section in this document and an independent review before it is built.
- **v5 (1.0.0):** "Time Machine": automatic checkpoints, and browsing a vault as it was on a date without a checkpoint made beforehand.

Open questions from v0.2.0, each with its issue; the current behaviour is described in the section named:

- **What `SecretStorage` does at rest on each platform is unverified** (#49); until it is, this document promises nothing about how a device key is protected on the device's disk (§4, §6). The plugin's code only shows that the key goes to `SecretStorage` and not to `data.json`.

Decided on purpose, each a finding of the v0.2.0 review accepted with its reason rather than left open:

- **The anonymous version includes the commit** (#44, §7). Hiding it would be security by obscurity: running a current build is the operator's responsibility, and the code is public anyway. The web app needs the commit to notice a new build between releases.
- **Pairing can be held off for everyone** (#45, §2, §6) by 100 wrong codes a minute. An attacker gains a delay and nothing else; codes long enough to need no server-wide limit would cost every user more typing at every pairing. Later, lockouts are to count by network instead of server-wide: the per-address limits already group IPv6 by /64, and counting the wrong codes by a wider prefix (a /48, say, as providers hand them out) would hold off only the attacker's own network.
- **Restores are detected for accounts only** (#48, §6, §7): a restored vault is back in its owner's sidebar, where they see it and can delete it again; a restored account is seen by nobody, hence its list.

Known gaps. Each is described where it matters above; none is scheduled yet:

- **What re-keying leaves open** (§3): a password change alone doesn't rotate the user key; re-keying revokes API keys whole and apps need a reconnect; dev-token vaults can't be re-keyed; the runner holds a user key in memory while a vault waits; damaged documents stay under the old key; the batch size is not yet checked on `mongo:8`. Revoking a credential alone still deletes only its slot, so an old backup opens with an old credential what it held.
- **Deletion does not reach backups**, nor removed documents MongoDB has not overwritten yet (§5.4, §6).
- **An expired API key that is never presented again** keeps its slots until its owner makes another key; they are refused all the same (§6).
- **API key expiry is optional**; a stolen session can create keys without one, and they outlive it until revoked, which a password change does by default and a recovery always (§4, §6).
- **Restoring a backup revives old credentials**, revoked API keys and deleted accounts and vaults included (§7).
- **Open invitations of a deleted admin stay valid** until they expire or another admin revokes them (§6).
- **Targeted sign-in lockout** through the per-username rate limit (§2).
- **A vault stays unlocked** after sign-out until idle, and any caller's use keeps it unlocked (§2).
- **Removing a checkpoint is permanent**, also for an API key with write rights, through MCP or the REST API (§4); the web app says so before it removes one.
- **Trash and move records' clear fields** are not bound into their seals (§5.2).
- **Model files are checked by SHA-256 only at download**, by size afterwards (§5.5).
- **An external embedding provider's retention can't be verified** by Kumbu²; the admin's description of it is shown to owners as the provider's promise (§5.5). Its API key is read once at startup, so replacing it needs a restart.
- **MongoDB without TLS** in Compose, and without authentication unless `KUMBU_MONGO_PASSWORD` is set; on the server's network in the shipped `compose.yaml` (§7).
- **The Traefik override** (`compose.traefik.yaml`) mounts the Docker socket into Traefik, and leaves IPv6 on its network to the operator, without which all IPv6 clients share one rate-limit address (§7).
- **The server log** records unlock and lock times per vault and key changes per user (§7).
- Rollback detection (a per-vault counter or manifest); zeroing keys in memory; rate limits shared across several instances (Redis); re-authentication before creating admin invitations; several server processes on one database (correct today, but one does not see another's new notes until its vault is reopened, and re-keying assumes one process, §3).

## 10. Glossary

| Term | Meaning here |
|---|---|
| **Vault** | A user's collection of notes (a folder tree); the unit of encryption and of API-key rights. |
| **Vault key / user key** | Random 256-bit keys; the vault key encrypts a vault, the user key wraps the vault keys of one user. |
| **Slot** | A key sealed under a KEK derived from one credential, stored in the database. Deleting the slot revokes the credential. |
| **Re-keying** | Replacing a user key or a vault key with a new random one, and sealing everything that hung on the old key again under the new one (§3). |
| **KEK** | Key-encryption key: derived from a credential, used only to wrap or unwrap another key, never stored. |
| **AES-256-GCM** | Authenticated encryption: confidentiality and tamper detection in one step. |
| **Associated data (context)** | Text bound into a seal without being encrypted; the blob only opens with the same text, which pins it to its document, vault and revision. |
| **HKDF** | A standard way to derive several independent keys from one high-entropy secret, one per label. |
| **Argon2id** | A deliberately slow, memory-hard password hash, so that guessing passwords is expensive. |
| **Keyed hash (HMAC)** | A fingerprint that only the key holder can compute; lets the database enforce uniqueness of paths and names without seeing them. |
| **Pairing code** | Eight characters, valid once and for ten minutes, that the web app shows and the Obsidian plugin exchanges for a device key (§6). |
| **Device key** | An API key made by pairing, with write on one vault, marked as a device's: its writes show as the user's own (§6). |
| **Sync ticket** | A single-use secret, valid 30 seconds, with which an API key opens the sync WebSocket for change hints (§6). |
| **Changeset** | What one writer did close together in time; the unit of a vault's Activity sheet (§5.4). |
| **Working set** | A vault decrypted in server memory while in use; locked again after 15 idle minutes. |
| **Operator** | Whoever runs and controls the server process, its host and its database. |
| **MCP** | Model Context Protocol: how AI agents call Kumbu²'s tools. |
